## Summary

**The original is server-authoritative state replication on top of a remote-call mechanism. It is neither lockstep nor a fixed-tick snapshot stream.**

- **One authoritative simulation.** A dedicated server or the host of a listen server simulates everything; a client loads the **same level from its own data**, receives a table that binds the level's entities to server handles, and then receives **state changes**. Clients do not run level scripts (macros do not run on a remote client, `main-loop.md`) and do not spawn enemies, projectiles or pickups: those come from the server.
- **Four roles, one class each** (section 3.1): single player is a **local** interface (a server that talks to nobody, except to feed a demo recording), a hosted or dedicated game is a **server** interface, a joined game is a **client** interface and a demo playback is its own interface kind. The game code asks `netIsHost` (server or local: "I own the truth"), `netIsRemote` (client or demo playback: "I do not"), `netIsServer`, `netIsLocal` and `netIsClient`.
- **State is replicated per entity, member by member, as a difference against a per-client baseline copy that is fixed when the entity becomes relevant** (for a create: the class's default state; for an initial update: the entity's state at that moment). **A regular update does not move the baseline**, so every update is self-contained ("these members differ from the baseline") and a lost update needs no repair: the next one repeats the difference (the demos show one entity sending the same payload 3,596 times). Only **members that carry the flag `SMF_NETUPDATE`** take part (248 flagged members in the 33 class tables found, section 3.4), values are quantised (floats to 1/256), and an update is at most 255 bytes.
- **Each entity has a net behaviour** (`ENetBehavior`): `NEB_NONE` 0 (not replicated: lights, markers, spawners, macros, most level geometry), `NEB_STATIC` 1 (an entity of the level file that exists on every machine; only its state is sent), `NEB_DYNAMIC` 2 (created on the server at run time; clients get a create message and a delete message) and `NEB_PREDICTED` 3 (the player's puppet and brain: **the client simulates them itself** and the server's state corrects the client). 29 classes override the default; the rest inherit `NEB_NONE`.
- **Who gets what is decided by relevance and priority.** An entity is relevant to a client when it is within a class-specific distance of the client's avatar (infinite for most gameplay classes; the model's cull distance for items, puppets, projectiles, props; the sound's fall-off for sounds). Relevant entities are updated in order of an **accumulated priority** (default 2, props and doors 5, projectiles 6, live puppets 8, players 10) until a **byte budget** (500 to 1,000 bytes) or a **time budget** (3 ms) of the pass is used up.
- **Discrete happenings are remote procedure calls, not events in a log.** 102 call sites of the remote-call mechanism were found: **36 functions go client to server** (the player's per-frame input `ClientAction`, weapon commands, use, sprint, chat, votes, creating the player, 15 cheat requests) and **62 go server to all clients** (chat lines, Netricsa speech, text effects, animation triggers, ride sequences, level end, death info, pickups, cheat effects). Effects and sounds are mostly **entities** whose members replicate.
- **Join** is the same code as running play: connect response, entity remap table, module list, strings, then a create or an initial update for every entity that is relevant, followed by the normal update stream; the **demo recorder reuses it** (the demos begin with that snapshot).
- **Time:** every packet carries the server's simulation time in 1/1024 s; a client **accumulates** the differences but **does not set its own clock from it** (no use of the server time was found in the game DLL). Clients free-run on their real clock through the same variable step as everyone.
- **Trust:** the server checks the version string (exact), the password, the ban list and the slot counts at connect; it validates vehicle-relative position claims in `ClientAction` against a speed limit; votes need more than half of the players. A client may pause the game **only if** `net_bClientsMayPause` (default 0).

Not established and parked: what the running game does (bandwidth, rates, prediction error), the packet layer, the member tables of 11 of the 29 overriding classes, the per-function reliability of the RPCs (Open questions, task IDs T01-096 to T01-101).

## Layout / rules

The sub-sections are numbered 3.1 to 3.11 and cited that way.

### 3.1 Roles and session kinds

| Kind | Engine class | `netIsHost` | `netIsRemote` | Notes |
|---|---|---|---|---|
| single player | `CLocalInterface` | yes (its `IsLocal` is true) | no | the "server" of a one-player game; **its per-frame send code runs only while a demo is being recorded** (the recorder is a pseudo client) |
| hosted (listen) game, dedicated server | `CServerInterface` | yes (`IsServer`) | no | one class for both: a listen server is a server whose host also plays (client index **16**); the session setting `sgp_bDedicatedServer` marks a dedicated one |
| joined game | `CClientInterface` | no | yes (`IsClient`) | |
| demo playback | `CDemoPlaybackInterface` | no | yes (counts as a client) | feeds a recorded message stream to the same message handlers |

- `netIsHost` = `IsServer` or `IsLocal`; `netIsRemote` = `IsClient` or `IsDemoPlayback`; `netIsServer`, `netIsLocal`, `netIsClient` are the single answers (high: the three predicates read, and `main-loop.md` already relies on `IsLocal` for the pause rule).
- **Connection table.** A server has **18 connection slots**: 17 client indices (**0 to 15 remote clients and 16 the host's own local player**, as the player create/remove code and the vote tables use them) and one **recorder slot** used by the demo recording. Connection states: free, challenge sent, authenticating, connected, disconnecting (**medium**).
- Slot counts come from the session: public, private (reserved) and observer slots are counted separately (`CNetworkSession::SetSlotCounts`, `AllocatePublicSlot`, `AllocatePrivateSlot`, `ReserveServerSlot`), the host reserves one for itself; `net_iMaxClients` defaults to 0 (the session sets it from `sgp_ctMaxPlayers` and `sgp_ctPrivateSlots`), `net_iMaxObservers` 16, `net_iVIPReserve` 0.

### 3.2 Architecture

1. **Authority.** All gameplay state is decided on the host. A client's own simulation runs the same step (`main-loop.md`) but (a) skips macro scripts, (b) does not create the replicated dynamic entities by itself and (c) after its world starts **deletes the dynamic entities that came from the level file** (`CClientInterface::DeleteDynamicEntities`) and waits for the server's create messages.
2. **Prediction exists for one thing: the player.** `CPlayerPuppetEntity` and `CPlayerBrainEntity` report `NEB_PREDICTED`. The brain carries the player's **input** as replicated members (`en_vNetOperatorLookDirEul`, `en_vNetOperatorRelMove`, `en_ubNetFireButtonStates`) and the server's answer (`en_vServerLastPosition`, `en_henServerLastFloor`, `en_henServerLastMover`, `en_vPredictedVelocityCorrection`, `en_ubResetPosition`, `en_ubResetLookDir`). Every other entity is shown as the last received state, corrected by the smoothing in 3.7. (**medium**: names and flags read; the exact exchange is T01-098.)
3. **Two channels of change.** (a) *Member state* through update messages (unreliable, a lost one is replaced by the next, **except** create, delete and initial update which are reliable); (b) *remote calls* (RPCs, 3.4), reliable or unreliable per function.
4. **No lockstep, no shared tick, no determinism requirement.** The only time on the wire is the sender's simulation time as a stamp (3.7).
5. **A message's fate on the client depends on the entity's existence.** An update, RPC or delete that names an entity the client does not know yet (or a string index not yet received) is **delayed** and retried for up to `net_fMessageDelayLimit` = **2.0 s**, then dropped (high: the limit is read in the delay loop).

### 3.3 The message set (19 types)

Numbers are the engine's `ENetworkMessageType`; names are the type-name strings; "reliable" is each class's `IsReliable`. Direction is from the dispatch of the server and client loops. In the demos these messages are stored as `u8 type` plus the fields below (little endian, `string` = `u16` length and bytes); the packet form differs slightly (no change in content).

| # | Name | Dir. | Reliable | Content (what a design needs) |
|---|---|---|---|---|
| 1 | `NMT_REQ_CONNECT` | C to S | yes | the client's version string, the connect password, two flag bits (private slot, observer) |
| 2 | `NMT_REQ_CHALLENGE` | S to C | yes | an authentication challenge (online sessions only) |
| 3 | `NMT_REP_CHALLENGE` | C to S | yes | the challenge response |
| 4 | `NMT_REP_CONNECT` | S to C | yes | the server's version string, a message (`Connection accepted`, a refusal text, or `DemoRec`), the **world path**, accepted flag (u8), **client index** (u8), the server's simulation time (8 bytes) |
| 5 | `NMT_DISCONNECT` | both | yes | a reason string (translated by the receiver) |
| 6 | `NMT_SESSIONPARAMS` | C to S, S to C | yes | a u32 bandwidth cap, three floats (the avatar position), two bytes of unknown meaning, then **pause requested** (u8) and **paused** (u8): 21 bytes in the demo form; the avatar entity handle is part of the parameters but not sent |
| 7 | `NMT_REMAPLIST` | S to C | yes | a list of (entity ID in the level file, server handle) pairs, 8 bytes each, several messages for a large level (9 messages with 402 pairs in `Demo_0001`) |
| 8 | `NMT_MODULEINDEX` | S to C | yes | module name and index: the **resource files that define entity classes** (one in all three demos) |
| 9 | `NMT_STRINGINDEX` | S to C and C to S | yes | a string and its index in the session's string table: identifiers, resource names, strings that updates refer to by index |
| 10 | `NMT_CREATE_ENTITY` | S to C | yes | server handle (u32), then a u32, a u8 and a u32 that together name the entity (its id in the level or template, the class's module index and the class id inside the module; the assignment of the three fields was not resolved), a `u16` body size and the entity's **initial state** as an update body of up to 255 bytes |
| 11 | `NMT_DELETE_ENTITY` | S to C | yes | server handle (4 bytes) |
| 12 | `NMT_UPDATE` | S to C | **no** | server handle, `u8` size, then the changed members (3.4); size 0 is allowed |
| 13 | `NMT_INITIAL_UPDATE` | S to C | yes | the same layout as 12, used when a **static** entity first becomes relevant to a client |
| 14 | `NMT_RELIABLE_RPC` | both | yes | a flag byte, entity handle, function id, `u16` argument size, the arguments |
| 15 | `NMT_UNRELIABLE_RPC` | both | no | the same layout |
| 16 | `NMT_KEEPALIVE` | both | no | nothing |
| 17 | `NMT_RELIABLE_KEEPALIVE` | both | yes | nothing |
| 18 | `NMT_PRE_WORLD_CHANGE` | S to C | yes | the next world's name |
| 19 | `NMT_POST_WORLD_CHANGE` | S to C | yes | a success flag (u8) |

Every packet starts with the server's **simulation time as a 32-bit stamp in units of 2^-10 s** (the `Time` value shifted right by 22); the receiver turns the stamp back into a `Time` and **adds the difference to its previous stamp** (so a wrap after 48.5 days is harmless, `main-loop.md`). Reliable messages are kept and resent by the packet layer; an unreliable **RPC whose function carries a "latest wins" flag replaces an older queued call of the same function on the same entity** in the send queue (medium).

Consequences: the **level's geometry, lights and AI scaffolding are never sent**; each machine loads them from its own data. **Spawner logic, macros and AI decisions exist only on the host.** The level's items, props and puppets are a case of "which side of the conditional": 186 initial updates against 32 creates in the first snapshot of `Demo_0001` fit "most are static" but the interpretation of `en_henSpawner` is not settled (T01-097).

**Replicated members.** A member takes part when its table entry has the flag `SMF_NETUPDATE` (**0x4000**; the same table gives `SMF_OWNED` 0x2000 and `SMF_TEMPORARY` 0x1000, whose roles are not read). An entity class's **network descriptor** is the list of all flagged members of the class and its parents (parents first), nested structures only through their own flagged members. A member's replicated **type** follows from its data type:

| Data type | Replicated as | Notes |
|---|---|---|
| `FLOAT` | **signed 32-bit integer = round(value x 256)**; decoded as integer / 256 | resolution 1/256 = 0.0039; compared **after** quantising, so changes smaller than half a step never send |
| BOOL; 1-, 2-, 4-byte integers; enumerations and pointer-sized values | as is | |
| `IDENT` (an interned name) | an index into the session's **string table** | the client first receives a `NMT_STRINGINDEX` for any index it lacks; an update that needs a missing string is delayed |
| resource pointers (models, sounds, textures, `.ep` files) | the **resource path** through the string table | the client loads the resource by name |
| `CString` | the string itself | |
| entity handles | a **handle value remapped** between server and client numbering | the client keeps a remap table (3.6) |
| one-dimensional arrays of the above | each element as a member `name[i]` | other arrays are refused with an error |

An update body is `(member index u8, value)` pairs for the members that **differ from the baseline**; at most 255 members per class and **255 bytes per update** (larger ones are refused with the error "Network update for an entity too large" and not sent).

**The baseline.** For each client and each relevant entity the server keeps a copy of the entity's replicated members. It is set **once**, when the entity becomes relevant to that client: for a **create** the copy starts as the class's default ("entity template") and the create message carries the difference from it, then the copy takes the entity's values; for an **initial update** (static entities) the copy takes the entity's values at that moment. **Nothing in the regular update path writes the baseline again** (read in the update function; **medium**). The demos agree: **35.7 %, 9.6 % and 5.5 % of the non-empty updates repeat the entity's previous non-empty payload byte for byte**, and one entity in `Demo_0002` sent the same payload 3,596 times of 3,657; this cannot happen if the baseline followed what was sent. So an update is "the members that differ from their value when the entity became relevant", which is why **no acknowledgement of updates is needed** (create, delete and initial update are the reliable ones). When an entity leaves and re-enters relevance it gets a fresh create or initial update and a fresh baseline.

### 3.5 Relevance, priority and the per-pass budget

All of this runs **per client connection** on the server in the send phase of each frame (`netStep` with sending allowed, `main-loop.md`). Terms marked (ours) are invented labels.

- **Relevance test** (high for the shape, medium for the numbers): an entity is relevant to a client when it is `NEB_PREDICTED`, or when this machine is a demo playback (everything is relevant), or when the **distance from the client's centre to the entity's position is at most `min(GetRelevantDistance of the entity, net_fMaxRelevantDistance)`**. `net_fMaxRelevantDistance` starts at **3.0 x 10^38** (set by a start-up routine), so by default only the class value limits. The **centre** is the position of the client's avatar entity when the game attached one (`netSetAvatar`, called when a player is attached) and otherwise the avatar position the client reported in its session parameters (3 floats), which the engine feeds from the listener position.
- **Class values of `GetRelevantDistance`**: **unlimited (3.0 x 10^38)** for weapons, diamond hand, chapter info, game info, mission objective, navigation beacon, voting info, world info, player brain, player puppet, door, portal, barrier field, bouncer, secret and animated mover; the **model's effective cull distance** for static models, props, items, puppets, projectiles, debris and effects (a puppet without a model: 0); the sound's own **fall-off distance** (`en_fFallOff`) for static sounds; **0** for the base class (not replicated anyway). `CPlayerPuppetEntity` and `CPlayerBrainEntity` are unlimited **and** predicted, so a player is always relevant to everyone.
- **Priority** (`GetUpdatePriority`, a number added to the entity's score every pass): default **2.0**; **10.0** player puppet and player brain; **8.0** an alive puppet (2.0 while `en_bAlive` is false); **6.0** a projectile (0 when its `en_hre` handle is empty); **5.0** doors, animated movers, the diamond hand; props, generic motors and external joints use a value computed from the **distance to the closest player** (formula not resolved, T01-096).
- **The record per relevant entity** ("update record", ours): the entity handle, its **baseline copy**, an **accumulated priority** and the per-pass priority (refreshed from `GetUpdatePriority` each time the entity is sent). Records for entities that are not relevant are kept in a separate ring ("irrelevant ring", ours).
- **A pass** (`PackUpdates`): (1) sort the records by accumulated priority, **highest first**; (2) walk them in that order: if the entity is no longer relevant, remove it (send a delete message for dynamic and predicted entities, nothing for static ones) and move it to the ring; otherwise build the difference against the baseline: a **static** entity with no difference sends nothing and keeps its accumulated priority; any other entity sends an update **even when the difference is empty** (a 6-byte message with size 0) and has its accumulated priority **reset to 0**; (3) stop when the pass's **byte budget** is exhausted, or when the **time budget** `net_ulMaxUpdateDuration` = **3 ms** is exceeded (the clock is read once per `net_ctUpdateTimeCheckStep` = **30** records); (4) add every record's per-pass priority to its accumulated priority. So an entity of priority 10 is, when the budget is the limit, sent about five times as often as one of priority 2. (**medium**: read in two functions; the sort comparator and the end-of-pass addition are explicit.)
- **The ring** is re-tested incrementally: each pass tests `count x step / net_fRelevantTestsInterval + 1.0` entries, converted to a whole number and never more than the ring holds (`step` = the last simulation step, interval default **2.0 s**). A large ring is therefore walked about **once per 2 s**, a small one faster (the `+ 1` dominates); an entity that has become relevant gets its create or initial update and moves to the update records (**medium**: the rounding mode was not determined).
- **Byte budget of a packet:** the packet builder asks for a payload of **500 to 1,000 bytes** (clamped; the upper value is `net_slUDPBlockSize` = 1,000) and pacing per connection: after a send of *n* bytes the next send is not before `(n + 31) / clamp(cap, 1,000, 1,000,000)` seconds, where the cap is the client's **`cli_iMaxBPS`** (default **100,000**, bytes per second: **medium**, the unit follows from the formula). The client limits its own upstream to `cli_iMaxOutBPS` = **7,500**. `cli_iLowQualityBPS` 12,000, `cli_iHighQualityBPS` 100,000 and `cli_iBPSQualityTreshold` 110,000 exist; their use was not read.

### 3.6 The join sequence

**Handshake** (server side, `HandleConnectRequest`, in this order; each failure is a `DISCONNECT` with the text in the right column, **high**):

| Check | Failure text key |
|---|---|
| the client's IP is on the ban list (`ser_strBanList`; permanent or time-limited) | `ETRSServer.PermanentBan` / `TemporaryBan` |
| the client's **version string equals the server's** (the build string, with ` - editor` appended in the editor) | `ETRSServer.VersionMismatch` |
| if `net_strConnectPassword` is set: the request carries the same password | `PasswordRequired` (none given) / `InvalidPassword` (wrong; the shipped text misspells it) |
| a free slot exists: a public one, or a private one when the request asks for it | `NoFreeSlots` |
| online sessions only: the challenge response authenticates (`AuthFailed`) | |

There is **no content or mod check** at this point (only the build string): the entity class list reaches the client **after** acceptance (module list below). A client that does not answer for `net_fConnectionTimeout` = **15 s** while connecting is dropped.

**After acceptance** (`ConnectClient`; the same order is used again for every connected client after each world change, `PostWorldChange`, and by the demo recorder, `StartDemoRecording`):

1. `NMT_REP_CONNECT`: accepted, `Connection accepted`, the world path (or the world being loaded), the client index, the server's simulation time. The client stores the server time as the base of its stamp accumulation and **starts loading the world itself** (`ChangeWorld`); its state is "loading" until the world has started, during which received messages stay queued unprocessed (only the time of the last message is refreshed, so the silence timer does not fire).
2. `NMT_REMAPLIST` messages: for every **level entity with a net behaviour other than none**, the pair (ID in the level file, server handle). The client binds its own loaded entity to the handle and makes a baseline copy for it.
3. `NMT_MODULEINDEX` messages: the resource files that define entity classes (1 in the demos).
4. The server **walks every entity of the world** and offers it to this client: relevant ones get a baseline copy and **`NMT_CREATE_ENTITY`** (dynamic and predicted: with the entity's initial state and the string-table messages it needs just before it) or **`NMT_INITIAL_UPDATE`** (static); non-relevant ones go to the ring. From here the normal pass of 3.5 continues, so the rest arrives over the following frames within the budgets. `Demo_0001`'s recorder slot has no packet limit and carries the whole snapshot in one block (47,943 bytes: 186 initial updates, 32 creates, 6,670 updates, 9 remap messages with 402 pairs, 19 string messages); `Demo_0002` and `Demo_0003` spread the same kinds over their first 5 and 10 blocks (3.10).
5. `NMT_SESSIONPARAMS` from the server carries the current pause state; the client answers with its own parameters whenever they change (bandwidth, avatar position, **pause requested**).
6. **Game level** (`CGameInfoEntity`): the new client sends the RPC `CreatePlayer(client index, name)`; the server spawns a player puppet and brain, then the broadcast `AttachPlayer(index, brain, puppet)` ties them together: sets the player's index and a default name `Player<index>`, boots the player (deathmatch or co-op boot), and each machine calls `netSetAvatar` for the puppet it owns (the server for remote players; the client for its own). The server announces `<name> has joined the game.` through `DisplayChatMessage`; `PlayerRemove` (a broadcast) deletes the puppet on leaving with `<name> has left the game.` (**medium**).

**Late joiners are not a special case**: the same steps run against the state of the moment (an entity's baseline is whatever the entity is now). There is no save-style blob; there is **no ordering guarantee** other than reliability of the create and initial messages, and an update for an entity that has not yet been created is delayed up to 2 s (3.2). **World change on a running server:** `NMT_PRE_WORLD_CHANGE` (name), the clients load, `NMT_POST_WORLD_CHANGE`, then steps 2 to 4 again; the server's class-default templates are discarded and rebuilt (`DeleteEntityTemplates`) and every client gets fresh baselines.

### 3.7 Timing

- **Update cadence:** one send pass per frame of the host (the dedicated server paces its loop at `sam_iDedicatedFPS` = 60, `main-loop.md`); how often an entity is included follows 3.5 and the per-connection pacing. **There is no send-rate variable** in the set: the bandwidth caps and budgets play that role.
- **Time on the wire:** the stamp of every packet is the host's `Now` in 2^-10 s. The client's `GetServerTime` is the accumulated value; **no code in the game DLL reads it** and **the client's own simulation time is not set from it** (the only `SetNow` calls are for loaded saves and demos): a client's clock free-runs. The demo player does set its clock from the recorded start time. (**medium**; T01-085 should confirm with two machines.)
- **Interpolation and extrapolation:** none by timestamp (`main-loop.md` section 10). A received update **overwrites the member values**; what remains is **error smoothing** of the predicted player and of placed models, with the network block of the global parameters (`ggp_snpNetworkParams`, `game-modes.md`): position error **below 0.05 is ignored**, **at or above 5** teleports, in between it is **melted** at factor 5 (a decaying correction applied each step); prediction tolerance for teleporting **0.2** horizontally and **3 times** that vertically (used when judging a vehicle-relative position claim, 3.8); animation-offset error ignored below **0.05**, teleported at **0.5**, melting factor **5**. The correction functions are `ApplyClientPositionCorrection` (puppets, rolling balls) and `ApplyClientOffsetCorrection` (doors, movers, static models) and `AdjustClientOrientation`; the formula is T01-098.
- **Lag compensation:** none was found (no rewind of hit-tests by a client's latency in the exported names; hit-scan is decided on the server from the replicated input). Open for confirmation (T01-098).
- **Timeouts** (all in seconds of real time; **high** where marked, the use read in code):

| Variable | Default | Meaning |
|---|---|---|
| `net_fConnectionTimeout` | 15 | high: the client in the connecting states gives up after this much silence |
| `net_fProblemsTimeout` | 15 | high: silence on an established connection (server per client, client from the server) means "Connection timeout" |
| `net_fDisconnectPeriod` | 2 | high: after a `DISCONNECT` the slot is held for this long, then terminated |
| `net_fMessageDelayLimit` | 2 | high: a delayed message is dropped after this age |
| `net_fRelevantTestsInterval` | 2 | high: every non-relevant entity is re-tested about this often |
| `net_ulMaxUpdateDuration` | 3 | high: milliseconds of the per-pass time budget |
| `net_ctUpdateTimeCheckStep` | 30 | high: records per clock check |
| `net_fUpdateTimeLimit` | 2 | medium: read only in the debug display |

### 3.8 Anti-cheat and trust

- **Connect-time:** the checks of 3.6; the ban list and the **kick, ban, time-ban and unban** commands (`serKickClient`, `serBanClient`, `serTimeBanClient`, `serUnBanClient`, `samKick...`); a kicked or terminated client is removed from every slot and the world info entity gets the script call `TerminateClient`.
- **Input:** a client sends **intent** (`ClientAction`: buttons, move and look vectors), not its position; the server simulates the puppet. The one place the server judges a client-sent **position** is **vehicle and mover riding**: the offset the client reports relative to the mover is compared with `speed x 0.2` horizontally and `speed x 3` vertically (the two tolerances of the network block); a larger claim is **refused and a sequence byte is incremented so the client is told to reset its position** (`en_ubResetPosition`). No other validation of the player's movement was found (**medium**; no rate limit on input was found: T01-098).
- **Cheats** are RPC requests (15 of the 36 above) executed by the server; whether the server checks that cheats are enabled for that client was not read (T01-101); the player puppet carries `en_ulCheatFlags`.
- **Votes** (`CVotingInfoEntity`, one per game, dynamic): types **1 next map, 2 restart map, 3 kick, 4 time-ban**; a type is allowed by a settings string that lists `all`, `nextmap`, `restart`, `kick`, `timeban`; kick and time-ban need a client index 0 to 16; one vote runs at a time (`IsVoteInProgress`); **a vote passes when `yes / players > 0.5` and fails when `no / players > 0.5`** (strict, so an exact half decides nothing); the vote window is **60 s**; on a pass the server runs `samNextMap`, `samRestartMap`, `samKickClient` or `samTimeBanClient(index, 60)` (the 60's unit was not read) followed by a kick. Clients vote with `VoteYes` and `VoteNo` RPCs; a client index is a number the caller supplies (whether the server checks it matches the sender: T01-101).
- **Pause by clients:** the server applies a client's `NMT_SESSIONPARAMS` pause request **only if `net_bClientsMayPause`** (default **0**); a client's `simUnPause` works only if the client-unpause permission is set (`main-loop.md`). The lobby option `opslClientsMayPause` sets it.
- **Passwords:** `net_strConnectPassword`, `net_strObserverPassword`, `net_strVIPPassword`, `net_strAdminPassword` exist; only the connect password was found in the connect check (the others: observer and VIP slots and the remote console, T01-101).
- **Rate limits:** none found on messages; the update size limit (255 bytes) and the 2 s delay limit bound what a client can queue. Anything beyond is unknown.

## Invariants

1. Message types are numbered 1 to 19 and every message in the three demos has one of them; each demo is consumed **exactly** by the layouts of 3.3 (3 of 3 files, 484,370 messages in all, `replication_verify.py`).
2. `SMF_NETUPDATE` is 0x4000 (enumeration table and descriptor builder agree); no other bit is tested when collecting members.
3. A class's replicated members number at most 255 and an update body at most 255 bytes (the body size is one byte in the demos: the largest non-empty body is 66 bytes in the 3 demos).
4. Only update (12), keep-alive (16) and unreliable RPC (15) are unreliable; every other message is reliable.
5. A static entity with an empty difference sends no message; any other relevant entity sends an update every time it is scheduled, empty or not (the demos: 54.5 to 74.8 % of updates are empty).
6. No `net_`, `ser_` or `cli_` variable is set by a shipped configuration script (0 lines in 6 files).
7. Macros do not run on a remote client; the client's clock is not set from the server's.
8. The client index of the host's own player is 16; remote clients use 0 to 15.

## Test vectors

1. **Float quantisation** (3.4): 1.0 sends the integer 256; 3.14159 sends 804 and decodes to 3.140625; 100.5 sends 25,728 and decodes exactly; 0.002 sends 1 and decodes to 0.00390625; -0.001 sends 0 (equal to a baseline of 0: **no change is sent**).
2. **A connect response in a demo** (`Demo_0001.dem`, the first message after `MSGS`): `04` (type 4), `3e 00` (62) and the 62 characters `$Version: Serious Sam 2; 2.068.00:61409; 2006-PATCH-2-068-inc$`, `07 00` + `DemoRec`, `48 00` (72) + the level path `Content/SeriousSam2/Levels/02_Magnor/2_3_Branchester/2_3_Branchester.wld`, then `01` (accepted), `10` (client index 16) and the 8-byte time `dc 01 e3 6d 06 00 00 00` = 27,613,397,468 ticks = 6.429245 s.
3. **The packet stamp of that time:** 27,613,397,468 >> 22 = 6,583 (units of 1/1024 s = 6.4287 s; the sub-stamp part is lost).
4. **An empty update** in the stream: `0c` (type 12), a 4-byte handle, `00` (size 0): 6 bytes. A create message is `0a` + handle (4) + three id fields (4, 1 and 4 bytes) + size (2) + body.
5. **Relevance** (3.5): avatar at (0, 0, 0); a puppet with cull distance 5 at (3, 4, 0) is relevant (distance 5 is not greater than 5); at (3, 4, 1) it is not; a player puppet is relevant at any distance (predicted); with `net_fMaxRelevantDistance` set to 2 even the first is not.
6. **Priority** (3.5): two dynamic entities A (per-pass priority 10) and B (5), a budget of one message per pass, ties resolved in favour of A, accumulated values start at 0. Pass 1: A is sent and reset to 0; at the end of the pass A = 10, B = 5. Pass 2: A (10) before B (5): A is sent; end: A = 10, B = 10. Pass 3: a tie: A first by the stated rule, so A is sent; end: A = 10, B = 15. Pass 4: B (15) first: B is sent; end: A = 20, B = 5. Pass 5: A is sent; end A = 10, B = 10, the state after pass 2, so from pass 3 the cycle repeats every 3 passes: **A is sent twice, B once**. Without a budget limit both would be sent in every pass. (The original sorts with an unstable quick sort; the order of equal values is not specified.)
7. **Vote** (3.8): 4 players, 3 yes: 0.75 is greater than 0.5, passes; 2 yes and 2 no: neither 0.5 is greater than 0.5, the vote runs until its 60 s end; 3 no: fails.
8. **Timeouts** (3.7): a client silent for 15.0 s receives `DISCONNECT` with `ETRSServer.ConnectionTimeout`, its slot is terminated 2.0 s later; a message delayed since 2.0 s (strictly more than the limit) is dropped.
9. **Ring re-test count** (3.5): 120 entries in the ring, a step of 0.0167 s, interval 2.0 s: the pass tests `120 x 0.0167 / 2.0 + 1.0` = 2.002, converted to a whole number (2 whether truncated or rounded), never more than the number of entries: 2 entries per pass, so the whole ring is covered in about 60 passes, about 1 s at 60 passes per second; the formula's `+ 1.0` makes a small ring finish faster than 2 s (medium: the rounding mode was not determined).
10. **Baseline, as the model of 3.4 predicts** (not observed on a running game): a puppet becomes relevant with health 100 (member `en_slHealth`): the create body carries the difference of its members from the class default and the baseline takes the entity's values, so `en_slHealth` = 100 is in the baseline. The puppet is hurt to 40: every update sent for it from then on carries `en_slHealth = 40` (the difference from the baseline 100) until it is deleted or leaves relevance, **even when 40 has not changed for minutes**. If health returns to exactly 100 the difference is empty and the update has size 0, and the client would keep showing 40: the model predicts a stale value there. Whether the original has such a case, or something that prevents it, is open question 5.
