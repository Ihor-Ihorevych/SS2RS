# Spec conventions (T01-001)

- **Roadmap task:** T01-001
- **Applies to:** every file in `docs/re/` and every script in `tools/re/`
- **Read first:** [`CLEANROOM.md`](https://github.com/Ihor-Ihorevych/SS2RS/blob/main/CLEANROOM.md). This page is the day-to-day working rules; the policy is there.

A spec is the contract between whoever read the original game and whoever writes our code. It is
useful only if the next person can (a) trust it, (b) re-check it, and (c) find it. These rules keep
all three true.

## 1. Which file, what name

| Kind of spec | File | Example |
|---|---|---|
| One file format | `<ext>.md`, extension without the dot | `tex.md`, `skl.md` |
| A format split into parts | `<ext>-<part>.md` | `wld-root.md`, `wld-geometry.md` |
| A format shared by many (container, types) | `<family>-<part>.md` | `ctsemeta-container.md` |
| Game behavior (rules, numbers) | `<topic>.md`, kebab-case, singular | `player-movement.md`, `weapon-autoshotgun.md` |
| One spec per weapon / enemy / boss | `weapon-<name>.md`, `enemy-<name>.md`, `boss-<name>.md` | `enemy-kleer.md` |
| Generated reference (never hand-edited) | `<topic>-schema.md`, header says which script wrote it | `ep-schema.md` |

Rules:

- lowercase ASCII, `-` between words, no spaces, no dates, no version numbers in names;
- one topic per file; if a file passes about 600 lines or two authors need to work at once, split it
  into parts and link them from a short overview;
- add the file to `docs/SUMMARY.md` in the same PR (the docs check fails on an orphan page);
- evidence scripts live in `tools/re/<topic>_verify.py` and are listed in `tools/re/README.md`;
- a roadmap task ID appears in the spec's first lines, and the roadmap line links back by name.

## 2. The spec template

Copy this to start a new spec. Every heading is required; write "none" rather than deleting one.

```markdown
# <Topic>

- **Roadmap task:** T01-nnn
- **Author:** @handle · **Reviewer:** _none yet (T01-049)_
- **Confidence:** **high** for …; **medium** for …; **low / open** for …

Prerequisites: <other specs a reader must know first>.

## Summary
What it is, where the game uses it, how many instances exist in the retail install.

## Evidence
What was measured and how many files or runs it covers. Name the script in `tools/re/` that
reproduces the counts. State what was *not* checked.

## Layout / rules
Byte or field layout (offset, size, type, meaning), or the behavior as numbers with units.

## Invariants
What is always true; what a reader must reject. Each one says how many cases it was checked on.

## Open questions
What is unknown, ranked by what blocks an implementer. Each item names the task that will answer it.

## Test vectors
Small hand-made or measured examples: input bytes (or input sequence) and the exact expected values.
```

Style:

- **Write for the implementer who cannot ask you.** Units, signedness, endianness, ranges, and what
  "unused" or "unknown" means must be stated, not implied.
- **Separate fact from guess.** Every field or rule carries a confidence word (`high`, `medium`,
  `low`) when it is not obvious. Names that we invented are said to be invented
  (see the naming dictionary below). Never present a guess in the voice of a fact.
- **Numbers over adjectives.** "Fast" is not a spec; `12.5 m/s` with the method of measurement is.
- **Counts say what they counted**: "all 9,269 format-8 files", not "all files".
- Use the project's own words for things (section tags, class names as they appear in the data); do
  not rename them for taste.

## 3. Confidence and review

| Word | Means | Needed before an implementer may rely on it |
|---|---|---|
| **high** | Checked against every instance in the install, or derived from a rule that is checked, with a script that reproduces the result | one independent read (T01-049) |
| **medium** | Consistent with all observed cases but the cases do not exercise every branch, or the meaning is inferred | the reader accepts the risk, or a second reviewer signs it |
| **low** | A hypothesis. Fine to publish, never fine to build on silently | a second reviewer **and** a follow-up task |

The reviewer is a different person from the author and checks the list below. Record the outcome in
the **Reviewer** line of the spec (name and date) and in the PR.

### Review checklist

1. **Clean room.** No decompiler output, disassembly, assembler mnemonics, function bodies, raw
   addresses or Ghidra identifiers; no pasted game content beyond a handful of bytes that illustrate a
   header. No SS1 (GPL) code or text.
2. **Reproducible.** Every count in the Evidence section can be regenerated by a script in
   `tools/re/`, or by a documented procedure for a behavior measurement. The reviewer ran at least one.
3. **Implementable.** Someone who has never seen the original could write a reader or the rule from
   the page alone: all sizes, orders, signs, units, defaults, and error cases are stated.
4. **Complete for its scope.** The scope in the roadmap line is covered, or the gap appears under
   Open questions with a task ID.
5. **Test vectors.** Present, small, and the reviewer decoded at least one by hand and got the stated
   values.
6. **Consistent.** Names, section tags and numbers agree with the other specs it depends on; any
   conflict is fixed in one place and the others linked.
7. **Honest confidence.** The confidence words match what the Evidence supports.
8. **Mechanics.** Linked from `docs/SUMMARY.md`, task ID present, `cargo xtask guard` passes, no
   broken links.

## 4. Evidence rules for scripts (`tools/re/`)

- Python 3 standard library only; run with `python -I`.
- **Read-only** on the install; never writes game content anywhere, and any cache of results contains
  numbers and paths only.
- They take the install directory as an argument and print a short summary a reviewer can compare
  with the spec text. They never print game data beyond a few bytes.
- Scripts that analyze the original **binaries** do not belong in the repository (`CLEANROOM.md`).

## 5. Binaries and Ghidra: what may be written down

Reading the original binaries (the engine and game DLLs, the executables) is allowed for spec
authors **only** when the result is prose about behavior. Everything below is about keeping that line
clear.

### 5.1 Where the work lives

- Ghidra projects, databases, exports and listings stay **on the author's machine**, outside the
  repository tree. The guard blocks the usual extensions; do not rely on it alone.
- Use one project per binary, named `ss2-<binary>-<build>` (for example `ss2-engine-2.068`), and note
  the exact build in the spec's Evidence section, because behavior differs across patch levels.

### 5.2 Naming dictionary for recovered symbols

Names you give in Ghidra are working notes, not product. Keep them consistent so two authors'
notes can be compared:

| Thing | Convention | Example |
|---|---|---|
| Class known from the data's own type names | exactly that name | `CStaticModelEntity` |
| Class known only from RTTI strings | the RTTI name, with a `rtti:` comment | `CWorld` |
| Struct without a name | `S_<Topic>_<Role>` | `S_Tex_Header` |
| Member of a known class | the data's member name or `Class.<index>` as the specs use it | `CHull.8` |
| Function with a known role | `<Class>_<Verb><Object>` | `CWorld_AddEntity` |
| Function guessed from behavior | prefix `guess_` | `guess_ApplyFriction` |
| Constant | `K_<Topic>_<Meaning>` | `K_Move_StepHeight` |
| Unknown | `unk_<Topic>_<Seq>`; never leave a default `FUN_`/`DAT_` name in a note you quote from | `unk_Move_03` |

A name we *invented* is marked `(ours)` the first time it appears in a spec. A name that the data or
the binary's own strings provide is quoted as-is.

### 5.3 Exporting notes without code

What leaves Ghidra and enters a spec is a **fact in plain words** plus the **numbers it implies**:

- ✅ "The player's horizontal speed is clamped to 8.0 units/s; the clamp is applied after friction."
- ✅ "A pickup respawns after 30 s on difficulty Normal, 60 s on Hard (three levels checked)."
- ✅ A table of constants with units, plus how you confirmed each by a black-box measurement.
- ❌ A pasted function, pseudocode that follows a function line by line, or a control-flow listing.
- ❌ Assembler mnemonics, instruction sequences, byte patterns of code, virtual addresses, offsets
  into a binary, or Ghidra auto-names.
- ❌ Screenshots of the decompiler or listing views.

If a rule is easiest to explain as a sequence of steps, write the steps as the behavior ("first X,
then Y, unless Z"), in your own words and from the *observable* order of effects, and **confirm it by
measurement** (instrumentation or the data) so the spec does not depend on having read code. A rule
that only exists because of what you saw in a listing and cannot be observed is `low` confidence
and says so.

### 5.4 One person, one side

A spec author does not write the product code for what they specified (`CLEANROOM.md`). Record in the
PR which topics you specified so the implementer assignment can avoid the overlap.

## 6. Where measurements and observations go

- **Format facts** → the spec of the format, with the evidence script.
- **Behavior numbers** → the behavior spec, with a table: value, unit, how measured, build, number
  of samples. Raw capture data (CSV from T01-038/039) stays local; the spec keeps the numbers.
- **Questions you cannot settle** → an issue labelled `spec`, linked from the spec's Open questions.
- **Spec bugs found by implementers** → an issue labelled `spec`; the implementer does not go and
  read the binary.
