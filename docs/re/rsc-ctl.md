# `.rsc` resource databases and `.ctl` character tools

- **Roadmap task:** T01-015
- **Author:** @Ihor-Ihorevych/agent · **Reviewer:** _none yet (T01-049)_
- **Confidence:** **high** for the structure of both formats, the root classes, the references and the class lists (checked on all 112 `.rsc` and 68 `.ctl` files, and generated from their own type tables); **medium** for the role of individual members that have readable names; **low** for the graph evaluation and for everything that is gameplay or GUI behaviour. Scope: **112** `.rsc` and **68** `.ctl` files, all format 8. The full member reference is `rsc-ctl-schema.md` (generated by `tools/re/ep_schema.py`: 145 classes, 785 members).

Prerequisites: `ctsemeta-container.md`, `ctsemeta-types.md`, `ctsemeta-objects.md`; `ep.md` (the same generator and conventions), `skl.md`, `fnt.md`.

## Summary

Neither extension names one format. **`.rsc`** ("resource database") is a **generic container**: the root object's class says what the file is. The 112 files are 99 **menu screen layouts**, 3 **skeletons** and 10 **global databases** (cameras, global game parameters, HUD parameters, menu fonts, crosshairs, power-up effects, spawner parameters). **`.ctl`** is a single kind: a **character tool**: a held, picked-up or thrown object (a weapon, a thrown prop, a piece of debris) described by animations, an attachment point and launch velocities. Both formats are data only, like `.ep`.

## Evidence

`tools/re/ep_schema.py --check --ext .rsc,.ctl` (read-only, `SS2_DATA_DIR`) over the retail install with all patches:

- **All 112 `.rsc` and all 68 `.ctl` files decode**, each with **exactly one shared root** and no extra records after `EDOB`.
- **All external references resolve** to a file of the install: `.rsc` 270 (`.tex` 236, `.fnt` 8, `.tfx` 8, `.wav` 5, `.rsc` 4, `.pfx` 4, `.mtr` 3, `.ctl` 1, `.ogg` 1) and `.ctl` 68 (`.mdl` 62, game module 4, `.ep` 2).

### Menu screens (`CMenuScreenLayout`, 99 files)

```
CMenuScreenLayout
  .1   int
  .2   list of gadget layouts (polymorphic; the screens have 2 to 79 objects per file, median 9, in all)
  .3   string: name of the underlay (C++ class of the game's menu code): CMSUnderlay (75), CMSPopupMenuUnderlay (11), CMSPopupMenuUnderlayLarge (7), CMSMainMenuUnderlay (1), empty (4)
  .4   string: name of the overlay: CMSOverlay (73), empty (26)
```

The gadget classes in the files (counts over all screens): `CMenuGadgetOptionSelectBoxLayout` 193, `CMenuGadgetLabelLayout` 187, `CMenuGadgetImageLayout` 106, `CMenuGadgetButtonLayout` 97, `CMenuGadgetButtonBarLayout` 78, `CMenuGadgetLinkLayout` 54, `CListColumnInfo` 36, `CMGImageButtonLayout` 27, `CMGArrangerLayout` 26, `CMenuGadgetSliderBoxLayout` 15, `CMenuGadgetVerticalSliderLayout` 13, `CMenuGadgetIntegerSelectBoxLayout` 11, `CMenuGadgetScrollListLayout` 8, `CMenuGadgetProgressBarLayout` 5 and ten more kinds with 4 or fewer. Names are strings from the file's `IDNT` table: the screen's class (`SCreateMatchMenuScreen`), the gadgets (`lblCaption`, `bbrButtonBar`, `imgSam2Logo`, `arrArranger`, `ibtnArrowUp`, …) and the font names (`SeriousZurich`, `SeriousVerdana`, `SeriousVerdanaLarge`, …). A screen is therefore "the layout for the game's menu class named by the identifier, with these named gadgets"; how a gadget is placed and styled is in the gadget members (see the schema reference); how screens link (menu flow) is the GUI spec (T01-036).

### The databases

- **`CMenuLayoutDatabase`**: a list of 10 `CFontInstance` (each: a `.fnt` from `fnt.md`, a colour `0xFFFFFFFF`, flags, a scale (0.11 to 1.0), and further numbers), a parameters structure (150, 128, 97), menu music (`Menu.ogg`), and a short list of ints (1, 5, 10, …).
- **`CCameraDatabase`**: 18 `CCameraHolder`, each pointing at a `CCameraControl`: `cc_idName` (the camera name, an `IDNT` string such as `3rdPersonCamera`, `3rdPersonRideCamera`, `HoverFighterCamera`, `HoverBikeCamera`), two **graphs** (`cc_pgrBehindDistanceOverPitch`, `cc_pgrAboveDistanceOverPitch`: how far behind and above the target the camera sits for a given pitch angle) and `cc_fMinPitch`/`cc_fMaxPitch` (−90 to 70 degrees). Puppets name their cameras by string: 10 of the 11 camera identifiers in the `.ep` files are camera names of this database (`3rdPersonDeathCamera` is the exception).
- **`CGlobalGameParams`**: spawning, tweak and boot-tweak parameter files (`.rsc`), default delay (0.5), standard see distance (100), short-sighted distance (40), character field of view (360), puppet sound ranges (`CPuppetSoundRanges`: fall-off 150, hot spot 10, moving fall-off 125 and a second set 50/10/50), a corpse sink configuration (`CCorpseSinkConfig`: steady 1.0 s, sink delay 0.1, sink period 0.45, a disappear effect and sound) and further graphs.
- The HUD, crosshair, power-up and spawner databases follow the same style (references to textures, fonts, effects and graphs); their members are in the schema reference.

### Graphs

The databases, like the `.ep` files and the shader modifiers of `mtr.md`, use the same **graph classes**: `CLinearGraph`, `CValueGraph`, `CStepUpGraph`, `CStepDownGraph`, all deriving from `CGraph` (base members `.7` to `.12`: floats and ints; `.12` equals the constant value of a `CValueGraph`). The key data is a list of **control points** (`CControlPoint`: `.3` a `Vector2f` (x, y) and `.4` an int that is often garbage such as `0xCCCCCCCC`, i.e. uninitialised memory in the editor: ignore it). Example: a camera's `BehindDistanceOverPitch` is a `CLinearGraph` with points (−90°, 0.0), (−45°, 0.05), (−30°, 0.4), …: the x axis is the pitch in degrees, the y axis the distance. A `CValueGraph` has one point (0, value). The evaluation (interpolation between points, the roles of `CGraph.7` to `.11`) is not specified here.

## `.ctl`: character tools

The root is a `CCharacterTool` (68 files, `Content/SeriousSam2/Databases/Tools/`). Members (readable names, prefix `ct_`):

| Member | Meaning (observed) |
|---|---|
| `ct_idDrawAnimationTerm`, `ct_idStoreAnimationTerm`, `ct_idPickAnimationTerm`, `ct_idThrowAnimationTerm` | `IDENT` strings: names of the animations played to draw, store, pick up and throw the tool (`Draw`, `Store`, `Pick`, `Throw`, `Body_ShotgunActivate_R`, `Body_Tool_ThrowChest`, …; empty = none) |
| `ct_bLerpDrawAnimation`, `…Store…`, `…Pick…`, `…Throw…` | `BOOL`: blend into the animation (1 in all store and pick) |
| `ct_pmcModel` | `Ptr<CModelConfiguration>`: the tool's model, an external `.mdl` (62 files; null in 6) |
| `ct_slHealth` | −1 or 40 |
| `ct_idLimb`, `ct_idAttachment`, `ct_idTargetBone` | `IDENT`: which limb (`RightHand`, `LeftHand`), which attachment (27 distinct names: `Hands`, `RightHand`, …) and which bone (`L_Hand`, `R_Hand`) the tool attaches to |
| `ct_qvTargetOffset` | `QuatVect`: placement relative to the target |
| `ct_fStretch`, `ct_bStretchWithOwner` | scale (0.3 to 20) and whether it follows the owner's scale |
| `ct_bThrownWhenOwnerDies`, `ct_bStraightenUpWhenThrowing` | `BOOL` |
| `ct_lvLaunchVelocities` | `CLaunchVelocities`: `lv_bRelativeToAttachment`, `lv_fMinVelocity`, `lv_fMaxVelocity` (5 to 20 in the sample) |
| `ct_ptecToolEntityCreator` | `CToolEntityCreator*`: what entity the tool becomes when thrown or dropped (17 files; null in 51) |

The **entity creators** (17 files): `CBaseItemToolEntityCreator` (8: it carries a complete **property record of an item entity**, for example `SHealthItemXLProperties`, `SShellsItemProperties`, `SDoubleShotgunItemProperties`: the same classes the world files use for item entities, see `wld-root.md`), `CDebrisToolEntityCreator` (7: life time 5 s, explode on timer, a trail effect) and `CGenericProjectileToolEntityCreator` (2: a projectile parameter file). `.ctl` files are used by weapons (`SBaseWeaponParams.35` and `.36`, 35 files each) and by mounted tools of puppets (`CMountedTool.mt_pctTool`, 8) in `ep.md`.

## Reader invariants

1. Read the root class first; it decides what the file is (for `.rsc`: one of the 12 roots above; for `.ctl`: `CCharacterTool`).
2. Identifiers (`IDENT` members, camera names, gadget names) are indices into the **file's own** `IDNT` table: compare strings, never numbers.
3. Polymorphic members (`gadget layouts`, `CToolEntityCreator*`, graph pointers) hold objects of derived classes: dispatch on the object's class; unknown classes must fail loudly.
4. Ignore the `.4` member of a control point.
5. All external references resolve in the retail data; treat a missing one as an error of that entry.
