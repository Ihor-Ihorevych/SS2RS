What a reader needs to know first:

1. **Names.** Every entity class `C<Name>ItemEntity` has a properties class `C<Name>ItemProperties` (the record a level stores) and no parameter class of its own: **one** shared class, `CBaseItemParams`, holds **one number** (`bip_fRespawnTime`, the multiplayer respawn delay in seconds), in 51 `.ep` files, one per pickup kind. The data stores `S...` twins for 76 of the 97 classes and the exported `C` name for 21.
2. **The amounts are in the code and in the world records, not in the `.ep` files.** `player-rules.md` guessed that the amounts "are not in the data": they are. The constructor of each size class sets the amount (health 5, 10, 25, 50, 100; armor 5, 10, 25, 50, 100, 200; treasure 100, 1,000, 5,000) and **every one of the 2,730 placed items carries the same value as its class constructor** (script). The ammunition amounts are constants of the classes (rockets 8, shells 20, ...). The `CBaseItemParams` number is **not** an amount: it is the respawn delay (a reading of the one place that uses it, medium). This also answers the open question 2 of `player-rules.md` (`CBaseItemParams.1` is `bip_fRespawnTime`: **high** for the name, medium for the use).
3. **One pickup protocol for all classes** (section 5): the host tests the touch, asks the class whether the player *needs* the item (`IsNeeded`), then broadcasts the `OnItemPicked` call; every machine runs the class's `OnPicked`, which hands the contents to the player and then hides the item (single player and co-op), hides it and respawns it after `bip_fRespawnTime` seconds (deathmatch), or deletes it (items created at run time). The classes differ in four virtual functions only: `IsNeeded`, `OnPicked`, `GetPickupAmount`/`GetPickupScore`, `OnlyFirstPlayerPicks`.
4. **Hiding is per player in co-op.** A pickup that is not "only the first player picks" is not removed when taken: its visibility mask (`en_ulVisible`, one bit per player, replicated) loses the picker's bit, so every player can take it once. The per-class options `sgp_bWeaponStaysInCoop`, `sgp_bAmmoStaysInCoop` and `sgp_bHealthAndArmorStayInCoop` choose between the two (section 5).
5. **Items made at run time.** The player drops weapons (those with an ammunition kind) and active power-ups when it dies; such items are `CWeaponItemEntity`/`CPowerUpItemEntity` children made by two factory functions, are marked dynamically created and delete themselves after `ggp_fWeaponItemStayTimeAfterDrop` / `ggp_fPowerUpItemStayTimeAfterDrop` (10 s each in the data). A dropped power-up remembers how much of its duration the player had used up (`en_fWastedTime`), so the next picker gets only the rest. This is a correction of the wording in `players-session-classes.md` (section 7.3): the inventory stores, per power-up, the **start** time, not an end time (section 5 of the vitals page).
6. **Binary-only classes.** 16 of the 113 are in no file: `CBladesItemEntity`, `CCircularSawItemEntity` and `CSerious_BombItemEntity` (and their properties) are **obsolete** (their `OnCreate` only logs that the class "is obsolete and should be removed from level ASAP"), and the entity and properties of `CColtItemEntity`, `CFlamerItemEntity`, `CZapGunItemEntity`, `CNapalmItemEntity` and `CStrengthItemEntity` are live classes that **no world places** (the run-time factories can still create the flamer and strength items; the others are reachable only from an editor, section 7).

### 3. `CBaseItemEntity`

**Role.** The pickup: a model with an optional glowing effect that waits for a player's body to touch it, gives the player something and then goes away (for good, or until the respawn). **Net:** `GetNetBehavior` is **`NEB_DYNAMIC` (2) when the item has no spawner and is not a multi-spawner template, otherwise `NEB_STATIC` (1)** (`replication.md` agrees: two readings, **high**); `GetRelevantDistance` is the model's effective cull distance, a very large constant (about 3.0e38) when the item is carried as a tool or has no model; **7 of the 19 members are replicated** (`replication.md`). The base class has **no per-step function**: nothing runs between pickups except the animation of the model.

### 5. The pickup protocol

All rules **medium** unless said; they apply to every class below `CBaseItemEntity` except where a class overrides the named function.

| # | Rule |
|---|---|
| 1 | **Touch (host only).** `OnHullTouched` returns at once on a client. On the host: the touching hull must belong to a **player puppet that is alive** (`IsAlive`), the puppet's brain must be a player brain, and the item must be visible to that player (`IsVisibleForPlayer(player index)`). Then `IsNeeded(puppet)` decides: **needed** → `OnItemPicked(puppet, OnlyFirstPlayerPicks())` and the touch returns 1; **not needed** → the touch returns 0, and the code then raises the level-script events `Picked` on the item and `OnePicked` on its spawner (the meaning of raising them for an unneeded item is not resolved: **low**, Open question 1) |
| 2 | **Broadcast.** `OnItemPicked` is a **server-to-clients call** (`replication.md` lists it): on the host it sends the call to every machine and runs it there; on a client it runs `OnPicked` when the call arrives. So `OnPicked` runs on **every machine**, host included; the parts that change the inventory test `netIsRemote` themselves (`ReceiveHealth`, `ReceiveArmor`, `ReceiveAmmo` act on the host only; `ReceivePowerUp` is its own call) |
| 3 | **`CBaseItemEntity::OnPicked`** (read; every subclass calls it after its own effect, or before): (a) tells the spawner that made the item (the spawner's own virtual); (b) stores the picker; (c) tells the **game info entity** to `ReceiveScore(GetPickupScore())` (the score added to the session's statistics, and an extra life per `ggp_slExtraLifeScore` points, 10,000 in the data, **for all players**); (d) if the item has no spawner and is not dynamically created and `IsChapterResurrectionEnabled()` is **false**, calls the game info entity's `DisableChapterResurrection(item)`, so that **a picked treasure or extra life does not come back when the chapter is restored** (it returns true in the base class and false in `CTreasureItemEntity` and `CLifeItemEntity`); (e) then, in a **deathmatch-type** session: an item without a spawner that was not made by game code is **hidden and the event `Unhide` is scheduled after `bip_fRespawnTime` seconds** (the item params of the item), any other item is **deleted** by a `Delete` event after a delay of 1e-5 s, that is at once; in every other session: if `OnlyFirstPlayerPicks` was true the item is hidden for everybody, otherwise only the picker's visibility bit is cleared; (f) raises the macro event `Picked` on the item; (g) calls the picker's `OnItemPicked(item)`: the HUD item-picked element and the model's "Pickup" sound |
| 4 | **Respawn** (deathmatch only). The item reappears when the scheduled `Unhide` runs; the delay is `bip_fRespawnTime` of the item's `.ep` file (60 s if the file is missing), per class (section 4). In single player and co-op a taken item **never respawns** by itself (a spawner may make a new copy; a chapter restore brings back the items whose `IsChapterResurrectionEnabled` is true) |
| 5 | **Co-op "stays" options** (`OnlyFirstPlayerPicks` of the class, game type co-op only): weapon pickups use `!sgp_bWeaponStaysInCoop`, ammunition `!sgp_bAmmoStaysInCoop`, health and armor `!sgp_bHealthAndArmorStayInCoop`; in every other game type, and for all other classes, the record's `ep_bOnlyFirstPlayerPicks` copied to the entity applies. (`sgp_bWeaponStaysInCoop` and the two others are session options of `replication.md`.) |
| 6 | **Item filter.** In a deathmatch-type session the host (and a local game) asks the session's list of disabled item classes (`CGameInfoEntity::IsItemAllowed`, T01-101); a disallowed class is hidden at boot and at simulation start and stays hidden after `Unhide`. All other game types allow every class |
| 7 | **Score.** `GetPickupScore`: ammunition **5**, power-up **50**, weapon pickup **100**, extra life **1,000**, health, armor, repair and treasure **their own amount** (so a treasure of 5,000 scores 5,000 and an extra life 1,000); the generic item 0. The same numbers feed the "serious score" multiplier that the player applies (`players-session-classes.md`; not read here) |
| 8 | **Drops.** `CPlayerPuppetEntity::DropWeapon` and `DropPowerUp` build the item through the factories `samCreateWeaponItemProperties(WeaponIndex)` and `samCreatePowerUpItemProperties(PowerUpIndex)`, spawn it at the player's placement, set `en_bDynamicallyCreated`, give it a random velocity along the view direction, and schedule a `Delete` after `ggp_fWeaponItemStayTimeAfterDrop` or `ggp_fPowerUpItemStayTimeAfterDrop` seconds. `DropWeapon` does nothing for a weapon that has no ammunition kind (saw, zap gun, Colt, combo); the dropped weapon carries the player's **current** ammunition count of that kind as its quantity. `DropActivePowerUps` drops every power-up that is still active and then resets all power-ups |

### 6. Values that differ from the class default

Of the 2,730 placed items, the member values equal the class constructor default in every item, with these exceptions in the **flags** (script section 4): `en_bOnlyFirstPlayerPicks` is 1 in 2 of 83 large armor, 2 of 157 large health, 1 of 47 extra-large health, 1 of 78 ammunition packs (editor overrides); `en_bFillsAboveHalf` (health, armor) is 1 only for the classes whose constructor sets it (extra-small and extra-large health, extra-small armor and XXL armor), checked on every item that has the member. The 14 older worlds lack the last member of five classes (`en_bFillsAboveHalf`, `en_fWastedTime`, `en_slAmmoQuantity`, the item params link): a reader must default them to the class constructor's value.

### 7. The generic item, the obsolete classes and the classes no world places

- **`CGenericItemEntity`** (52 placed items in 14 worlds, 102 records): a pickup with **no effect of its own**: `IsNeeded` is true (base), score 0, amount 0, `OnPicked` is the base one, so taking it only raises the `Picked` events and hides it. It is the **story item**: the model comes from the record (`ep_strBodyPath`, default `Models/Default/Box.mdl`; 17 distinct models in the data, among them a key, a coin, a gold record, a crossbow, a banana, a trumpet and four boss trophies), `ep_bOnlyFirstPlayerPicks` is 1 by default and in all 102 records; `bip` file `genericitem.ep` (30 s). **Medium**.
- **Obsolete (3 classes, 6 with properties)**: `CBladesItemEntity` (ammunition kind blades), `CCircularSawItemEntity` (weapon pickup of the saw) and `CSerious_BombItemEntity` (ammunition kind serious bomb): their `OnCreate` is the function shared with obsolete brain and puppet classes (it only logs the "obsolete" message). The same message appears in `puppet-classes.md` for 11 puppet kinds. No world has one (script). The factory for weapon pickups has no case for weapon index 0 (saw) or 14 (combo). **High** that they are unused in the data, medium that they do nothing.
- **Live classes with no placement** (10 classes): `CColtItemEntity`, `CZapGunItemEntity`, `CFlamerItemEntity`, `CNapalmItemEntity`, `CStrengthItemEntity` and their properties. The Colt and zap gun have no ammunition kind and are never dropped (rule 8); the **flamer pickup** (drop of a flamer, ammunition napalm) and the **strength power-up** (drop of an active strength) can be made at run time only; the napalm ammunition pickup has no creator in the code read here (**low**; Open question 5).

## Invariants

1. 113 exported classes = 56 entities + 56 properties + `CBaseItemParams`; 97 are in the data (48 + 48 + 1), 16 are not (script section 1). A reader must not look for the 16 in a world file.
2. Every placed item has a record of the matching class, and there are **4,222 = 2,730 + 1,492** records: the extra 1,492 are owned by spawners and carry `CEntityProperties.2` null (script).
3. A placed item either has a spawner link and no mechanism, effect or body (1,492) or none of the link and all three (1,238); never both (script).
4. In every placed item the class-specific members equal the class constructor's defaults (amounts, ammunition kind, weapon index and quantity, power-up index, model); the `.ep` link goes to one file per class (script, 2,730 and 2,140 items).
5. `CBaseItemParams` holds one number; it is never an amount.
6. `GetPickupScore` of health, armor, repair and treasure equals the amount; of ammunition 5, power-up 50, weapon 100, life 1,000 (medium).
7. In a deathmatch the pickup respawn delay is the per-class `.ep` number; elsewhere an item is not respawned by its own timer.

## Test vectors

All from the retail install via `tools/re/item_classes_verify.py`, unless a binary reading is named.

1. **Counts.** 113 exported classes, 919 exported functions; 97 in the data (76 as the `S` twin, 21 under the `C` name); 2,730 placed items in 58 worlds; 4,222 property records; 1,492 items behind a spawner, 1,238 without; 51 `CBaseItemParams` files; 8 `.ctl` files with an item record.
2. **Order rule.** `SBaseItemEntity` has 19 members; the data's numbers `.12`, `.15`, `.16`, `.30`, `.40`, `.20`, `.31`, `.202`, `.501`, `.502`, `.503` are, in order, `en_hre`, `en_hmech`, `en_hbo`, `en_henSpawner`, `en_bMultiSpawnerTemplate`, `en_qvOriginalPlacement`, `en_henSpawnerWhoSpawnedMe`, `en_bNoGravity`, `en_vNetDesiredVelAbs`, `en_qvNetPlacement`, `en_pbipItemParams`.
3. **Respawn.** An extra-large health item in a deathmatch, taken at time *t*, is hidden and reappears at *t* + 120 s (`healthitemxl.ep`); an extra-small one at *t* + 10 s; an item with no parameter file would use 60 s (binary reading).
4. **Score.** A medium health item (25) adds 25 to the session score; a large treasure adds 5,000 and, with `ggp_slExtraLifeScore` 10,000, two such pickups cross one extra-life threshold; an ammunition pickup adds 5; an extra life 1,000; a weapon pickup 100.
5. **Co-op.** In a co-op session with `sgp_bAmmoStaysInCoop` set, an ammunition pickup is not removed when taken: the picker's bit in `en_ulVisible` is cleared (mask `-1` becomes `-1 & ~(1 << n)`); with the option off, it disappears for everybody.
