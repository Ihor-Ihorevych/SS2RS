# `.ep` entity parameter files

- **Roadmap task:** T01-014
- **Author:** @Ihor-Ihorevych/agent · **Reviewer:** _none yet (T01-049)_
- **Confidence:** **high** for the file structure, the class tree, the inheritance rule, the references to other files and the link from world entities (checked on all 322 files and all 59 worlds); **high** for the schema reference (generated from the files' own type tables); **medium** for member names that are numbers only; **low** for what the individual parameters mean (units, effects): that is gameplay (T01-024…T01-029) and is only sampled here. Scope: the **322** distinct format-8 `.ep` files of the retail install with patches.

Prerequisites: `ctsemeta-container.md`, `ctsemeta-types.md`, `ctsemeta-objects.md`. The full member reference is **`ep-schema.md`** (generated by `tools/re/ep_schema.py`: 80 classes, 592 members, with the values observed in the install).

## Summary

An `.ep` file is a **parameter set for one kind of game object**: one projectile type, one enemy or vehicle type, one pickup, one weapon. The file is pure data: a `CResourceFile` and **one root object** whose class derives from `CEntityParams`, plus the sub-objects it owns (attacks, blasts, animations, graphs). World entities do not copy these numbers; they **refer to the file** (`world → .ep`), so changing a file changes every entity that uses it. There is **no file-level inheritance or override**: classes inherit through the C++ class tree, and values are set per file.

The files live under `Content/SeriousSam2/Databases/`: `GenericProjectiles/` (94: `Common_Projectiles` 70, `Boss_Projectiles` 17, `Spawning_Projectiles` 7), `EntityParams/` (104: `Items` 51, the weapons and their rendering parameters) and `Puppets/` (124: `Enemies` 48, `NPCs` 22, `Vehicles` 21, `Turrets` 11, …).

`tools/re/ep_schema.py --check` (read-only, `SS2_DATA_DIR`; `--worlds N` adds the world links) over the retail install with all patches:

- **All 596 external references resolve to a file of the install**: `.mdl` 256, `.ep` 118, `.ctl` 78, `.pss` 78, `.tex` 29, `.wav` 24, `.pfx` 6, `.tfx` 4, `.fnt` 2, `.rsc` 1.

## Class tree and inheritance

Inheritance is the **class chain of the type table** (`parent` of each class): members are stored **flat, base class first**, exactly as in every CTSEMETA object. That is the whole inheritance mechanism. A derived class adds members; a file sets **every** member of the chain; nothing is inherited from another file. The root classes and their chains:

| Branch | Root classes (files) |
|---|---|
| `CEntityParams > SBaseProjectileParams > SGenericProjectileParams` | `SGenericProjectileParams` (93), `CFlamerProjectileParams` |
| `CEntityParams > SPuppetParams` | `SLeggedPuppetParams` (81), `SAircraftPuppetParams` (19), `STurretPuppetParams` (14), `SHovercraftPuppetParams` (5), `SPlayerPuppetParams` (4, below `SLeggedPuppetParams`), `SRollingBallPuppetParams`, `SGenericLeggedPuppetParams` |
| `CEntityParams > CBaseItemParams` | `CBaseItemParams` (51 pickups; one member) |
| `CEntityParams > SBaseWeaponParams` | one class per weapon: `SColtWeaponParams`, `SUziWeaponParams`, `SAutoShotgunWeaponParams`, `SDoubleShotgunWeaponParams`, `SMiniGunWeaponParams`, `SSniperWeaponParams` (these six through `SBaseScatterWeaponParams`), `SRocketLauncherWeaponParams`, `SGrenadeLauncherWeaponParams`, `SCannonWeaponParams`, `SPlasmaRifleWeaponParams`, `SBeamGunWeaponParams`, `SZapGunWeaponParams`, `SCircularSawWeaponParams`, `SCircularSawBladesWeaponParams`, `SKlodovikGunWeaponParams`, `SSeriousBombWeaponParams`, `CFlamerWeaponParams` (2–3 files each) |
| `CEntityParams > SBaseWeaponRenderingParams` | one `…WeaponRenderingParams` class per weapon (the view-model and effect side of each weapon) |

Class variants: 6 classes are defined differently in different files (`CResourceFile` 2 variants, `CResource` 3, `SPlayerPuppetParams` 3, `SPuppetHealthParams` 2, `CMiscPupeptParams` 2, `CFlamerWeaponParams` 2): the type table of **each file** is authoritative, as for every CTSEMETA file; `ep-schema.md` lists each variant.

### Member names

About 71 % of the members (472 of the 667 rows of `ep-schema.md`) have **readable** names (the engine's own naming: `bp_pmcModel`, `bp_bHorizontalProjectile`, `pp_paPuppetAttack`, `sb_pgppProjectileParams`, `td_pgrPitchOverDist`, …; prefixes per class: `bp_` base projectile, `gpp_` generic projectile, `pp_` puppet, `lpp_` legged puppet, `sb_` single blast, `sp_` shooting process, `pa_` puppet attack, `td_` throw description, `gh_` graph holder, `mc_` move character), the rest are **numbers** (for example `SBaseProjectileParams.10`); a reader identifies members by the qualified name `Class.member` in either case. Several member types are identifiers: `IDENT` members hold an index into the file's own `IDNT` table (a string such as an attachment or animation name: `Blast`, `Barrel01`, `Mouth`, `Shoot`, `3rdPersonCamera`, `Body_Commander_IdleFight`; index 0 is the empty identifier; 132 of 322 files have a non-empty table).

## How entities use the files

A world entity or its property record holds an **external reference to an `.ep` file** in a member of its own class, and the root class of that file is the matching parameter class:

| Entity / record | Member | Root class of the referenced `.ep` |
|---|---|---|
| `SLeggedCharacterEntity` (an enemy or NPC) | `SPuppetEntity.en_pppPuppetParams` | `SLeggedPuppetParams` |
| `SLeggedCharacterProperties` (its extra record) | `SPuppetProperties.ep_pppPuppetParams` | `SLeggedPuppetParams` |
| `SAircraftCharacterEntity` / `…Properties` | `SPuppetEntity.en_pppPuppetParams` / `SPuppetProperties.ep_pppPuppetParams` | `SAircraftPuppetParams` |
| `STurretCharacterEntity` / `…Properties` | the same members | `STurretPuppetParams` |
| all item entities (`SShellsItemEntity`, `SArmorItemSEntity`, `SHealthItemMEntity`, …) | `SBaseItemEntity.503` | `CBaseItemParams` |

The pattern is `S<Kind>CharacterEntity` ↔ `S<Kind>PuppetParams` (legged: 3,780 + 1,818 references, aircraft 518 + 254, turrets 299 + 164) and every item entity ↔ `CBaseItemParams` (about 1,500 references); the editor record (`…Properties`) and the runtime entity carry the same reference. Projectiles are reached **from other `.ep` files** (below); the player's weapons are not entities of the worlds, so the weapon files are used by the game code (T01-028); no world entity refers to a hovercraft or rolling-ball parameter file.

## What the files refer to

- **Between `.ep` files:** blasts name their projectile: `CSingleBlast.sb_pgppProjectileParams` → a `SGenericProjectileParams` file (145 references); weapons name theirs (`SBaseWeaponParams.23`); puppets reach projectiles through their attacks (89 from `SLeggedPuppetParams`, 26 aircraft, 15 hovercraft, 15 turret). So an attack tree ends in a projectile file. The reference graph between the 322 files has **no cycles** and the projectile files refer to **no** other `.ep` file (checked).
- **To other formats:** the model of a projectile (`SBaseProjectileParams.bp_pmcModel` → `.mdl`, 93 files), the weapon models (`SBaseWeaponParams.24`), control files (`SBaseWeaponParams.35` and `.36` → `.ctl`, 35 each, and `CMountedTool.mt_pctTool` → `.ctl`, 8), the **puppet spine data** (`SLeggedPuppetBodyParams.lpbp_psdPuppetSpineData` → `.pss`, 78: one per legged puppet; the `.pss` format is unidentified, T01-019), effects (`.pfx`, `.tfx`), sounds (`.wav`), textures and fonts. The `.ctl`, `.pss`, `.pfx`, `.tfx` formats are specified elsewhere or open.

## Reader invariants

1. Read the file as a CTSEMETA file; require exactly one shared root and that its class chain contains `CEntityParams`.
2. Take member meanings from the **qualified** name `Class.member` of the **file's own** type table; do not assume that a member number means the same in a class variant.
3. `IDENT` members index the file's `IDNT` table.
4. External references must be resolved through the virtual file system (all of them resolve in the retail data); a missing file is an error for that entity, not for the whole database.
5. Polymorphic pointer members (`SMoveCharacter*`, `CGraph*`, `CPuppetAttack` parts) hold objects of derived classes: dispatch on the object's class.
6. Do not copy numbers into entities at load time; keep the reference, because many entities share one file.
