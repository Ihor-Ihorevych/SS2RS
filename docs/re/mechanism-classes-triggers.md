## Summary

This page covers **22 exported classes** that mark areas, count progress and run cameras: `CDetectorAreaEntity`/`Properties`, `CKillerEntity`/`Properties`, `CLocatorEntity`/`Properties`, `CEnvironmentDamagerEntity`/`Properties`, `CAlarmEntity`/`Properties`, `CSecretEntity`/`Properties`/`Data`, `CMissionObjectiveEntity`/`Properties`/`Data`, `CNavigationalBeaconEntity`/`Properties`/`Data`, `CCameraEntity`/`Properties`/`EnvelopeProvider`. In the 59 worlds they are **1,712 placed entities**: detector areas 1,077, mission objectives 131, navigation beacons 174, secrets 110, killers 104, cameras 76, locators 17, environment damagers 23. **Alarms are in no file.** The three `...Data` classes are small structures stored inside the game's save state, not entities.

What a reader needs to know first:

1. **All of these are invisible markers or announcers.** They have an editor renderable only; what the player sees comes from effects, sounds, the Netricsa and the HUD. Their behaviour is driven by two channels: **touch** of a hull (detector, killer, damager) and **macro commands and events** (`level-logic.md`): the detector raises "Activated", the mission objective is activated, accomplished or failed by script, the camera plays a path by script.
2. **Detector areas are the level scripting's main trigger**: 1,077 of the 1,712 placed entities; 516 carry a chapter link (they belong to that chapter).
3. **Secrets and mission objectives report to the game info entity** (`players-session-classes.md`): a secret increments the secret counter, announces itself with a message, a sound and a Netricsa icon; objectives show a text, play a success or failure sound and music and appear on the scanner.
4. **Net behaviour:** the secret, the mission objective, the beacon and the camera are `NEB_STATIC`; detectors, killers, locators, damagers and alarms are `NEB_NONE` (host only, nothing replicated: they export no `GetNetBehavior`, `replication.md` 3.4). The four `NEB_STATIC` classes were confirmed by a second reading of the exported functions (each returns 1).
5. **Uninitialised data in the files.** `en_mosNetMissionObjectiveState` (the replicated copy of the objective state) holds **stray values in 36 of 131 stored entities** (for example 23,564,888 or 360); the true start value is 0. A reader must treat any value outside the enumeration as 0.

### 2. Detector areas: `CDetectorAreaEntity`

**Role.** A box, sphere or other primitive (`CPrimitiveDesc`: 4 values per record) that **fires the macro event "Activated" when something enters it**. 1,077 in 41 worlds; it is the trigger of the level scripts (`level-logic.md`).

**Properties (7).** `ep_pdPrimitive` (`.1`, the shape, 1,077), **`ep_hepTarget`** (`.2`, an optional **target record**: null in 1,074, a chapter info record in 2 and a prop record in 1: the entity that the detector notifies when something enters; read: the target entity's virtual function is called with the toucher), `ep_bCustomEventDetectorArea` (1 in 97 of 1,077), `ep_bPlayersOnly` (`.3`, 1 in 979 = the area reacts to players only, 98 react to everything; medium: the name and the two hull categories below), `ep_colActive` (`.6`) and `ep_colInactive` (`.7`) (the editor colours as packed colour values: 98 and 32 distinct), `ep_idParentPart` (0). **Entity (14).** The hull (`.3`), the editor renderable (`.10`), the target entity (`.2`), an **"activated" flag** (`.13`, 0 in all 1,077), the last activator (`.6`, null), the three properties above, `en_eaCustomDetections` (the entities currently detected in custom mode), the parent entity (`en_henParent`: an animated mover in 22 of 1,077) and its body, and `en_idParentPart`.

**Rules (read).** *Normal mode:* the first time a valid entity (the hull owner is a real entity) touches the hull, the detector stores it as the last activator, calls the target entity if there is one, switches itself off (the hull's aspect is deleted so no more touches arrive), changes the editor colour to the **active** colour and raises the **macro event "Activated"**. *Custom mode* (`ep_bCustomEventDetectorArea`, 97 detectors): the detector does **not** switch off: a script registers entities with `RegisterCustomDetection` and removes them with `UnregisterCustomDetection` (both log an error "... is called on detector area that is not marked as 'Custom entity detector'" when the flag is off); only registered entities are detected and each touch by a registered entity raises the event **"CustomDetection"** and removes the entity from the list. `Recharge` re-arms a used detector (the activated flag is cleared, the hull is created again and the inactive colour is restored). `Deactivate` clears the list and deletes the hull. The hull categories are "playerdetector" (players only) and "detector" (everything) and, for the custom list, "custom_detector" and "ignoreall" (the category an entity gets when it is not in the list).

**Methods (14 + 3).** `OnCreate`, `OnBoot` (arms with `Recharge`), `OnShutDown`, `OnDelete`, `OnUpdate` (follows the parent), `CreateHull`, `OnHullTouched`, `Recharge`, `Deactivate`, `GetLastActivator` (script query), `RegisterCustomDetection`, `UnregisterCustomDetection`, `SetupCustomDetectionCollisionCategory`, `GetAbsPlacement`. Properties: `GetBoundingBox`, `OnGetStretch`, `OnStretch`.

The envelope provider (1 member, the camera handle) exposes the envelopes "Master", "Target" and "Camera" of the animation editor (positions "Pos.X/Y/Z", "Rot.H/P/B" and the values "Val.FOV", "Val.Fade", "Val.Aspect"): the same editor interface as the animated mover.

**Rules (read / profiled, medium).** `SetState(2)` (playing) enables the per-step update, resets the animation instance's playback when one exists (read in part) and calls the movement-started hook (`MovingStarted`); the **step** evaluates the animation (`EvalFrame`: position, rotation, field of view, aspect, fade) into the camera's placement and moves the camera aspect. Leaving state 2 disables the update, calls the camera stop hook if the new state is 1, raises the **macro event "AnimationFinished"** and ends the latent wait of the script (`PlayAnimWait` / `StartWait` block the script until then). `SetCurrent` makes this the **world's current camera** (the world info entity renders through it; `SetCurrentCameraInternal` registers it, `UnsetCamera` clears it), `RenderView` draws the scene from the camera into the current draw port with the field of view and aspect ratio and the fade overlay, then the text queue.

**Envelope evaluation, the fade overlay, the text queue and user break — now read in full (T01-171):**

- **`EvalFrame` delegates all keyframe/interpolation work** to three per-channel evaluators, `aniEvaluatePosLength`, `aniEvaluateRotation` and `aniEvaluateStrength`, each called with a string channel identifier: `"Camera"` (always, for the camera's own placement), `"Camera.FOV"`, `"Camera.Aspect"`, `"Camera.Fade"` (always, the three scalar outputs), and — only when the corresponding flag is set — `"Master"` (when `en_bUseMaster`/`ep_bUseMaster`) and `"Target"` (when `en_bUseTarget`/`ep_bUseTarget`). No keyframe lookup or interpolation method is visible in `EvalFrame` itself: it is entirely the evaluators' job (the same `ani*` envelope family already used by `CAnimatedMoverEntity`; interpolation kind not re-derived here). This confirms, and gives the exact mechanism for, what the property table already named: the envelope provider's three editor channels are literally called "Master", "Target" and "Camera".
- **"Master" is a parent transform, not a separate entity.** No entity handle, name lookup or link to another object was found anywhere in `OnCreate`/`SetInitialParameters` (the only entity link set there is the ordinary property-tree parent). Instead, when the camera's own `"Camera"` channel is **relative** (`en_bRelativePath`, read as the gate at a flag next to the camera's base transform), the `"Camera"` channel's quaternion/position is composed **onto** the `"Master"` channel's result — i.e. "Master" is simply a second envelope of the *same* camera's own animation data that the relative "Camera" channel is applied on top of, exactly matching the envelope provider's own interface (`GetProviderAbsPlacement`, `GetTargetAbsPlacement`).
- **"Target" drives a look-at, not a second camera.** When `en_bUseTarget` is set, `EvalFrame` additionally computes the vector from the evaluated camera position to the evaluated "Target" position, normalises it, derives a pitch via `asin` (clamped to [-1, 1]) and a yaw via `atan2`-style `fpatan`; the yaw is forced to 0 whenever the pitch falls outside a small band (so a near-vertical look-at keeps the camera's existing yaw rather than spinning); the pitch/yaw pair is converted to a quaternion (`mthEulerToQuaternion`) and multiplied into the camera's rotation. A single threshold gates the whole branch (unresolved value), so very small target offsets presumably leave the authored rotation untouched.
- **The fade overlay** (`RenderView`) compares the evaluated `en_fFade` against a threshold: above it, the overlay is **white** and its alpha grows with the distance above the threshold; below it (or equal), the overlay is **black** and alpha grows with the distance below. Alpha is clamped to [0, 1] and scaled by a second constant before being packed into the fill colour; `gfuOrtho`/`gfuBlendType`/`gfuFill` draw it, after the 3D scene and after the draw port is popped, and the **text queue draws last of all** (`CTextQueue::Render2D` on the handle at `en_htqTextQueue`) — confirming the stated draw order (scene, then fade, then text).
- **The text queue's "fade" is a queue-method choice, not a timed value this class exposes.** `SetText`/`SetTextFade`/`ClearText`/`ClearTextFade`/`ClearAllTexts`/`ClearAllTextsFade` are thin wrappers that forward to `_net` twins; the `_net` functions carry the actual replication: on the host they serialise the call onto the VM stack and run it through `CVirtualMachine::ProcessRPC_t` (`replication.md`'s RPC mechanism) so every machine's queue stays in sync, while a non-host machine applies the call locally. No slot count, duration or advance/clear timer is visible in `CCameraEntity` itself — that state lives inside `CTextQueue`, which this task did not open.
- **User break, corrected.** `en_bEndCameraOnUserBreak`'s stated effect was wrong: `UserBreak1`/`UserBreak2` do **not** gate on it. On a client, both RPC the call to the host; on the host, if the camera is active (`en_csState` == 2, playing), both set `en_bLastCameraInterrupted` and raise **two** macro events (object = this camera when the event's own class derives from the camera's type, else none — the literal event names were not recovered, since the decompiler never materialises the constant strings in this function); **only if the user-break flag is currently set** does the host additionally call a stop-camera vtable slot. So breaking an active camera always interrupts it and fires its macro events; the flag (`EnableUserBreak`/`DisableUserBreak`, toggled at runtime) controls only whether the break *also* stops the camera outright. If the camera is not active, both functions just log a message and do nothing.
