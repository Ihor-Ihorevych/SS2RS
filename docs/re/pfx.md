# `.pfx` particle effects

- **Roadmap task:** T01-016
- **Author:** @Ihor-Ihorevych/agent · **Reviewer:** _none yet (T01-049)_
- **Confidence:** **high** for the file structure, the three kinds of particle effect, the emitter shapes, the constant-or-graph parameter rule, the references and the enumerations in use (checked on all 604 files; the member list is generated from the files' own type tables, see `pfx-schema.md`); **medium** for the blend types (derived from the textures they are used with) and for what members with number-only names do; **low** for the graph evaluation and for the exact simulation (units, formulas). Scope: all **604** distinct format-8 `.pfx` files of the retail install with patches.

Prerequisites: `ctsemeta-container.md`, `ctsemeta-types.md`, `ctsemeta-objects.md`; `tex.md` (particle textures), `mtr.md` (the blend enumeration), `rsc-ctl.md` (graphs). The full member reference is **`pfx-schema.md`** (generated by `tools/re/ep_schema.py`: 31 classes, 180 members).

## Summary

A `.pfx` file is one **effect**: a `CEffect` root that holds a list of **particle effects**, each a particle emitter with its own texture, blending, emitter shape and parameters that change over the particle's life. Almost every parameter is a **constant that may be replaced by a graph** (`CGraphHolder`). The files are pure data; the simulation is in the engine. 604 effects (explosions, smoke, sparks, flares, debris trails, weather, nature, weapon effects) hold 1,867 particle effects between them.

## Evidence

`tools/re/pfx_verify.py` and `tools/re/ep_schema.py --check --ext .pfx` (read-only, `SS2_DATA_DIR`) over the retail install with all patches:

- **All 604 files decode**, each with exactly one shared root of class `CEffect`, no extra records; **all 1,608 external references are `.tex` files and all resolve**.
- In every file, the particle effects are **exactly the objects listed in `CEffect.5`**, and each is one of the three kinds below: `CMachineParticleEffect` 1,842, `CCloudsParticleEffect` 22, `CAtomicParticleEffect` 3. A file holds 1 (181 files), 2 (124), 3 (137), 4 (54) or up to 8 or more (45 files).
- **Every one of the 1,842 machine effects has exactly one emitter shape** (sphere 1,744, box 76, cylinder 22).
- Of **88,343** graph holders, 2,066 (2.3 %) use a graph; the rest are constants. 4,850 control points in all.

## Particle effects

All three kinds derive from `CParticleEffect`:

| Member | Meaning |
|---|---|
| `CParticleEffect.1` | `CString`: a name (mostly empty) |
| `CParticleEffect.3` | `CParticleEffectTexture`: `.1` → the **texture** (an external `.tex`), `.2` × `.3` = **atlas columns × rows** (1×1 in 1,590 particle effects; 2×2 in 152; 4×1, 8×1, 2×1, 4×4, 1×4, 8×4), `.4` an animation rate (0 to 5), `.5` a flag |
| `CParticleEffect.4` | `CParticlesRendering`: `.1` **blend type** (`GfuBlendType`, see below), `.3` flag, `.4` float (0, 0.413, 0.5, 1), `.5` **render order** (`RenderOrder` 0 in 1,556, 3 in 126, 1 in 122, 2 in 63) |
| `CParticleEffect.11` | `ParticleEffectOrientation`: 1 (871), 0 (588), 3 (310), 4 (98): how the particles face (names not in the data) |
| `CParticleEffect.7` | `DistanceAcceptanceFlags`: 8 (1,853), 24 (9), 4 (4), 16 (1): at which distances the effect is accepted (a level-of-detail bit set) |
| `CParticleEffect.5` | int: 1 to 2,000,000 (10,000 in the test vector): probably the **maximum number of particles** |
| `CParticleEffect.6` | `CRelativePlacement`: ten graph holders (`rp_ghOffsetX/Y/Z`, `rp_ghVelocityX/Y/Z`, `rp_ghHeading`, `rp_ghPitch`, `rp_ghBanking`, `rp_ghWeight`) |
| `CParticleEffect.2`, `.8`, `.9`, `.10` | flags and a float (−0.3 to 2.1); not analysed |

        mpel_ghEmittingFreq                emission frequency
        mpel_ghEmittedParticleLifeMin/Max  life span of an emitted particle
        mpel_ghEmitVelocityMin/Max         launch velocity

  .3  CParticlesCollision          .1 BOOL (collide), .2 float 0 .. 1.4 (bounce?), .3 float (0.2 .. 3.241)

Emitter shapes derive from `CEmitterShape` (pivot offset X/Y/Z graph holders, a `LaunchDirOverride` 1 to 3 and an override ratio holder): `CSphereEmitterShape` (positions by heading, pitch and radius ranges: `ses_ghEmitPosH/P/RMin/Max`), `CBoxEmitterShape` (`bes_ghBoxW/H/L`), `CCylinderEmitterShape` (`ces_ghHeight`, top and bottom radius ranges, `ces_ghHMin/Max`).

### `CCloudsParticleEffect` (22) and `CAtomicParticleEffect` (3)

Special emitters with their own, mostly numbered, members (see the schema reference): **clouds** (22 files: members with value ranges for a count, sizes, two pairs of angles, four `COLOR`s, a vector, atlas and rendering as in the base) and **atomic** (3 files, for example the flies of the test vector: a count, a gradient pair for the head and trail colour, `ape_ghTrailWidth`): trailing particles. Their meaning is not worked out beyond the members' value ranges.

## Constant or graph: `CGraphHolder`

Nearly every numeric parameter is a **`CGraphHolder`**: `gh_fValue` (a float) and `gh_pgrGraph` (a pointer to a graph, null in 97.7 % of the holders). **If the graph pointer is null the parameter is the constant `gh_fValue`**; otherwise the graph gives the value (and `gh_fValue` is probably its scale or default; not determined). The graphs are the classes of `rsc-ctl.md`: `CLinearGraph` (1,943 holders), `CValueGraph` (86), `CSineGraph` (27), `CStepDownGraph` (5), `CStepUpGraph` (3), `CRandomGraph` (2); the x axis is the particle's or the effect's life, the evaluation is **not specified** (shared with the camera and shader graphs).

A **gradient** (`CGradient`) is a list of `CColorKeyFrame` (`.1` position, `.2` colour as ARGB with alpha in the top byte, for example `0xFF858585`): colour over life, 1 to 7 keys.

## Blend types (evidence for `mtr.md`)

The `GfuBlendType` of `CParticlesRendering.1` is the same enumeration as in materials (`mtr.md`). Correlated with the alpha channel of the particle's texture over all 1,867 particle effects:

| Value | Uses | Textures | Reading |
|---|---|---|---|
| `0x1F5` (501) | 983 | **all have an alpha channel** (DXT5 388, 32-bit 376, DXT3 219): smoke, chimney smoke, wooden debris | **alpha blending** |
| `0x1F7` (503) | 495 | mostly **no alpha** (24-bit 401, DXT1 23; some with alpha): flares, fire clouds, trail debris, "wavering" | **additive** |
| `0x1F8` (504) | 366 | mostly no alpha (24-bit 223, DXT1 44): flares, sparks, floater trails | an additive-type variant (the difference to `0x1F7` is not determined) |
| `0x1FA` (506) | 19 | no alpha (24-bit 17): explosion flares | an additive-type variant |
| `0x1F4` (500) | 4 | alpha textures | opaque/default |

For materials this supports the tentative reading in `mtr.md` for `0x1F5` (alpha blending) and `0x1F7` (additive-like). `0x1F8` behaves as an additive-type mode in particles although materials mostly use it with alpha textures: its exact mode stays open (T01-059).

## Reader invariants

1. Require one `CEffect` root; take the particle effects from `CEffect.5` and dispatch on their class (three kinds).
2. A machine effect must have an emitter shape of one of the three classes; fail on an unknown class.
3. Read every `CGraphHolder` as "constant unless the graph pointer is set".
4. The control point's second member is garbage: ignore it (`rsc-ctl.md`).
5. All 1,608 texture references resolve in the retail data; a missing texture is an error of that particle effect only.
6. Do not interpret the unnamed enumerations (`EffectLifeType`, `ParticleShape`, orientation, distance flags, render order) before the renderer spec fixes them (T04).
