## Summary

The weapon entity's state machine is 10 states (`weapon-classes.md` section 3). Every state-entry goes through one function, `SetState`, which starts that state's animation or sound and, for four states, schedules the entity's own think (`main-loop.md` section 7) to call the matching end-of-state callback after a duration that is **always an animation length** (bring-up, put-down, boring, the bomb's fuse) or **the animation length rescaled by a stored duration when one is given and otherwise the animation length** (reload) — **no state's duration is a bare data number**: `bwp_fMinRecoilDuration`/`bwp_fMaxRecoilDuration` set the *recoil* duration (by `lerp`, not by an animation), but bring-up, put-down, boring and (in the retail data) reload all wait for a model animation to finish. The repeat-fire loop while a trigger is held, and the "shots owed" catch-up after a long frame, are one function, `DoFiringsFromLastFireTime`, called from four places (the first press, a charge release, a scheduled auto-fire, and the per-step continuation while idle/boring or recoiling); it fires one shot immediately in the common case and **several in one call** when the elapsed time since the last shot covers more than one recoil period (a long frame, or a lag spike). An **uncharged shot always passes fire power exactly 0.0** — read directly in `CallFireStart`, closing `weapon-classes.md` open question 9's second half.

2. **The firing chain is one function called from four places, through one entry point:**

   `CallFireStart` (fire button pressed, idle or boring, `CanFireFromWeaponNow` agrees) → **no flag**: `DoFiringsFromLastFireTime(0.0)` at once. **Charging flag**: `DoCharging()` only (no shot yet). **Spin-up flag**: `SetState(WS_SPIN_FIRING)` only (no shot yet; the first shot waits for the barrel to reach full speed, section 6).

   `FireReleasedInternal` (fire button released) → in `WS_CHARGING`: `DoFiringsFromLastFireTime(charge)` with `charge = clamp((now − charge start) / bwp_fChargingTime, 0, 1)`. In `WS_SPIN_FIRING`: `SetState(WS_IDLE)` (no final shot).

   `OnChargingEnd` (the scheduled auto-fire, `DoCharging`'s own think) → `DoFiringsFromLastFireTime(1.0)` — a held charge always auto-fires at full power.

   `OnStep` (every step, section 4) → while `WS_SPIN_FIRING` and fully spun up, or while `WS_RECOIL` on a non-charging weapon, once the time since the last shot reaches `GetRecoilDuration()` and the owner still wants to fire: `DoFiringsFromLastFireTime(0.0)`.

   `DoFiringsFromLastFireTime(power)` itself (section 5) calls `DoTheFiring(power)` one or more times; `DoTheFiring` re-checks `CanBeUsedForFiring()`, applies the **discrete-power rule** (zap gun only: a power below 1.0 becomes 0.0), stores the result as `en_fLastFirePower`, and calls the weapon's own `OnFire(power)` (the base pays ammunition and returns whether it could; a subclass launches only when it returns true). After the loop, `DoRecoil()` runs once, using the last shot's `en_fLastFirePower`.

3. **`SetState`, read in full.** Leaving `WS_BORING` notifies the owner; leaving `WS_CHARGING` stops the charging sound; entering `WS_CHARGING` starts it (from the weapon params' scheme sound, by `samPlaySchemeSound`); entering `WS_IDLE` blends (0.2 s) into the idle animation, looped; entering `WS_CANT_FIRE` tells the owner with this weapon's handle (the same call `OnStep`'s can't-fire branch repeats every step); entering `WS_BORING` clones the current pose (0.2 s) and plays the boring animation once — **but when there is no boring animation, `SetState` recurses into `SetState(WS_IDLE)` (which does play and does set the state member to 1) and then, after that call returns, unconditionally writes the state member back to 7** — so a weapon with no boring animation plays its idle pose once but is left reporting `WS_BORING` as its current state (a genuine reading of the code, not a guess; it means `IsRecoiling`/`CanBeChanged`-style state tests still see "boring" even though the idle animation ran); entering `WS_WAIT_FUSE_TO_BURN` plays a fixed fuse animation once. Every scheduled state (bring-up, put-down, boring, reload, fuse) uses the **same mechanism**: the weapon schedules its own think (`main-loop.md` section 7's `SetNextThink`-equivalent) for `(animation length, end-callback id)`; any later schedule on the same entity **replaces** the pending one (confirmed again here, as `projectile-launch.md` section 3.2 found for charging).

4. **`BringUp`/`PutDown`, read in full.** `PutDown(forced)`: refuses (does nothing) when not forced and `CanBeChanged()` is false (only `WS_WAIT_FUSE_TO_BURN` refuses, `weapon-classes.md` section 3); otherwise `SetState(WS_PUTTING_DOWN)`, blends (0.2 s) into the **same animation `BringUp` uses** (`weapon-classes.md`'s single `GetActivateAnim`, played in a different mode for putting down — there is no separate "deactivate" animation getter), schedules `OnWeaponPutDown` after its length. `OnWeaponPutDown` tells the owner, then **deletes the weapon entity outright** (`CEntity::Delete`) — switching away from a weapon does not hide it, it destroys the entity; the next time it is held, a fresh entity is created (`weapon-classes.md` point 2, now extended to weapon *switching*, not only pickup). `BringUp(0)` (normal): no blend (0.0 s), plays the activate animation forward, schedules `OnWeaponBroughtUp` after its length, which `SetState(WS_IDLE)`s. `BringUp(nonzero)` ("immediate"): clears to the idle animation at once (0.0 s blend) **without calling `SetState`** — the state member keeps whatever it was until a near-zero scheduled callback runs a moment later; this matches `weapon-classes.md` rule 4's "skip the animation and be idle" functionally (the idle animation does play at once) but the stored state is not `WS_IDLE` until that callback fires.

5. **`DoFiringsFromLastFireTime`, the catch-up after a long frame.** Reads the current `GetRecoilDuration()`. If the weapon has the **charging flag** (`WCF_CHARGE`; grenade launcher, cannon, zap gun), it always fires **exactly one** shot, never catching up — a charging weapon's "shot" is one deliberate release or auto-fire event, not a held-trigger cadence. Otherwise it reads the elapsed time since `en_tmLastFire` and the number of shots owed from it: both the recoil duration and the elapsed time are guarded against being exactly 0 (a defensive divide-by-zero check that logs "Invalid recoil duration for weapon …" or "Invalid 'delta from last fire time' for weapon …" and fires nothing if either is 0 — a weapon whose numbers are this broken cannot fire through this path at all). The shot count itself is computed by a shared floating-point rounding helper whose operand is not directly visible in this decompile (it is left on the FPU stack, not assigned to a named value); by elimination — the only quantity in scope is `elapsed / duration`, and the common case (one period or less since the last shot) must yield exactly one shot — the read is **`round(elapsed / duration) + 1`**, both truncated toward the nearest step; this doc does not commit to whether the `+1` is added before or after the rounding (**medium-low**, see Open questions). It then fires that many shots **in a tight loop within the same step** (every repeat is stamped with the *same* `simNow()` as the last-fire time, not spaced apart): each iteration calls `DoTheFiring(power)`; if `WS_WAIT_FUSE_TO_BURN` was entered meanwhile (the Serious Bomb) the loop stops at once; if `DoTheFiring` returns false (ammunition ran out) it enters `WS_CANT_FIRE` and stops; otherwise it increments `en_ctShootsFiredFromRound` and checks `ShouldReload()`, stopping the loop early (without firing the remaining owed shots) once a reload becomes due. After the loop (for whatever reason it ended, including zero shots fired by the charging-weapon's forced single pass through a failed `DoTheFiring`), `DoRecoil()` runs exactly once.

6. **The minigun's spin states, read in full (`CMiniGunWeaponEntity`, `CBaseWeaponEntity::MoveWeaponParts`).** `en_fSpinningVelocityDeg` is a **linear ramp**, stepped every frame by `MoveWeaponParts` (called from `OnStep` whenever a part mover exists): while the owner wants to keep firing this weapon, it rises toward `bwp_fSpinSpeed` at a rate of `bwp_fSpinSpeed / bwp_fSpinUpTime` per second (clamped at the target); once it has reached the target exactly, the spinning part's angle instead receives a small random jitter each step (a vibration at full spin, read but not measured); while the owner does not want to fire, it falls toward 0 at `bwp_fSpinSpeed / bwp_fSpinDownTime` per second. `CallFireStart` (`CMiniGunWeaponEntity` override): calls the base (which, by rule 2's spin-up branch, enters `WS_SPIN_FIRING`), then `SetSpinType(MGST_SPINUP)` unless already `MGST_SPIN`, and plays a one-shot trigger-click sound on its own channel. `OnFireReleased`: `SetSpinType(MGST_SPINDOWN)`, `SetFireType(MGFT_NONE)`, another trigger click. `SetSpinType`/`SetFireType` each own a **looping** sound channel (spin-up/spin/spin-down for the barrel; fire/click for the muzzle) that only changes when the requested type differs from the current one; `OnStep`'s `WS_SPIN_FIRING` branch fires the first (and every later) bullet **only once `en_fSpinningVelocityDeg` equals `bwp_fSpinSpeed` exactly** (full spin), at the same `GetRecoilDuration()` cadence every other weapon uses; `OnFire` (per `weapon-classes.md` section 6.2) is where the spin type is driven to `MGST_SPIN` and the fire type to `MGFT_FIRE` once a bullet actually leaves — so the "fully spinning, fully firing" looping sounds only start once the barrel has reached speed and a shot has gone through, not as soon as the trigger is pulled. Numbers (section 2 of `weapon_timing_verify.py`): minigun spin-up 0.5 s, spin-down 1.5 s, speed 550°/s (single player; 500°/s deathmatch); circular saw spin-up 0.6 s, spin-down 0.8 s, speed 500°/s (both files; the saw's own cutting behaviour is T01-120, not this page). Every other weapon's file carries the **same generic 0.5/3.0/500 spin defaults** (unused data: only the binary's charging/spin-up flags gate which weapon reads them; grenade launcher and plasma rifle are the two exceptions with 0/0/0, matching `weapon-classes.md`'s reading of `bwp_fSpinSpeed`).

7. **The sniper's zoom steps are `weapon-view.md` section 6, not repeated here**: the alternative-fire toggle, the `r = clamp((now − start) / fullZoomingTime, 0, 1)` ramp and the field-of-view multiplier it drives, with the single-player and deathmatch numbers and test vectors.

## Layout / rules

### 1. The ten states, as a diagram in prose

Every weapon entity starts `WS_IDLE` once brought up. From **`WS_IDLE`** or **`WS_BORING`**, pressing fire calls `CallFireStart`, which branches three ways by the weapon's own flags (at most one of the two is set): **no flag** → fire now, enter `WS_RECOIL`; **charging flag** → enter `WS_CHARGING`; **spin-up flag** → enter `WS_SPIN_FIRING`. From **`WS_RECOIL`**, once `GetRecoilDuration()` has passed, `OnRecoilEnd` runs: if the weapon can no longer be used (no ammunition) → `WS_CANT_FIRE`; else if a reload is now due → `DoReload` → `WS_RELOAD`; else → `WS_IDLE` (and, while the owner still wants to fire a non-charging weapon, `OnStep` fires the next shot once the recoil period elapses and re-enters `WS_RECOIL`, without a visit to `WS_IDLE` in between — the state only becomes externally visible as idle when the trigger is released or the next `OnStep` tick happens to observe it). From **`WS_IDLE`**, if the owner has not fired recently enough, `OnStep` enters `WS_BORING`; firing again from `WS_BORING` plays a quick idle-pose interrupt before proceeding exactly as from `WS_IDLE`. From **`WS_CHARGING`**: releasing the trigger (`FireReleasedInternal`) fires at the built-up charge and enters `WS_RECOIL`; holding past `bwp_fChargingTime + bwp_fChargingAutoFireTime` auto-fires at full power (`OnChargingEnd`) and enters `WS_RECOIL`. From **`WS_SPIN_FIRING`**: releasing the trigger returns to `WS_IDLE` directly (no recoil state); while held, `OnStep` fires repeatedly at the recoil cadence once fully spun up, staying in `WS_SPIN_FIRING`. **`WS_CANT_FIRE`** is left only by `CanBeUsedForFiring()` becoming true again (checked every step while the weapon would otherwise be idle or boring) — then `CallFireStart` can run again. **`WS_RELOAD`** ends (`OnWeaponReloaded`) in `WS_IDLE` after the reload animation. Switching away from the current weapon calls `PutDown`, entering `WS_PUTTING_DOWN` from any state except `WS_WAIT_FUSE_TO_BURN` (which refuses `CanBeChanged`); at the end of that animation the entity **deletes itself**. Switching to a weapon creates a fresh entity, which calls `BringUp`, entering `WS_BRINGING_UP` (or going idle at once for an "immediate" bring-up) and ending in `WS_IDLE`. The Serious Bomb's `OnFire` enters `WS_WAIT_FUSE_TO_BURN` instead of `WS_RECOIL`; its own `Explode` (not the base's) runs at the end of the fuse (`weapon-classes.md` rule 9).

### 3. The firing cadence rule (summary of Summary points 2 and 5)

A held trigger fires at the weapon's recoil cadence: shot → `WS_RECOIL` for `GetRecoilDuration()` (which depends on the *last* shot's fire power, so a charging weapon's cadence is itself charge-dependent through the recoil lerp) → next shot. `DoFiringsFromLastFireTime` is the single point that both fires "now" and catches up: called with elapsed time since the last shot above one recoil period (a step longer than `sim_fStepMax`'s usual 0.1 s ceiling cannot by itself cause this, since `main-loop.md` caps every step at 0.1 s; a catch-up instead happens when a weapon's own think was delayed — a reload, a charge, or a run of several frames each shorter than `sim_fStepMin` followed by one that is not, `main-loop.md` test vector 7 — or when the recoil duration itself is very short relative to the step, e.g. the minigun's 0.035 s recoil against a 0.1 s step), it fires more than one shot in that single call, all stamped with the same `simNow()`.

### 4. The fire power of an uncharged shot

**0.0**, read directly: `CallFireStart`'s non-charging, non-spin-up branch calls `DoFiringsFromLastFireTime(0.0)` with the literal constant. This closes the second half of `weapon-classes.md` open question 9 (the first half, the cheat-set bits, is unrelated and stays open there). It cross-checks `weapons-tables.md`/`weapon-classes.md` test vector 3's "assumed" fire power 0 for an uncharged Colt shot: no longer an assumption.

## Invariants

1. Every scheduled state-end callback (bring-up, put-down, boring, reload, fuse, the auto-fire's `OnChargingEnd`) rides the same single-pending-think mechanism (`main-loop.md` section 7); scheduling a new one replaces whatever was pending for that entity.
2. `DoFiringsFromLastFireTime` always fires exactly one shot for a charging weapon (grenade launcher, cannon, zap gun) and `round(elapsed / GetRecoilDuration()) + 1` (at least 1) shots for every other weapon, never more than fits before `ShouldReload()` or a failed shot stops the loop.
3. `GetRecoilDuration()` is the recoil animation's length whenever `bwp_fMinRecoilDuration ≤ 0` on a weapon that is not both charging-flagged and "scalable"; otherwise it is the lerp (checked against `weapon-classes.md` rule 2 and section 4.1's data).
4. The reload rescale (`bwp_fReloadDuration`) never fires in the retail data (the only reloading weapon, the Colt, has it 0; `tools/re/weapon_timing_verify.py`).
5. Putting a weapon down always ends by deleting its entity; bringing one up always creates (or recreates) one.
6. An uncharged shot's fire power is the literal constant 0.0, read in `CallFireStart`.

## Open questions

Ranked by what blocks an implementer. The next free ID is appended to `docs/roadmap/T01-reverse-engineering.md`.

1. **`DoFiringsFromLastFireTime`'s exact shot-count arithmetic** (whether the `+1` precedes or follows the rounding, and the rounding mode's tie-breaking) was read from a shared, unnamed floating-point helper whose operand this decompile does not show; a cleaner disassembly pass (reading the FPU stack state directly rather than the decompiler's summary, the same limitation `weapon-view.md` section 6 hit for the sniper wheel's rotation) could settle it. Until then, implementers should treat "one shot, plus one more per whole recoil period already elapsed" as the model and confirm the exact rounding against the live oracle.
2. **Run-time confirmation of every number on this page** (recoil periods, the minigun's spin-up/down times and the full-speed gate, the reload animation length the retail Colt actually waits, the boring threshold, bring-up/put-down animation lengths): the oracle capture **T01-433** (weapon validation, already on the roadmap, split out of T01-038's original scope) is the place for it; nothing here was run.
3. **The boring-state threshold** (the exact constant `OnStep` compares the owner's "time since last fire" against) was read as a comparison but the constant's value was not resolved to a concrete number in this pass (the data section holds it as an unlabelled constant). Left to T01-433.
4. **The random jitter at full minigun spin** (`MoveWeaponParts`'s "already at target speed" branch) was read as a structure (a new random angle each step) but its amplitude and distribution constants were not resolved. Low priority: a purely cosmetic effect.
5. **Enemy puppets** firing their own weapons through this same base class (through `CShooterEntity`/AI puppet ownership rather than a player) were not examined here; `weapon-classes.md` rule 5 already notes that a non-player owner's `OnFire` always returns 0 in the base class, so enemy weapon entities (if any exist at run time) cannot complete this exact chain — how enemies actually attack is `brain-classes.md`/`puppet-attacks.md` territory, not this page.

## Test vectors

All from the retail install via `tools/re/weapon_timing_verify.py` for the data, and from the functions read above for the rules; **nothing run** on the original.

1. **Minigun, held fire, single player.** Press: `CallFireStart` → base enters `WS_SPIN_FIRING`; `CMiniGunWeaponEntity::CallFireStart` adds `SetSpinType(MGST_SPINUP)` and a click. The barrel accelerates from 0 to 550°/s over 0.5 s (`550 / 0.5` = 1,100 °/s²). Once it reaches 550°/s exactly, `OnStep` starts firing every `GetRecoilDuration()` = `lerp(0.035, 0, 0)` = **0.035 s** (fire power is always 0 for this non-charging weapon), each shot also setting spin type `MGST_SPIN` and fire type `MGFT_FIRE` once it lands. Release: `OnFireReleased` → `SetSpinType(MGST_SPINDOWN)`, `SetFireType(MGFT_NONE)`, a click; the barrel decelerates to 0 over `550 / (550/1.5)` = **1.5 s**.
