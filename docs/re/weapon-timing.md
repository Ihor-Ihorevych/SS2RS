## Summary

The weapon entity's state machine is 10 states (`weapon-classes.md` section 3). Every state-entry goes through one function, `SetState`, which starts that state's animation or sound and, for four states, schedules the entity's own think (`main-loop.md` section 7) to call the matching end-of-state callback after a duration that is **always an animation length** (bring-up, put-down, boring, the bomb's fuse) or **the animation length rescaled by a stored duration when one is given and otherwise the animation length** (reload) — **no state's duration is a bare data number**: `bwp_fMinRecoilDuration`/`bwp_fMaxRecoilDuration` set the *recoil* duration (by `lerp`, not by an animation), but bring-up, put-down, boring and (in the retail data) reload all wait for a model animation to finish. The repeat-fire loop while a trigger is held, and the "shots owed" catch-up after a long frame, are one function, `DoFiringsFromLastFireTime`, called from four places (the first press, a charge release, a scheduled auto-fire, and the per-step continuation while idle/boring or recoiling); it fires one shot immediately in the common case and **several in one call** when the trigger has been held since the last shot and the elapsed time covers two or more whole recoil periods: a long frame or a lag spike gives `trunc(elapsed / recoil duration)` shots (section 5). An **uncharged shot always passes fire power exactly 0.0** — read directly in `CallFireStart`, closing `weapon-classes.md` open question 9's second half.

2. **The firing chain is one function called from four places, through one entry point:**

   `CallFireStart` (fire button pressed, idle or boring, `CanFireFromWeaponNow` agrees) → **no flag**: `DoFiringsFromLastFireTime(0.0)` at once. **Charging flag**: `DoCharging()` only (no shot yet). **Spin-up flag**: `SetState(WS_SPIN_FIRING)` only (no shot yet; the first shot waits for the barrel to reach full speed, section 6).

   `FireReleasedInternal` (fire button released) → in `WS_CHARGING`: `DoFiringsFromLastFireTime(charge)` with `charge = clamp((now − charge start) / bwp_fChargingTime, 0, 1)`. In `WS_SPIN_FIRING`: `SetState(WS_IDLE)` (no final shot).

   `OnChargingEnd` (the scheduled auto-fire, `DoCharging`'s own think) → `DoFiringsFromLastFireTime(1.0)` — a held charge always auto-fires at full power.

   `OnStep` (every step, section 4) → while `WS_SPIN_FIRING` and fully spun up, or while `WS_RECOIL` on a non-charging weapon, once the time since the last shot reaches `GetRecoilDuration()` (`WS_RECOIL`: reaches or passes it, and the owner still wants to fire; `WS_SPIN_FIRING`: strictly passes it, with no owner check; section 5): `DoFiringsFromLastFireTime(0.0)`.

   `DoFiringsFromLastFireTime(power)` itself (section 5) calls `DoTheFiring(power)` one or more times; `DoTheFiring` re-checks `CanBeUsedForFiring()`, applies the **discrete-power rule** (zap gun only: a power below 1.0 becomes 0.0), stores the result as `en_fLastFirePower`, and calls the weapon's own `OnFire(power)` (the base pays ammunition and returns whether it could; a subclass launches only when it returns true). After the loop, `DoRecoil()` runs once, using the last shot's `en_fLastFirePower`, unless the loop was left by the bomb's fuse or by a failed shot (section 5).

3. **`SetState`, read in full.** Leaving `WS_BORING` notifies the owner; leaving `WS_CHARGING` stops the charging sound; entering `WS_CHARGING` starts it (from the weapon params' scheme sound, by `samPlaySchemeSound`); entering `WS_IDLE` blends (0.2 s) into the idle animation, looped; entering `WS_CANT_FIRE` tells the owner with this weapon's handle (the same call `OnStep`'s can't-fire branch repeats every step); entering `WS_BORING` clones the current pose (0.2 s) and plays the boring animation once — **but when there is no boring animation, `SetState` recurses into `SetState(WS_IDLE)` (which does play and does set the state member to 1) and then, after that call returns, unconditionally writes the state member back to 7** — so a weapon with no boring animation plays its idle pose once but is left reporting `WS_BORING` as its current state (a genuine reading of the code, not a guess; it means `IsRecoiling`/`CanBeChanged`-style state tests still see "boring" even though the idle animation ran); entering `WS_WAIT_FUSE_TO_BURN` plays a fixed fuse animation once. Every scheduled state (bring-up, put-down, boring, reload, fuse) uses the **same mechanism**: the weapon schedules its own think (`main-loop.md` section 7's `SetNextThink`-equivalent) for `(animation length, end-callback id)`; any later schedule on the same entity **replaces** the pending one (confirmed again here, as `projectile-launch.md` section 3.2 found for charging).

4. **`BringUp`/`PutDown`, read in full.** `PutDown(forced)`: refuses (does nothing) when not forced and `CanBeChanged()` is false (only `WS_WAIT_FUSE_TO_BURN` refuses, `weapon-classes.md` section 3); otherwise `SetState(WS_PUTTING_DOWN)`, blends (0.2 s) into the **same animation `BringUp` uses** (`weapon-classes.md`'s single `GetActivateAnim`, played in a different mode for putting down — there is no separate "deactivate" animation getter), schedules `OnWeaponPutDown` after its length. `OnWeaponPutDown` tells the owner, then **deletes the weapon entity outright** (`CEntity::Delete`) — switching away from a weapon does not hide it, it destroys the entity; the next time it is held, a fresh entity is created (`weapon-classes.md` point 2, now extended to weapon *switching*, not only pickup). `BringUp(0)` (normal): no blend (0.0 s), plays the activate animation forward, schedules `OnWeaponBroughtUp` after its length, which `SetState(WS_IDLE)`s. `BringUp(nonzero)` ("immediate"): clears to the idle animation at once (0.0 s blend) **without calling `SetState`** — the state member keeps whatever it was until a near-zero scheduled callback runs a moment later; this matches `weapon-classes.md` rule 4's "skip the animation and be idle" functionally (the idle animation does play at once) but the stored state is not `WS_IDLE` until that callback fires.

5. **`DoFiringsFromLastFireTime`, the catch-up after a long frame (re-read at instruction level by T01-435).** Reads the current `GetRecoilDuration()` (call it `d`, a 32-bit float). Then one of two paths:

   - **Forced single shot.** The weapon keeps a "fire exactly one next" flag. It is **set** by the constructor (a freshly brought-up weapon), by the base `OnFireReleased` (every trigger release) and by `DoReload`; and `DoFiringsFromLastFireTime` itself sets it on entry when the weapon has the **charging flag** (`WCF_CHARGE`; grenade launcher, cannon, zap gun). When the flag is set it is cleared and the shot count is **1**, without looking at the elapsed time and without the zero guards below. So a charging weapon always fires exactly one shot, and **so does the first press after any release, reload or bring-up**: the catch-up applies only to a trigger held continuously since the previous shot.
   - **Catch-up.** Otherwise `elapsed = (simNow() − en_tmLastFire)` is formed as an exact 64-bit tick difference, converted to seconds by dividing by 2^32 (the engine's 32.32 fixed-point time, `main-loop.md`) and **stored as a 32-bit float**. Both `d` and `elapsed` are guarded against being exactly 0.0 (an unordered compare, so a NaN passes): either one at 0 logs "Invalid recoil duration for weapon …" or "Invalid 'delta from last fire time' for weapon …" and **returns at once, firing nothing and not calling `DoRecoil()`**. Otherwise the shot count is

     **`shots = trunc(elapsed / d)`**

     computed as one x87 division of the two floats, whose result goes straight (without a store) into the compiler's standard float-to-integer conversion routine. That routine is the C cast: it does a round-to-nearest integer store, subtracts it back from the original value and **corrects by one toward zero** when the rounding went away from zero, so the net result is **truncation toward zero** (the T01-117 reading of this routine as "round-to-nearest" missed the correction step). There is **no `+1`**, no rounding to nearest and therefore no tie-breaking rule: an exact half (`elapsed / d = 2.5`) gives 2, like 2.4999 and 2.0. Since `elapsed` and `d` are both positive, `trunc` is `floor`. There is **no upper cap** either: only the loop exits below bound a burst.

   It then fires up to `shots` shots **in a tight loop within the same step** (a count of 0 or less skips the loop). Each iteration, in this order: `DoTheFiring(power)`; if the state is now `WS_WAIT_FUSE_TO_BURN` (the Serious Bomb) **return at once, without `DoRecoil()`**; if `DoTheFiring` returned false (no ammunition) enter `WS_CANT_FIRE` and **return at once, without `DoRecoil()`**; otherwise increment `en_ctShootsFiredFromRound`, set `en_tmLastFire = simNow()` (every shot of a burst gets the *same* stamp), and if `ShouldReload()` now holds, leave the loop early. `DoRecoil()` then runs exactly once — after the loop completed, after the `ShouldReload()` exit, or when the count was 0 (in which case a recoil period starts with no shot fired). This corrects T01-117's "`DoRecoil()` runs whatever ended the loop": the bomb's fuse and the out-of-ammunition exits skip it.

   **How it meets the callers.** `OnStep` calls the catch-up path only once `simNow() ≥ en_tmLastFire + D` (the `WS_RECOIL` branch, which also requires the owner still to want to fire) or `simNow() > en_tmLastFire + D` (the fully spun-up `WS_SPIN_FIRING` branch, which does not ask the owner), where `D` is `d × 2^32` stored as a float and then rounded to whole ticks. So at an `OnStep` call `elapsed ≥ d` and the count is at least 1 in practice. The `CallFireStart` path (idle or boring with the trigger held) uses the catch-up path only when the flag is clear, i.e. the trigger was never released since the last shot. Then an elapsed time below one period would give 0 shots plus a recoil period. A long one, for example ammunition restored while the trigger stayed held through `WS_CANT_FIRE`, would give a burst bounded only by ammunition and `ShouldReload()` (a consequence of the formula, not traced at run time).

   **Precision.** The division runs under whatever x87 precision control the process has set. Under single precision (what Direct3D 9 sets unless created with FPU preservation), the quotient is rounded to a 32-bit float before truncation, which is exactly "divide two `f32`s, truncate". Under extended precision an elapsed time that is an exact multiple of `d` in ticks can give a quotient a hair below the integer and so one shot fewer (minigun: 5 × `D` ticks gives 4.9999999 → 4). Which precision the original runs at was not established. **An implementer should compute `(elapsed_f32 / d_f32) as i32` in `f32`.** The differences are confined to elapsed times within about one float ulp of a multiple of `d`.

   Worked examples, using the two non-charging weapons whose recoil this page gives: the **Colt**, `d = 0.5` s (exact in binary), and the **minigun**, `d = 0.035` s (stored as the float 0.0350000001…, `D` = 150,323,856 ticks). Elapsed times are given in seconds, rounded to whole ticks first. The last column is the T01-117 reading, kept here to show where it was wrong.

6. **The minigun's spin states, read in full (`CMiniGunWeaponEntity`, `CBaseWeaponEntity::MoveWeaponParts`).** `en_fSpinningVelocityDeg` is a **linear ramp**, stepped every frame by `MoveWeaponParts` (called from `OnStep` whenever a part mover exists): while the owner wants to keep firing this weapon, it rises toward `bwp_fSpinSpeed` at a rate of `bwp_fSpinSpeed / bwp_fSpinUpTime` per second (clamped at the target); once it has reached the target exactly, the spinning part's angle instead receives a small random jitter each step (a vibration at full spin, read but not measured); while the owner does not want to fire, it falls toward 0 at `bwp_fSpinSpeed / bwp_fSpinDownTime` per second. `CallFireStart` (`CMiniGunWeaponEntity` override): calls the base (which, by rule 2's spin-up branch, enters `WS_SPIN_FIRING`), then `SetSpinType(MGST_SPINUP)` unless already `MGST_SPIN`, and plays a one-shot trigger-click sound on its own channel. `OnFireReleased`: `SetSpinType(MGST_SPINDOWN)`, `SetFireType(MGFT_NONE)`, another trigger click. `SetSpinType`/`SetFireType` each own a **looping** sound channel (spin-up/spin/spin-down for the barrel; fire/click for the muzzle) that only changes when the requested type differs from the current one; `OnStep`'s `WS_SPIN_FIRING` branch fires the first (and every later) bullet **only once `en_fSpinningVelocityDeg` equals `bwp_fSpinSpeed` exactly** (full spin), at the same `GetRecoilDuration()` cadence every other weapon uses; `OnFire` (per `weapon-classes.md` section 6.2) is where the spin type is driven to `MGST_SPIN` and the fire type to `MGFT_FIRE` once a bullet actually leaves — so the "fully spinning, fully firing" looping sounds only start once the barrel has reached speed and a shot has gone through, not as soon as the trigger is pulled. Numbers (section 2 of `weapon_timing_verify.py`): minigun spin-up 0.5 s, spin-down 1.5 s, speed 550°/s (single player; 500°/s deathmatch); circular saw spin-up 0.6 s, spin-down 0.8 s, speed 500°/s (both files; the saw's own cutting behaviour is T01-120, not this page). Every other weapon's file carries the **same generic 0.5/3.0/500 spin defaults** (unused data: only the binary's charging/spin-up flags gate which weapon reads them; grenade launcher and plasma rifle are the two exceptions with 0/0/0, matching `weapon-classes.md`'s reading of `bwp_fSpinSpeed`).

7. **The sniper's zoom steps are `weapon-view.md` section 6, not repeated here**: the alternative-fire toggle, the `r = clamp((now − start) / fullZoomingTime, 0, 1)` ramp and the field-of-view multiplier it drives, with the single-player and deathmatch numbers and test vectors.

8. **`OnStep`'s boring threshold (re-read at instruction level by T01-435).** In the idle/boring branch of `OnStep`, the steps run in this order. First, if `CanBeUsedForFiring()` fails, enter `WS_CANT_FIRE`. Then, if the owner wants to fire, call `CallFireStart`. Then the state is read again: in `WS_CANT_FIRE` the owner is told (as every step); **only if the state is still `WS_IDLE`** (not already `WS_BORING`, so a boring weapon is not re-triggered by this test) does the boring test run. The test forms `idle = (simNow() − owner's last-fire time)`, an exact 64-bit tick difference divided by 2^32 and kept on the FPU (not stored as a float). It compares that against the literal 32-bit float constant **5.0** and enters `WS_BORING` (`SetState(7)`) when **`idle > 5.0` s, strictly**: exactly 5.0 s does not qualify. The constant is the same for every weapon and every game mode: it is a code constant, not a weapon-params member. Precision: under single-precision x87 control an `idle` within half a float ulp above 5.0 (about 2.4e-7 s) rounds to 5.0 and fails the test. That is negligible next to any simulation step, but it is why an implementer comparing `idle_f32 > 5.0_f32` matches the original best.

   Worked examples. The threshold does not depend on the weapon, so the Colt (0.5 s recoil) and the minigun (0.035 s) behave alike. The owner last fired at t = 10.0 s, the weapon went `WS_RECOIL` → `WS_IDLE` after one recoil period (t = 10.5 s or 10.035 s), and the trigger stays released. An `OnStep` at t = 14.9999 s (idle 4.9999): stays idle. At exactly t = 15.0 s (idle 5.0): stays idle. At t = 15.0001 s (idle 5.0001): enters `WS_BORING`. With a fixed 0.1 s step whose ticks land exactly on 15.0, boring therefore starts on the **15.1 s** step, not the 15.0 s one. The recoil period does not move the threshold: it counts from the owner's last fire, not from the return to idle.

## Layout / rules

### 1. The ten states, as a diagram in prose

Every weapon entity starts `WS_IDLE` once brought up. From **`WS_IDLE`** or **`WS_BORING`**, pressing fire calls `CallFireStart`, which branches three ways by the weapon's own flags (at most one of the two is set): **no flag** → fire now, enter `WS_RECOIL`; **charging flag** → enter `WS_CHARGING`; **spin-up flag** → enter `WS_SPIN_FIRING`. From **`WS_RECOIL`**, once `GetRecoilDuration()` has passed, `OnRecoilEnd` runs: if the weapon can no longer be used (no ammunition) → `WS_CANT_FIRE`; else if a reload is now due → `DoReload` → `WS_RELOAD`; else → `WS_IDLE` (and, while the owner still wants to fire a non-charging weapon, `OnStep` fires the next shot once the recoil period elapses and re-enters `WS_RECOIL`, without a visit to `WS_IDLE` in between — the state only becomes externally visible as idle when the trigger is released or the next `OnStep` tick happens to observe it). From **`WS_IDLE`**, once the owner has not fired for more than 5.0 s, `OnStep` enters `WS_BORING`; firing again from `WS_BORING` plays a quick idle-pose interrupt before proceeding exactly as from `WS_IDLE`. From **`WS_CHARGING`**: releasing the trigger (`FireReleasedInternal`) fires at the built-up charge and enters `WS_RECOIL`; holding past `bwp_fChargingTime + bwp_fChargingAutoFireTime` auto-fires at full power (`OnChargingEnd`) and enters `WS_RECOIL`. From **`WS_SPIN_FIRING`**: releasing the trigger returns to `WS_IDLE` directly (no recoil state); while held, `OnStep` fires repeatedly at the recoil cadence once fully spun up, staying in `WS_SPIN_FIRING`. **`WS_CANT_FIRE`** is left only by `CanBeUsedForFiring()` becoming true again (checked every step while the weapon would otherwise be idle or boring) — then `CallFireStart` can run again. **`WS_RELOAD`** ends (`OnWeaponReloaded`) in `WS_IDLE` after the reload animation. Switching away from the current weapon calls `PutDown`, entering `WS_PUTTING_DOWN` from any state except `WS_WAIT_FUSE_TO_BURN` (which refuses `CanBeChanged`); at the end of that animation the entity **deletes itself**. Switching to a weapon creates a fresh entity, which calls `BringUp`, entering `WS_BRINGING_UP` (or going idle at once for an "immediate" bring-up) and ending in `WS_IDLE`. The Serious Bomb's `OnFire` enters `WS_WAIT_FUSE_TO_BURN` instead of `WS_RECOIL`; its own `Explode` (not the base's) runs at the end of the fuse (`weapon-classes.md` rule 9).

### 2. Duration sources, summarised

| Step | Stored data member | Or: computed from |
|---|---|---|
| Recoil | `bwp_fMinRecoilDuration`, `bwp_fMaxRecoilDuration` (lerp by fire power) | the recoil animation's length, when the minimum is ≤ 0 on a non-scalable weapon |
| Charging | `bwp_fChargingTime`, `bwp_fChargingAutoFireTime` (sum, for the auto-fire schedule) | — (both are stored members; `projectile-launch.md`) |
| Bring-up / put-down | none | the activate animation's length (always) |
| Boring | none | the boring animation's length, or none (immediate re-idle, with the state-member quirk of section 3) |
| Reload | `bwp_fReloadDuration` (rescales the animation's **playback speed**, not its own value, so the schedule still waits for the *data-driven* target duration when it is positive) | the reload animation's length, unscaled, whenever `bwp_fReloadDuration` is 0 (every retail weapon that actually reloads) |
| Fuse (Serious Bomb) | none | the fuse animation's length |
| Spin-up / spin-down | `bwp_fSpinUpTime`, `bwp_fSpinDownTime` (rate = `bwp_fSpinSpeed` / each) | — |
| Double-weapon fire delay | `bwp_fDoubleWeaponFireDelay` | — (`weapon-view.md` section 5) |
| Sniper zoom ramp | `swp_fFullZoomingTime` | — (`weapon-view.md` section 6) |

### 3. The firing cadence rule (summary of Summary points 2 and 5)

A held trigger fires at the weapon's recoil cadence: shot → `WS_RECOIL` for `GetRecoilDuration()` (which depends on the *last* shot's fire power, so a charging weapon's cadence is itself charge-dependent through the recoil lerp) → next shot. `DoFiringsFromLastFireTime` is the single point that both fires "now" and catches up: called with elapsed time since the last shot of two or more whole recoil periods while the trigger stayed held (a step longer than `sim_fStepMax`'s usual 0.1 s ceiling cannot by itself cause this, since `main-loop.md` caps every step at 0.1 s; a catch-up instead happens when a weapon's own think was delayed — a reload, a charge, or a run of several frames each shorter than `sim_fStepMin` followed by one that is not, `main-loop.md` test vector 7 — or when the recoil duration itself is very short relative to the step, e.g. the minigun's 0.035 s recoil against a 0.1 s step), it fires `trunc(elapsed / recoil duration)` shots in that single call (section 5), all stamped with the same `simNow()`.

### 4. The fire power of an uncharged shot

**0.0**, read directly: `CallFireStart`'s non-charging, non-spin-up branch calls `DoFiringsFromLastFireTime(0.0)` with the literal constant. This closes the second half of `weapon-classes.md` open question 9 (the first half, the cheat-set bits, is unrelated and stays open there). It cross-checks `weapons-tables.md`/`weapon-classes.md` test vector 3's "assumed" fire power 0 for an uncharged Colt shot: no longer an assumption.

## Invariants

1. Every scheduled state-end callback (bring-up, put-down, boring, reload, fuse, the auto-fire's `OnChargingEnd`) rides the same single-pending-think mechanism (`main-loop.md` section 7); scheduling a new one replaces whatever was pending for that entity.
2. `DoFiringsFromLastFireTime` always fires exactly one shot for a charging weapon (grenade launcher, cannon, zap gun) and also exactly one for the first shot after a trigger release, a reload or a bring-up. While the trigger stays held it fires `trunc(elapsed / GetRecoilDuration())` shots, truncated toward zero with no `+1` and no rounding to nearest; this is at least 1 at every `OnStep` call, since those wait for a full period. It never fires more than fits before `ShouldReload()` or a failed shot stops the loop.
3. `GetRecoilDuration()` is the recoil animation's length whenever `bwp_fMinRecoilDuration ≤ 0` on a weapon that is not both charging-flagged and "scalable"; otherwise it is the lerp (checked against `weapon-classes.md` rule 2 and section 4.1's data).
4. The reload rescale (`bwp_fReloadDuration`) never fires in the retail data (the only reloading weapon, the Colt, has it 0; `tools/re/weapon_timing_verify.py`).
5. Putting a weapon down always ends by deleting its entity; bringing one up always creates (or recreates) one.
6. An uncharged shot's fire power is the literal constant 0.0, read in `CallFireStart`.
7. A weapon enters `WS_BORING` from `WS_IDLE` only when the owner's time since its last fire is strictly greater than 5.0 s, for every weapon and game mode.

## Test vectors

All from the retail install via `tools/re/weapon_timing_verify.py` for the data, and from the functions read above for the rules; **nothing run** on the original.

1. **Minigun, held fire, single player.** Press: `CallFireStart` → base enters `WS_SPIN_FIRING`; `CMiniGunWeaponEntity::CallFireStart` adds `SetSpinType(MGST_SPINUP)` and a click. The barrel accelerates from 0 to 550°/s over 0.5 s (`550 / 0.5` = 1,100 °/s²). Once it reaches 550°/s exactly, `OnStep` starts firing every `GetRecoilDuration()` = `lerp(0.035, 0, 0)` = **0.035 s** (fire power is always 0 for this non-charging weapon), each shot also setting spin type `MGST_SPIN` and fire type `MGFT_FIRE` once it lands. Release: `OnFireReleased` → `SetSpinType(MGST_SPINDOWN)`, `SetFireType(MGFT_NONE)`, a click; the barrel decelerates to 0 over `550 / (550/1.5)` = **1.5 s**.
2. **Grenade launcher, tapped at 0.25 s, single player.** `CallFireStart` enters `WS_CHARGING` via `DoCharging` (which schedules `OnChargingEnd` at `0.5 + 0 = 0.5` s). Released at 0.25 s: `FireReleasedInternal` computes `charge = clamp(0.25 / 0.5, 0, 1) = 0.5`, calls `DoFiringsFromLastFireTime(0.5)` → exactly one shot (charging-flag rule) → `DoTheFiring(0.5)` → `OnFire(0.5)`; recoil duration `lerp(0.2, 0.5, 0.5) = 0.35` s (matches `projectile-launch.md` test vector 1).
3. **Colt, six shots then a seventh, single player.** Each shot: `DoTheFiring(0.0)` (no charging/spin-up/discrete flags) → `OnFire` → `en_ctShootsFiredFromRound` 1, 2, …, 6; `ShouldReload()` becomes true at 6 (`bwp_ctFiresToReload` = 6); `OnRecoilEnd` after the sixth shot's 0.5 s recoil sees `ShouldReload()` true and calls `DoReload()` instead of going idle: `en_tmLastReload` = now, `WS_RELOAD`, `en_ctShootsFiredFromRound` reset to 0, the next `DoFiringsFromLastFireTime` call forced to one shot, the reload animation plays at its own natural length (the Colt's `bwp_fReloadDuration` is 0, so no rescale), `OnWeaponReloaded` → `WS_IDLE`.
4. **A long frame on the minigun (catch-up).** Suppose the weapon's last shot was 0.22 s ago (about 6.3 recoil periods of 0.035 s) when `OnStep`'s recoil branch next calls `DoFiringsFromLastFireTime(0.0)`: by the rule of section 5, `trunc(0.22 / 0.035) = trunc(6.2857) = 6` shots fire within that one step (T01-117's reading gave 7), each consuming one unit of ammunition and all stamped with the same `simNow()`, before `DoRecoil()` starts the next 0.035 s wait. If the ammunition runs out partway, the loop enters `WS_CANT_FIRE` and returns without `DoRecoil()`. On the Colt, a burst stops early at the shot that makes `ShouldReload()` true, and `DoRecoil()` still runs.
5. **Switching from the Colt to the Uzi.** `PutDown(0)` on the Colt (not forced, `CanBeChanged()` true outside `WS_WAIT_FUSE_TO_BURN`): `WS_PUTTING_DOWN`, blends 0.2 s into the activate animation played backward, schedules `OnWeaponPutDown` at that animation's length; when it runs, the owner is told and the Colt's entity is deleted. A new `CUziWeaponEntity` is created and `BringUp(0)` called on it: `WS_BRINGING_UP`, no blend, the activate animation plays forward, `OnWeaponBroughtUp` after its length sets `WS_IDLE`.
6. **Sniper zoom steps:** `weapon-view.md` test vector 5 (0 s → ×0.5, 0.4 s → ×0.375, 0.8 s and later → ×0.25 in single player).
