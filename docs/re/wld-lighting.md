## Summary

Lighting in a world has two layers. **Dynamic lights** are entities (`CPointLightEntity`, `CDirectionalLightEntity`) with a runtime light source and an editor property record; all light sources are listed in the rendering domain and in the **light grid**. **Static lighting is baked into textures**: every lit model instance carries a **`CTextureOvenShaderModifier`** in its modifier list that overrides one texture slot of the model's material with a **lightmap texture stored inside the world file**, together with a UV map id; a bake record and an ambient mask are kept in the extra section (editor data). Flares (`SFlareEntity`) attach a flare renderable to a model next to a light.

## Light entities

```
CPointLightEntity                      (class code 18)
  .2   -> CPointLightSource            the runtime light (an aspect, owner null)
  .3   -> parent entity or null        4,048 point lights have a parent: a CStaticModelEntity; 2 more have a CGenericItemEntity
  .4   int                             (as the entity serial in wld-root.md)
CDirectionalLightEntity                (class code 17)
  .2   -> CDirectionalLightSource
  .3   -> null in all 89
CPointLightProperties / CDirectionalLightProperties   (extra records, one per entity, see wld-root.md)
```

The light source is an **aspect**. It is a **root aspect exactly when the light has no parent entity** (11,438 of 11,438); a light with a parent entity is a child of one of the parent's aspects (the parent's renderable): its parent aspect belongs to the parent entity in 4,050 of 4,050 cases and `CEntityProperties.5` is the parent's property record (4,050 of 4,050). Placement follows the rule of `wld-geometry.md`: for a light **with** a parent the property placement is the source's local placement (4,048 of 4,050); for a light without one it is the source's world placement (7,216 of the 7,388 lights; the remaining 172 differ and are not analysed).

The **editor marker** is a `CEditorPrimitiveRenderable` that is a child aspect of the light source (11,349 under point lights, 89 under directional lights). Directional lights also carry a `CShadowBufferBaker` child (89) and a `CShadowBuffer` reference (record `.12`, source `.15`, for the lights with shadows).

## Baked lightmaps

The chain, for each lit instance of a model (`wld-geometry.md`):

```
CModelInstance.4          -> CShaderModifierList (main section)
  CShaderModifierList.1   list of modifiers; one of them is
CTextureOvenShaderModifier  (main section)
  CShaderModifier.1       EPlatform
  .1, .2                  int, int: two shader parameter ids (the texture and the UV map slot being overridden)
  .4                      CShaderArgValTexture -> the LIGHTMAP TEXTURE (a CStaticTexture in the main section, exposed)
  .3                      CShaderArgValUVMap   -> the UV map id to use for it
  .6                      -> CTextureBakerLightMap (extra section)
CTextureBakerLightMap     (extra section, editor data)
  .9                      -> CAmbientMaskCache (extra section)
CAmbientMaskCache
  .1, .2                  width, height
  .3                      the mask bytes (width x height, one byte per cell)
```

- **One lightmap per instance.** 18,392 instances have oven modifiers (18,105 exactly one, the others two or more); every lightmap texture is used by exactly one instance.
- **Texture.** The lightmap is a `CStaticTexture` object stored **in the world file** (18,679). The formats are DXT1 (17,299), 24-bit (1,123), 32-bit (251), and a few others; sizes are powers of two from 16 to 2,048 (64: 7,601, 128: 7,185, 256: 2,287, 32: 906, 512: 452, 1,024: 129, 16: 111, 2,048: 5), square in 18,265 of 18,676 cases. The `TexFlags` of the lightmaps are `0x71` (15,812), `0x31` (2,325), `0x30` (525), `0x70` (13) and `0x20` (1): **bit `0x10` is set on 18,675 of 18,676**, while `tex.md` found it on only three standalone textures (`0x71` twice, `0x60` once); so `0x10` marks a generated/baked texture (T01-054). The wrap modes are `0x51`/`0x51` (14,625), `0x50`/`0x50` (4,050) and `0x52`/`0x52` (1).
- **Editor copy.** For each main-section oven modifier there is one oven modifier in the extra section (18,680 against 18,679; equal in 58 of 59 worlds); the copies are referred to by the property records of the entities that were baked: `CStaticModelProperties` (18,481), `SDoorProperties` (115) and `SPropProperties` (84).
- **Bake record and mask.** The bake record lives only in the extra section: 18,495 of 18,679 modifiers point to one; 181 records have no member `.9`. Where present, the **ambient mask is half the lightmap size** (width and height halved, one byte per cell) for 16,589 of the lightmaps checked; the others have a different size. The bake record's parameters are nearly constant: two profiles in the sample of four worlds (`.10` = 10.0 with `.11` = 2 and `.12` = 20 in 722 records, 25.0 / 12 / 36 in 52); `.2`, `.7`, `.14` = 0.5, `.13` = 0.3, `.20` = 0.4. They are editor settings.
- **UV map id (T01-406: not a mesh id, not per-instance, not a stored stream — a per-world constant; where it is consumed stays open).** The id in `.3` is **not** one of the model's mesh UV ids: not just in a four-world sample, but checked directly against the actually-referenced mesh of every lit instance in the 8 smallest worlds (732 instances; the mesh check resolves the instance's external `.mdl` and scans **every** UV slot of **every** surface of **every** LOD, not only the slots a material uses) — **0 of 732** have their lightmap id anywhere in their own mesh's UV id list. This rules out "a mesh UV stream under a different id" directly, not just statistically.

  **T01-406 also found that the id is not per-instance at all: it is (almost always) a single constant for the whole world.** Over all 59 worlds, grouping each world's oven modifiers by UV id: **31 of 59 worlds use exactly one id for every one of their lit instances**, 25 use two, 2 use three (`tools/re/wld_lightmap_uv_verify.py`); **18,468 of 18,679 modifiers (99 %)** carry their world's single most common id, and that id is **55 of 59 worlds'** only id. The two overridden shader-parameter ids (`.1`/`.2`) follow the same pattern — a handful of large, distinct pairs (e.g. `(378, 379)`, `(320, 322)`, `(23, 24)` — some consecutive, some not), each reused 700–1,700 times, consistent with one pair per world (or bake session), not per instance. So the id cannot be a per-instance generated unwrap, nor an index into a per-instance or per-world array keyed by instance (a shared id would collide every mesh against every other mesh in the world); the earlier text's "probably generated for the instance" is **superseded** by this finding.

  **Ruled out, not just "not found": a stored UV stream in the oven-modifier chain, and a remap/layout table.** The full oven-modifier → bake-record (`CTextureBakerLightMap`, all 12 members dumped for the test vector) → ambient-mask chain, and the extra-section property-record copy (`CStaticModelProperties`), hold only scalar bake-tool settings (floats, small ints) and the ambient-mask byte array — no float array of the right shape for UV coordinates anywhere reachable from the modifier. Classes named for UV maps in `classes-catalog.md` (`CUVMapLayout`, `CForegroundUVMapList`, `CTexCoordVertexMap`, `CUVMapViewCustomData`) are rare and do not track the oven-modifier count: `CUVMapLayout` and `CForegroundUVMapList` occur in **0 of the 59 worlds**; `CTexCoordVertexMap` in 41 of 59 but 1 to 69 per world, uncorrelated with that world's (constant) lightmap count; all four are strings found only in the EditKit modules per `classes-catalog.md`, not in `Engine.dll`/`Core.dll`/`Sam2Game.dll` — editor mesh-import bookkeeping, not the universal mechanism.

  **The mechanism that pushes the override is confirmed (T01-061, re-confirmed T01-406) to run in the shipped game, not only the editor.** `CTextureOvenShaderModifier::ApplyModifications` (`Engine.dll`, read in full again) calls the generic `shaModifyValue` override-stack push (`mtr.md`) **twice**, once for the parameter id paired with the texture wrapper and once for the id paired with the UV-map wrapper, each time passing the engine's own "invalid identifier" as the search key — so each push always creates a **fresh** stack entry; `ApplyModifications` itself takes no placement or geometry argument, so it cannot be computing or generating UV coordinates. **Newly traced (T01-406):** this virtual call is driven by `CModelRenderable::Bake()`, which builds a placement matrix and calls the free function `mdlBakeModel(CModelInstance*, const Matrix34f&)` — a **different, shipped** function from the modifier's own `Bake`; it walks the instance's shader-modifier list and invokes each modifier's virtual apply. So the override genuinely happens every time a lit renderable bakes in the real game (this refines, not contradicts, the existing finding: it is `CTextureOvenShaderModifier::Bake` — the pixel-painting function below, confirmed **editor-only** — that never runs in the shipped game, not the modifier's `ApplyModifications`/`CModelRenderable::Bake` path).

  **Where the overridden value is actually read back and matched to a vertex stream was not found in `Engine.dll`.** `shaExecutePreset` (read in full) dispatches each shader config straight to the shader's `Exec` with an already-built `CShaderArgs`; it contains no mesh, UV or stream-matching code, so the general rule for ordinary materials ("match the UV map id against the surface's declared ids", `mtr.md`) is not implemented there — it must happen earlier, while a surface's `CShaderArgs`/vertex declaration is assembled, a step this reading did not locate by name (`CModelRenderable::RenderObject` → `mdlRenderModel` → unnamed callees). The surface's **own** material (checked on the mesh of the test vector's model) never uses member numbers `12`/`13` for its own texture/UV-map argument pair (it uses `.10`/`.11`, `.20`/`.21`, …, the per-class slot numbers of `mtr.md`), so the oven modifier's two overridden ids are not simply "the diffuse slot's own numbers": they come from some other, evidently shared/global id space. `CBaseTexture::IsLightMap` / `CTextureModifier::IsLightMap` (both read in full) exist as a predicate on the texture (matching the `TexFlags 0x10` bit already found in the data) but this reading found no caller of either by name in `Engine.dll`, `Core.dll`, `Sam2Game.dll` or `GfxD3D.dll` (both are virtual; a caller through the vtable would not show up in a name search). No unwrap, planar- or box-projection, or "generate UV" function was found among the named functions of `Engine.dll` either (`mdlGetSurfaceUVMaps`/`rmGetUVMaps` only **enumerate** a mesh's existing declared ids, for example for an editor UI; they do not create one).

  **T01-406's hypothesis ("samples the instance's own base/diffuse UV") is tested and superseded by T01-407, against the data.** The reasoning that the runtime special-cases a texture flagged `IsLightMap()` and samples it through an already-bound channel still holds; which channel does not. A lightmap unwrap has a property an ordinary (tiling) UV channel does not: it is **unique and non-overlapping inside [0, 1]** so that each texel lights one spot of the instance and no two charts collide. `tools/re/wld_lightmap_stream_verify.py` resolves every lit instance's mesh (the `.mdl`/`.bmf` chain, now also following one level of external `.bmf` reference) and measures, for every UV stream of the mesh's first PC-eligible LOD (`bmf.md` surface members 12/14, `EPlatform` bit 0): the min/max of u and v; whether the stream is entirely inside [0, 1] (small epsilon); the fraction of its rasterized triangle area that overlaps another triangle (a grid test sized to bound the work, 256x256 for a typical surface, coarser for very dense meshes); and, separately, whether the id is ever used by the surface's own material (`mtr.md`, any texture group, any shader class) -- the discriminator against the "base/diffuse" hypothesis. A stream in [0, 1] with at most 2 percent overlapping rasterized area is called a *candidate*.

  Over all 59 worlds, **18,641 of the 18,679 oven-modifier instances resolve to an external mesh** (38 do not: an embedded model configuration, the same gap T01-406 hit). Of those, **16,147 (86.6 percent) have exactly one candidate stream**; at the level of distinct meshes (many instances share one `.mdl`), **1,645 of 1,935 (85.0 percent)** do (135 meshes have none, 147 have two, 8 have three or four -- multiple UV channels that each happen to pack without overlap, for example a small quad). **The candidate is overwhelmingly the mesh's first declared UV slot** (surface member 12/14, index 0): 87.0 percent of instances (14,044 of 16,147) and 90.0 percent of distinct meshes (1,482 of 1,645) with exactly one candidate have it there; slot 1 accounts for most of the rest (11.3 percent / 8.3 percent).

  **Crucially, the candidate is usually not the id the surface's own material uses for any of its texture groups** -- the opposite of the "base/diffuse channel" hypothesis: **83.0 percent of instances (13,404 of 16,147) and 74.7 percent of distinct meshes (1,229 of 1,645)** with exactly one candidate have it unreferenced by their own material. On the test vector itself, `Fence.mdl`'s one surface declares UV ids 3 and 4 (`bmf.md` member 12); its material's diffuse and detail texture groups (`CShadeShaderArgs.10`/`.11` and `.20`/`.21`) both use id 4, with a UV scale of 1.5 (a tiling channel, consistent with not being a candidate: id 4's measured range runs well outside [0, 1]), while id 3 (slot 0) is the one entirely inside [0, 1] and non-overlapping, and is not referenced anywhere in the material. So the leading data-supported rule is: **sample the lightmap through a dedicated UV channel, not materially used for anything else -- in the large majority of cases the mesh's first declared UV slot -- rather than the instance's base/diffuse channel.**

  **A visual check corroborates it.** `--texels` rasterizes a mesh's triangles under the candidate stream into its lightmap texture's own texel grid and reports what fraction of "lit" texels fall inside a triangle. A texel is "lit" when it departs from a near-neutral grey by more than a small tolerance: inspecting several lightmaps' colour histograms found the gaps between charts decode to that grey, **not to black** -- the mode colour of the test vector's own lightmap sits a few DXT1-quantization steps off an even r=g=b=127 fill. For the test vector (`dm_stadium.wld` instance #2435, `Fence.mdl`, 128x128 lightmap): 44.7 percent of texels are lit, and 53.7 percent of those fall inside a candidate-stream triangle (the DXT1 block size, 4x4 texels, is a large fraction of this small, thin-chart texture, which blurs chart edges and depresses the figure). For three more instances in the same world -- bigger architecture pieces with their own full-size lightmaps (`Arena.mdl`/`Arena_02.mdl`, instances #2438/#2441, 512x512) -- 98.4 percent / 94.0 percent of texels are lit and 91.9 percent / 90.2 percent of those fall inside a triangle, much closer to "nearly all".

  **This was not pinned to an exact engine instruction.** `CModelRenderable::RenderObject` (`Engine.dll`, read in full) only builds a placement matrix and calls `mdlRenderModel`, confirming T01-406's call path; `mdlRenderModel` (read in full) itself does the same work T01-406 already described up to `shaExecutePreset`, and, on the ordinary (non-destruction-editing) path, calls an unnamed static helper that loops over a per-frame queued-draw list and calls a second unnamed helper per entry -- this pair, not `shaExecutePreset`, is where a surface's actual vertex streams would be bound for the GPU, and neither was decompiled by name or traced further in this task; `Shaders.dll` (T01-020) is still not decompiled for this project. So **confidence is high that this stream behaves like a lightmap unwrap and is usually not the base/diffuse channel** (a large, cross-checked, data-only result), but **medium that it is the exact channel the shipped renderer reads** (not directly observed in code).

  **T01-408 resolved the two unnamed helpers, decompiled `Shaders.dll`, and found a vtable caller of `IsLightMap` — but this refutes a literal "verbatim" reading rather than confirming it.** The per-frame queued-draw loop and its per-entry helper (both now read in full) do the following, per surface, every frame: push the mesh's and the surface's own shader-modifier lists (this is where `CTextureOvenShaderModifier::ApplyModifications` actually fires for a draw, confirming T01-406's trace lands here); lock the mesh's buffers; run GPU skinning where applicable; **bind every one of the surface's own declared vertex streams (positions, normal, colours, and each of its own declared UV slots) into a fixed-size per-draw table, keyed by each stream's own id** (so a UV slot's id travels with it into the table, it is not simply "slot 0, 1, 2…" by raw position); call into `shaExecutePreset` (confirming T01-406/407's call path exactly); then unlock the buffers. **The matching step T01-406 found missing from `shaExecutePreset` itself is implemented by a separate, generic pair of functions** (also read in full) that every shader class' own `Exec` calls (confirmed for `CShadeShader::Exec`, `Shaders.dll`, read in full): one scans that per-draw table for an entry whose own id equals a requested UV-map id and returns which bound stream (if any) carries it; the other does the reverse (publishes a stream into the table under a given id). So **the general rule `mtr.md` already documents for ordinary materials — match the UV-map id against the surface's own declared ids, not its slot position — is real engine behaviour, implemented once, generically, and shared by every shader class**, not something `shaExecutePreset` special-cases and not something that reads back "whatever is in slot 0" regardless of id. This directly contradicts a literal "read the first declared slot verbatim" instruction: no code path was found that binds a UV argument by position once its id fails to match. The puzzle T01-406 already proved (the oven modifier's overridden id is *never* one of the mesh's own declared ids) therefore stays unresolved at the level of an identified instruction: by this generic matching rule alone, the override's id could never resolve to a real stream, which is inconsistent with lightmaps visibly rendering correctly. Tracing the surface's own declared-stream table further shows it is built from **two separate, equally-sized groups of id'd slots**, only the first of which was checked against this id (the one `bmf.md` member 12 describes and T01-406 already scanned exhaustively); the second group's own id source was not identified in this task and may be where the override's id actually resolves — **left open, see the follow-up task**. **Confidence: medium** (read from the binary, not observed at runtime).

  **T01-414 identifies the second group's own id source, rules it out by data, and traces the override one level deeper — but still cannot pin down the exact instruction that makes a lightmapped draw sample a real stream.** Re-reading the per-entry queued-draw helper's own layout against a fresh read of `CRenderMeshSurface`'s compiled object layout (`Engine.dll`, its copy-constructor and assignment operator, both read in full) shows the second, equally-sized group of id'd slots T01-408 left open is built from the exact byte range that holds `bmf.md` member `.13` ("eight color-map identifiers") paired with its own element-path array (member `.15`) — the structural twin of the already-checked `.12`/`.14` UV pair, one step further down the same surface object. `tools/re/wld_lightmap_colormap_verify.py` (read-only, `SS2_DATA_DIR`; about 2 minutes) checks this directly, not on `bmf.md`'s general 76-file sample but on the meshes **actually referenced by lit world instances** (the same `.mdl`/`.bmf` resolution as T01-406/407/408), over all 59 worlds: of **18,641 resolved lit instances, 0 have a single non-empty `.13` slot anywhere on their mesh**, and the oven modifier's own UV id (`.3`) is accordingly found in that array 0 times. So the second group is real (confirmed structurally) but, for every lit instance in the shipped game, **always empty** — it cannot be where the override's id resolves either; hypothesis "another mesh-declared array" from the follow-up is ruled out by data, not merely unconfirmed.

  Tracing the override one level further (`Engine.dll`, read in full: `CTextureOvenShaderModifier::ApplyModifications` itself, confirming it does exactly two `shaModifyValue` calls and nothing else — no call to the per-draw table's own "publish" function; and `CShaderArgs::ReadModifiers`, not read by any prior task) shows *where* the pushed override is actually consumed: every shader-argument class carries its own compiled table of per-member metadata (used by the save/load and editor reflection machinery), and each entry names a numeric id distinct from the file's own CTSEMETA member numbers (`mtr.md`'s `.10`/`.11`/`.20`/`.21`… numbering) — a separate, compiled-in id space of the argument *class* itself. `ReadModifiers` walks this table (for the class and every base class) and, for each declared member, calls `shaReadValue` with that member's own id; if the current override-stack frame holds a value under that same id (pushed by `shaModifyValue`, confirming T01-406/T01-059's reading), `shaReadValue` overwrites the member **in place**, directly in the live `CShaderArgs` copy the shader class's `Exec` is about to read. So the oven modifier's two overridden ids (`.1`/`.2`) are entries in *this* id space, not mesh-channel ids or CTSEMETA member numbers; and the override does not inject a new row into the `shaGetChannel`/`shaSetChannel` per-draw table at all — it substitutes a plain integer into one `CShaderArgs` member (the UV-map-id argument of whichever texture group `.2` names), then lets the *same* generic, by-id stream lookup every ordinary material's UV id already goes through run against that substituted value. Since that value is confirmed (T01-406) never one of the mesh's declared UV ids and (this task) never one of its colour-map ids either, `shaGetChannel` — read again, in full, for this task — has no matching entry in **either** group and, by its own code, returns channel 0 (the surface's **position** stream) on a total miss; this task found no other call site that would publish a different entry under the override's id before the shader's `Exec` runs. A position stream bound as a 2-component texture coordinate is not a plausible way to reproduce a baked unwrap, so this is not a confirmed resolution — it is the same open puzzle T01-408 already found (**inconsistent with lightmaps visibly rendering correctly**), now narrowed to a precise, reproducible dead end: both of the two groups a lightmap's overridden UV id could resolve against are checked and empty, and the fallback code path they feed is identified and does not plausibly explain the shipped result. **Confidence: medium** (read from the binary, not observed at runtime); **the exact instruction stays open, see the follow-up task.**

  **The practical data rule for a loader (T01-414), extending T01-407's and verified over every lit instance that resolves):** since no engine-level resolution was found, keep the existing "unwrap-like" stream test (a UV stream inside [0, 1] with at most 2 percent rasterized overlap) as the primary rule, and add two deterministic tie-breaks for its residual cases, both verified with `tools/re/wld_lightmap_tiebreak_verify.py` (read-only, `SS2_DATA_DIR`, reruns the same rasterization as `wld_lightmap_stream_verify.py`; about 2.5 minutes over all 59 worlds):
  - **Several candidates** (901 of 18,641 resolved instances, 155 of 1,935 distinct meshes): pick the **lowest-indexed** declared UV slot among the candidates — consistent with the dominant pattern already found among the single-candidate cases (slot 0 wins 87.0 percent of instances, 90.0 percent of distinct meshes there).
  - **No candidates** (1,593 of 18,641 resolved instances, 135 of 1,935 distinct meshes): fall back to the mesh's **slot 0** regardless of its own [0, 1]/overlap status — already suggested as "a reasonable default" by the existing reader invariants. This is not a blind guess: of these instances, slot 0 is **itself inside [0, 1] for 1,457 (91.5 percent)**, failing only the overlap test (most only barely past the 2 percent cut-off; the surface's winding/seam duplication plausibly inflates the rasterized overlap measurement at UV chart boundaries without the chart itself being wrong), so the fallback is a close approximation for the large majority of this bucket, not an arbitrary pick.

  Both tie-breaks are deterministic and need no rasterization at loader time (the mesh's own declared ids and slot order are enough); the rasterization is only how this task's own script *picked* the rule, not something a production loader needs to repeat. Combined with the existing single-candidate rule, this resolves **100 percent of the 18,641 lit instances whose mesh resolves at all** (16,147 single-candidate + 901 several-candidate + 1,593 no-candidate) to a definite UV id, leaving only the 38 instances whose model does not resolve to an external mesh at all (an embedded model configuration, the same gap T01-406/407 already hit) unresolved. **Confidence: high** for all instance/mesh counts (data script, every lit instance, all 59 worlds); **medium** for the tie-break's *correctness* against the shipped renderer (not independently visually re-verified by this task beyond the existing T03-039b spot checks; a reader adopting it should expect the "no candidate" bucket in particular to occasionally look slightly off at a chart seam, not broken).

  **T01-420 found both of T01-414's tie-breaks pick the wrong stream on real levels, and replaces them with a two-stage rule — after a first pass whose own overlap measure did not reproduce the shipped loader's, and a second pass that found why.** The loader built on T01-414's rule (T07-044) left every several-candidates mesh unlit and shipped "the lowest id the material does not use, else slot 0" for the no-candidate bucket; a visual check of the shipped renderer against real levels found the **same almost-black symptom in both buckets**: on the known several-candidates case, `1_7_city_metropolis`'s `platform_03/platform.mdl` (candidates UV id 3 at slot 0 and UV id 5 at slot 2; the material uses ids 2 and 4) renders almost black through slot 0 and plausibly lit, with a lit top and shaded sides, through slot 2 — and *neither* T01-414's lowest-index rule nor "not used by the material" tells the two apart, since both candidates are unused by the material and slot 0 is the lower index. On `6_2_military_base`, the shipped no-candidate rule produces the same symptom on the crate-stack models `Container_03/Container_Group.mdl` and `Container_Group_02.mdl`: their lowest-indexed, material-unused id (2, slot 0) is a **tiling channel with a UV range of roughly u ∈ [4.2, 20.0], v ∈ [−0.5, 6.0]** — nowhere near [0, 1] — so sampling the lightmap through it tiles the texture on a roughly 16×6 grid, consistent with the reported "nearly black with thin bright bands".

  **This task's own first-pass overlap numbers for `platform_03` (0.79 percent for id 3, 0.0 percent for id 5) could not be reproduced by the shipped loader, which measures 0.0 percent for *both* — a genuine tie, not a close call, confirmed at both a 256 and a 1024 grid.** `crates/ss2-world/src/load/lightmap.rs`'s own `rasterize`/`overlap` is a correct, fixed-256-cell-grid rasterizer that tests a pixel's *centre* against a triangle and breaks every edge shared by two triangles of the same chart in favour of exactly one of them (the standard "top-left rule", confirmed by that file's own unit test, `shared_edges_and_the_small_overlap_allowance`, which asserts a finely, evenly subdivided unwrap measures exactly 0.0 percent overlap). This task's first-pass script instead reused `wld_lightmap_stream_verify.py`'s own `overlap_fraction` (T01-407/414's own measure): it sizes its rasterization grid **dynamically** by triangle count (16 to 256 cells) and tests a pixel centre against all three of a triangle's edges with a plain, inclusive "≥ 0" half-space test — which **double-counts** every pixel centre that lands exactly on a shared edge, once as "inside" each of the two triangles that share it, with no rule to break the tie. `platform_03/platform.mdl`'s slot 0 (UV id 3) is exactly the kind of chart that triggers this: a finely, evenly subdivided unwrap whose internal edges are grid-aligned to simple UV fractions, which hits the double-count often enough at a 256 grid to read a few tenths of a percent of spurious "overlap" even though no two triangles' interiors truly overlap anywhere. `tools/re/wld_lightmap_streamselect_verify.py` now ports `rasterize`/`overlap`/`cross`/`cell` from the shipped loader line for line (same fixed 256-cell grid, same centre-sampling, same top-left rule, same `RANGE_EPS` of 1e-3 for the [0, 1] test) as [`overlap_exact`]/`exact_analyze_mesh`, used for every overlap number below; T01-407/414's own existing scripts and specs are untouched (out of this task's scope) and still use their own, earlier measure.

  **Re-measured this way, overlap almost never discriminates several candidates at all: a real lightmap unwrap has no true triangle overlap anywhere, so every genuine candidate typically reads exactly 0.0 percent, and a tie — not a close call — is the *normal* case, not a rare one.** Over all 59 worlds, of the several-candidates bucket's 155 distinct meshes, overlap alone resolves to one lowest-overlap id for only **32 (20.6 percent)**; the other **123 (79.4 percent)** tie on their lowest overlap value (most commonly two ids tied at exactly 0.0 percent) and need a second signal — `platform_03/platform.mdl` (ids 3 and 5, both exactly 0.0 percent at grid 256 *and* grid 1024) is one of them. The no-candidate bucket behaves differently: of its 128 distinct meshes, 22 (17.2 percent) have no id inside [0, 1] at all (T01-414's slot-0 fallback, unchanged) and overlap alone resolves 104 of the remaining 106 (98.1 percent) — `Container_Group.mdl`/`Container_Group_02.mdl` resolve this way too, since id 3 is their *only* id inside [0, 1] at all (overlap 3.65 / 3.28 percent — a near-miss unwrap, just over the existing 2 percent cutoff, the same pattern T01-414 already found explains most of this bucket); only 2 of 128 meshes tie here.

  **The tie-break is the fraction of a candidate's own UV footprint that is actually "lit" baked pixel data in the instance's own already-baked lightmap texture, `frac_lit`** (rasterized the same way as T01-407's `--texels` check; a texel departs from near-grey by more than the existing tolerance). On `platform_03`, slot 0's footprint covers the *entire* lightmap (100.0 percent of its texel area) yet is only 96.4–99.6 percent "lit" across its several instances — a sliver of its own footprint lands on unused, near-grey texels right at the image edge — while slot 2's smaller footprint (79.4 percent of the texture) is 98.1–100.0 percent lit: it never leaves the real baked chart. `frac_lit` resolves 254 of the 867 several-candidates instances this task could fully measure (29.3 percent) after an overlap tie; the remaining ties (415 of 867, 47.9 percent — `frac_lit` itself ties too, most often at 100 percent for both) fall back further, to the existing order (lowest id unused by the material, then lowest slot index) — so that older heuristic is still the single most common deciding step, just no longer the *first* one tried, and no longer applied ahead of a real overlap or `frac_lit` difference when one exists. Two other signals were tested and rejected as unreliable on their own: raw mean texel luminance under a candidate's footprint is *anti-correlated* with the correct pick on the hard case (slot 0's larger, wrong footprint averages *brighter*, not darker, than slot 2's, on every one of `platform_03`'s instances checked — for example 80.6 against 78.1 out of 255 on one instance, 33.9 against 31.3 on another — and agrees with the adopted rule's pick only 51.6 / 53.6 percent of the time, near chance); texel-area "coverage" alone is confounded by the same out-of-range-channel artifact as the `Container_Group` bug (a channel's UV bounding box clamps into the grid even when its true range runs far outside [0, 1]) and agrees 70.1 / 91.0 percent of the time. UV/lightmap aspect-ratio match is a real but weaker corroborating signal (79.1 / 91.3 percent).

  **The adopted rule, over the mesh's declared ids restricted to those themselves inside [0, 1] (within `RANGE_EPS`, 1e-3 — never a channel that runs outside [0, 1], however unused by the material or low-slotted it is):**
  1. If exactly one id has the lowest [`overlap_exact`] fraction (the fixed-256-grid, top-left-rule measure above, the same one the shipped loader computes), pick it.
  2. Otherwise, among those tied on the lowest overlap, pick the one with the highest `frac_lit`.
  3. Otherwise, fall back to the existing order: lowest id unused by the surface's own material, then lowest slot index.
  4. If no id is inside [0, 1] at all, keep T01-414's slot-0 fallback, unchanged.

  This picks UV id 5/slot 2 on `platform_03/platform.mdl` (stage 2, `frac_lit`) and UV id 3/slot 1 on `Container_Group.mdl`/`Container_Group_02.mdl` (stage 1, `overlap` — id 3 is their only id inside [0, 1] at all, so there is no tie to break) — both the plausibly-lit streams, not the almost-black ones.

  **Over all 59 worlds, at the instance level** (867 several-candidates instances and 1,280 no-candidate instances with a full signal set — texture-dependent signals need the instance's own lightmap, so this could not be measured per distinct mesh the way T01-414's own counts were): the rule resolves at stage 1 (`overlap`) for 198 (22.8 percent) of several-candidates instances, stage 2 (`frac_lit`) for 254 (29.3 percent), and the stage-3 fallback for 415 (47.9 percent); for no-candidate instances, 1,176 of 1,280 (91.9 percent) resolve at stage 1, 100 (7.8 percent) have no id inside [0, 1] at all (the unchanged slot-0 fallback), and 4 (0.3 percent) reach the stage-3 fallback. The adopted rule's pick **differs** from T01-414's superseded lowest-index tie-break on 262 of 867 several-candidates instances (30.2 percent) and from T07-044's shipped not-used-by-material rule on 28 of 1,145 comparable no-candidate instances (2.4 percent) — `Container_Group.mdl`/`Container_Group_02.mdl` are among those 28. At the distinct-mesh level (the cheap, texture-free pass, `--meshes`, which can only report the stage-1-only view and so undercounts how often the full rule disagrees): of the several-candidates bucket's 155 meshes resolved by overlap alone (32), 18 agree with lowest-index and 17 of 27 comparable agree with not-used-by-material; of the no-candidate bucket's 128 meshes resolved by overlap alone (104), 86 agree with lowest-index and 86 of 93 comparable agree with not-used-by-material.

  **The oven modifier's own UV id (a per-world constant, T01-406) was checked once more for a relation to the newly chosen stream**: per-world, (oven id − chosen id) does not settle on one dominant value (many distinct offsets recur within the same world, in both buckets) — this does not newly pin the engine mechanism, which stays the open question of the follow-up (`T01-419`). **Confidence: high** for every instance- and mesh-level count above (data script, every lit instance and every distinct mesh that resolves, all 59 worlds, using the same fixed-grid, top-left-rule measure as the shipped loader); **medium** for the rule's correctness beyond the two cases checked here against a render or against the mesh's own UV ranges directly (`platform_03` by a visual check of the shipped renderer; `Container_Group`/`Container_Group_02` by this task's own reading of their UV data, not independently re-rendered).

  **A real, through-the-vtable caller of `IsLightMap` was found** (`Engine.dll`, by scanning for calls at `CTextureModifier::IsLightMap`'s own inner virtual-call site rather than by name, since neither T01-406 nor T01-407 found one by name): `gfuCurrentTexture`, the function that binds a texture to a GPU texture unit immediately before a draw, calls it on every non-null texture and special-cases the lightmap case twice — once to let a debug cvar replace a flagged lightmap with a flat grey, a false-colour luminance visualisation, or the ordinary texture (a three-way debug rendering mode), and once to **disable anisotropic filtering and LOD bias by default** (overridable by a second cvar) for any texture the flag marks. Neither use decides which UV channel is sampled; this only answers "does any code call `IsLightMap` through the vtable" and what it does when it does. Internally, `CBaseTexture`'s own methods (`GetSize`, `mdCollect_t`, `Upload`, `Finalize`) call the same virtual method on themselves to choose between two independent image-quality cvar groups (one for ordinary textures, one for lightmaps) for mip bias, max size and quality tier — again nothing about UV channels. **Confidence: medium.**

  **The brightness factor: the shader-program data and the real-game visual check (T03-039b) disagree, and this reading could not reconcile them — keep the renderer's visually-validated choice.** `lighting.md` already establishes (inferred) that a lightmapped, full-bright instance is rendered through the shade family's "full bright, N shade textures" permutation, treating the lightmap as a generic multiply-in "shade" texture over the base texture. Comparing that family's pixel programs for zero, one, two and three shade textures (`GPU-Programs.asm`, T01-020's own source, not a binary read) shows a clean, systematic pattern, identical in substance on both the Direct3D and OpenGL code paths (which reach it through different instruction sequences, a cross-check): **each additional shade texture doubles the pixel program's overall output scale relative to one fewer** (factor of four with none, eight with one, sixteen with two, thirty-two with three), while the shade texture itself is combined with the base texture by a plain, unscaled multiply — naively read, this says a lightmapped draw's output is scaled twice as hard as an otherwise-identical non-lightmapped full-bright draw. **T03-039b (`docs/superpowers/specs/2026-11-27-lightmaps-design.md`, "Result on real levels", 2026-11-28) already tested exactly this by eye against the real game on three levels and found the opposite: ×1 "reads natural next to the sky", ×2 "is blown out in the city"**, and shipped ×1. Direct, real-game visual comparison is stronger evidence than an indirect reading of relative pixel-program scale factors (whose baseline — a flat, non-lightmapped full-bright surface — is not necessarily the right reference point for "what a neutral, fully-lit lightmap texel should reproduce"; the vertex-side full-bright constant that feeds both programs was not traced to confirm it is the same in both cases). This reading could not identify the specific instruction that resolves the discrepancy. **Recommendation: keep ×1** (matches the shipped game by direct comparison); treat the pixel-program scale pattern as an unreconciled signal, not a confirmed factor. **Confidence: low** on "the factor is 2"; the ×1 finding is comparatively strong (direct visual match against the retail game) but was not independently re-derived by this task.

  **The V coordinate: no flip instruction was found, consistent with the real-game check.** The shade family's vertex program applies the same single scale-and-offset instruction to both components of a shade texture's coordinates; no separate per-axis negation exists in the program text, so any flip would have to be baked into the scale/offset values a shader class uploads for a given draw, which this task did not trace. **T03-039b independently confirmed no flip by eye** against the real game (a flipped V breaks the `dm_stadium` beams into mismatched, seamed patches), matching T01-407's own rasterisation check (raw, unflipped V, 54-92 percent texel coverage) and the absence of a flip instruction here. **Confidence: medium** (no flip instruction found; corroborated by two independent checks, but the absence of an instruction is not the same as having read the one that matters).

- **`Bake(instance, placement)` on the modifier itself** (read in full, T01-061) is confirmed to be **editor-only**: it does nothing unless the modifier has a bake record (`.6`/`.9` chain), and when it runs it prepares the texture and asks the bake record's own virtual method to fill the pixels — the shipped game loads the already-baked texture directly and never calls this. (This is `CTextureOvenShaderModifier::Bake`, distinct from `CModelRenderable::Bake` above, which does run in the shipped game.)

## Reader invariants

1. For each `CModelInstance`, apply the modifiers of its list in order; a `CTextureOvenShaderModifier` replaces a texture slot by the lightmap texture.
2. Read the lightmap texture from the world's own `CStaticTexture` objects (zlib blob, formats of `tex.md`); never expect it as an external file.
3. **Do not look up the oven modifier's UV map id (`.3`) in the mesh's own per-surface UV id list** (`bmf.md` member 12/14), nor in its colour-map id list (member 13/15, T01-414: confirmed always empty on every lit instance, so it is not a hidden second place to find the id either): it is confirmed (T01-406) never to be one of them, and it is a per-world constant, not a per-instance or per-mesh value — treat it as opaque. **T01-407:** sample the lightmap instead through the mesh's own UV stream that is simultaneously (a) entirely inside [0, 1] (small epsilon) and (b) non-overlapping in UV space (at most a couple of percent of its rasterized area overlaps another triangle of the same stream) — in practice this is the mesh's **first declared UV slot** (surface member 12/14, index 0) in the large majority of cases (87.0 % of instances, 90.0 % of distinct meshes with exactly one such stream, over all 59 worlds), and it is usually **not** a UV id the surface's own material references for any of its own texture groups, so it is *not*, in general, the instance's base/diffuse channel (that earlier pragmatic approximation is superseded). **T01-414, for the 13.4 % of instances with no such stream or more than one** (verified over all 18,641 resolved lit instances, `tools/re/wld_lightmap_tiebreak_verify.py`): with **several** candidates, pick the **lowest-indexed** one (901 instances, 155 distinct meshes); with **none**, fall back to **slot 0** regardless (1,593 instances, 135 distinct meshes — slot 0 is itself inside [0, 1] for 91.5 % of these, so the fallback is a close approximation, not an arbitrary pick, for the large majority). **T01-420 supersedes both of these tie-breaks with a two-stage rule** (`tools/re/wld_lightmap_streamselect_verify.py`, all 59 worlds; `overlap_exact` ports the shipped loader's own fixed-256-grid, top-left-rule rasterizer line for line, since T01-407/414's own measure double-counts shared chart edges and does not reproduce the loader's numbers): restrict to ids that are themselves inside [0, 1] (never a channel that runs outside [0, 1], however unused by the material or low-slotted); if exactly one has the lowest rasterized overlap fraction, pick it; a correctly measured overlap fraction rarely discriminates on its own (true candidates typically measure exactly 0.0 percent, so ties — not close calls — are the normal case for several candidates, resolving only 20.6 percent of the several-candidates bucket's distinct meshes by themselves), so on a tie pick the id whose own UV footprint is the most fully "lit" baked pixel data in the instance's own lightmap texture (`frac_lit`, resolves a further 29.3 percent of several-candidates instances); a further tie falls back to the order above (unused by the material, then lowest index, the single most common deciding step overall); a mesh with no id inside [0, 1] at all still falls back to slot 0. This picks UV id 5/slot 2 (not id 3/slot 0, tied at 0.0 percent overlap, resolved by `frac_lit`) on `1_7_city_metropolis`'s `platform_03/platform.mdl` — the known hard case where the two superseded tie-breaks both pick the wrong, almost-black stream — and UV id 3/slot 1 (not the tiling id 2/slot 0, resolved at the overlap stage since id 3 is the mesh's only id inside [0, 1] at all) on `6_2_military_base`'s `Container_Group.mdl`/`Container_Group_02.mdl`, where T07-044's shipped no-candidate rule shows the identical failure; see "Baked lightmaps" above for the full counts (differs from the superseded rules on 30.2 percent of several-candidates instances and 2.4 percent of comparable no-candidate instances, over all 59 worlds). **Implement this two-stage ranking**, not the two tie-breaks it replaces, which are kept above only for history. Combined with the single-candidate rule this resolves **100 % of the lit instances whose mesh resolves to an external model at all**. This is still a **data-driven** rule, not a confirmed engine instruction — **T01-408** found the engine's own UV-channel resolution is a generic, id-matching lookup against a per-draw table built from **two** equally-sized groups of id'd slots (shared by every shader class, not a position-based read); **T01-414** identified the second group's own id source (the mesh's own colour-map ids, confirmed always empty for every lit instance) and traced the override mechanism one step further (`CShaderArgs::ReadModifiers`/`shaReadValue`: the override substitutes a plain value directly into the shader argument object `Exec` reads, in an id space private to the argument class, not a CTSEMETA member number or a stream-table entry) — by this task's reading, the substituted id still cannot match either now-identified group, which is inconsistent with lightmaps visibly rendering correctly, so the exact instruction that resolves the oven modifier's own id to a real stream **remains unidentified**; implement the rule above as the best available **data-driven default**, not as a confirmed engine rule (see the follow-up task).
4. **Multiply the base texture by the lightmap texel with a plain, unscaled (×1) factor; do not flip V.** Both are validated by direct, real-game visual comparison (T03-039b, `docs/superpowers/specs/2026-11-27-lightmaps-design.md`): an unflipped V and a ×1 multiply match three retail levels by eye, while a ×2 multiply "blows out" and a flipped V breaks a stadium's beams into mismatched, seamed patches. T01-408 found a signal in the shipped shader programs (`GPU-Programs.asm`) that looks, on a naive reading, like a systematic ×2 scale for a lightmapped draw relative to a non-lightmapped one, but could not reconcile it with the real-game result above — treat that signal as unresolved, not as grounds to multiply by 2.
5. A reader may ignore the extra-section bake records and ambient masks (editor data).
6. Use the light list (or the light grid) for dynamic lights; the light source holds the runtime values, the record is the editor copy.
7. A light source has no owner: reach it through its entity's member `.2`.
8. Convert cone angles from radians (source) or degrees (record) consistently.
