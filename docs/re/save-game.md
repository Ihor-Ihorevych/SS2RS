# Save games: what the original writes, what a load does, what must persist (T01-032)

- **Roadmap task:** T01-032
- **Author:** @Ihor-Ihorevych/agent · **Reviewer:** _none yet (T01-049)_
- **Confidence:** **high** for the names of everything quoted from the binaries and the data (class, member, function and string names), for the data checks of `savegame_verify.py` (the save-data pointer of every shipped world, the save counter, the classes that no data file defines, the demos) and for the **absence** of any real save in the install; **medium** for every rule below, because each rests on a static reading of the binaries (usually two paths that agree) and **no real save file was available to open**; **low / open** for sizes, what exactly is left out of a save, and everything that needs the running game.

Prerequisites: `ctsemeta-container.md` and `ctsemeta-types.md` (the container a save is written in), `wld-root.md` (`CWorld`, the domains, the state manager), `main-loop.md` (`Time`, the simulation clock, `SetNow`), `console-config.md` (profiles), `gui.md` and `menus-tables.md` (the Save and Load screens), `level-logic.md` (chapters), `docs/SAVES.md`, `docs/CAMPAIGN.md` and `docs/LEVEL_PROGRESS.md` (our own design, the right-hand column of the last table).

## Summary

**A saved game of the original is a copy of the whole running world, written as a world file.** The engine makes a deep copy of the live `CWorld` (every entity, the domains, the macro threads and the think queue; resources are shared, not embedded), attaches a three-field record `CWorldSaveData` (the simulation clock, the save counter of the level, the file name of the level the world came from) and writes it with the same resource-file writer that writes `.wld` files, under the extension **`.sav`**. Two text files go next to it: **`.nfo`** (the name and statistics shown in the list) and **`.preload`** (the level's resource list plus one line). Loading is the normal "start a world" path with a flag: the file is read as a world, copied, started **without** the start-of-game events, and the clock is set to the saved one.

The rest of the answers, in the order of the roadmap line:

- **Kinds.** (1) *Named save* from the in-game menu (new slot `Save_NNNN` or overwrite); (2) *quick save* (`QuickSave.sav`, with a quick-load command); (3) the **chapter save**, an in-memory summary (`CStoredLevelStatus`: players' inventory, secrets, beacons, objectives, statistics) made **every time a chapter starts** and, in single player, copied into the **player profile** and written to `Profile.dat`; that is what "Continue" uses and the only automatic persistence found. **No autosave file exists** (the save function has three callers, all user commands). **Saving and loading are refused in every network game, co-op included.** Demos (`.dem`) are a different mechanism (recorded network messages). Per-level "persistent" state between levels is the chapter save (secrets, beacons, objectives, players).
- **Container.** A world resource file (CTSEMETA family, medium); not signed (the profile is), no compression step found; the level name inside is stored as plain bytes between two text markers, which the game finds by scanning the raw file.
- **What is saved.** Everything in the world object graph that the metadata system copies. **Not** saved: the random-number generator (two process-wide words seeded from the CPU's time-stamp counter at start-up), the real-time clock, resources, the UI, options and key bindings (profile), the network session. Details and confidence per category in the last table.
- **A load** restores the clock and does not re-run level start-up; it refuses (logs, and sends a failure message) a save made from a **newer** version of the level than the installed one (one-directional counter test).
- **Limits.** Single player only; per-profile folder; no slot limit, no combat, difficulty or cutscene rule found; up to **64** profiles; the "Saving..." text shows for **1.0 s**.
- **What must persist for us:** the table at the end. The headline: our property-based save (`ss2_sim::save`) is **much smaller by design**, so every state the original keeps "for free" by copying the world (timers, running scripts, objective and beacon states, per-player inventories) must be put into persistent properties or the checkpoint payload on purpose, and **co-op saves are new** (the original has none).

## Evidence

- **Binaries.** Read statically with Ghidra 12.2 (headless, read-only), notes outside the repository: `Core.dll` 794,624 bytes, `Engine.dll` 3,493,888, `Sam2Game.dll` 5,550,080, `Sam2.exe` 28,160, `DedicatedServer.exe` 18,432 (the sizes identify the build, as in `main-loop.md`; the demos in the install carry the build string `2.068.00:61409; 2006-PATCH-2-068-inc`, which is the baseline of the shipped demos, not necessarily of the DLLs). Not read: `GfxD3D.dll` and the other back ends, `EngineGui.dll`, `InSamnity2Game.dll`.
- **How the pieces were found.** The DLLs export decorated C++ names, so the work started from exported names (`CSimulation::Save_t`, `CSimulation::Load_t`, `wldPrepareSaveData`, `wldGetSaveData`, `CMSSaveGame::CreateSaveGameFileName`, `CGameInfoEntity::GenerateChapterSaveGame`, `CPlayerBrainEntity::StoreChapterSaveData`, `CStoredChapterStatus::GetSavedPlayer`, `CWorldInfoEntity::ResetWorldToChapter` and others), then callers and cross references, then the member-name strings the metadata system registers for each class (`ps_`, `sls_`, `pp_`, `pop_`, `pls_`, `apd_`, `gs_`, `wsd_` members), then the data files' type tables.
- **Cross-checks (two readings).** (1) The save-data record: the data's own type table of every shipped world declares the pointer **`CWorldSaveData*`** as the member `CWorld.18`, and it is null in every version of every world (`savegame_verify.py`); the code that saves attaches a record to the copy, the code that loads reads it back, and a third function (the one that finds the source level of a `.sav`) scans the raw file for the same marker text. (2) The save counter: the binaries name `wo_ulSaveCounter` (world) and `wsd_ulSaveCounter` (record) and compare them on load; the data member `CWorld.19` (a `ULONG`, the only counter-like member left) **never decreases from one patch level of a world to the next** in the install and rises in most (script, numbers below). (3) "No save in multiplayer": the save command, the load command and the engine's own `Save_t` each test for a local session independently. (4) "No other writer": the save function has three callers, all user-facing. (5) The classes a save adds (`CPlayerSave`, `CStoredLevelStatus`, `CGameInfoEntity`, `CPlayerProfile`, ...) are defined in **no** data file (script), so the member lists below can only come from the binaries' own name tables.
- **Data.** `python -I tools/re/savegame_verify.py <install>` (about 6 minutes; `--skip-worlds` skips the slow part, which takes about 3 minutes). It reads every version of every `.wld` (59 worlds), the type tables of all 9,269 format-8 files, the 46 `.wld.preload` files and the 3 demos with their `.nfo` files.
- **Not done, and why it matters.** **No save file and no `Profile.dat` exist on this machine or in the install** (the install has no `SavedGames` or `PlayerProfiles` folder; the only user-made files are the three shipped demos). So **no header, size or byte was checked against a real save.** Everything about the save's bytes is inferred from the code and from the fact that a world file is written by the same machinery. Whether a rule really happens at run time ("is it refused while dead?", "does the music resume?") needs the running game: T01-038, T01-039, T11-008, listed under Open questions.

## Layout / rules

### 1. The kinds of save

| Kind | How it starts | What is written | When it is allowed | Confidence |
|---|---|---|---|---|
| **Named save, new slot** | In-game menu, `Save game`, the list row `< save a new one >`; a text entry (`Enter name`) gives the display name (empty: a default name from the game) | `Save_NNNN.sav` + `.nfo` + `.preload` in the profile's folder (section 2) | single-player (local) session only | medium |
| **Named save, overwrite** | Pick an existing row, answer `Overwrite?`, enter a name | the same file names as the picked row, new content and a new display name | same | medium |
| **Quick save / quick load** | Player commands `plccmdQuickSave` and `plccmdQuickLoad` (display names "Quick save", "Quick load") | `QuickSave.sav` + `.nfo` (display name `Quick Save`) in the same folder; quick load opens that file | save: local session only (same function); load: local session only | medium |
| **Chapter save** | Every time a chapter is marked started (`CChapterInfoEntity::MarkStarted`) the game info entity builds a `CStoredLevelStatus`; in **single player** it is copied into the active player profile, the level's statistics are updated, and the **profile is written to disk** | memory; and `Profile.dat` (section 6) | every chapter start (single player); the profile file is **not** written for the temporary (guest) profile | medium |
| **Console** | Console functions `samSaveGame(szSaveFile)` and `samLoadGame(szSaveFile)` | a `.sav` only (the `.nfo` writer is called by the three user paths and by nothing else), so such a save is **not listed** in the menu | as the others | low (wrapper binding not read) |
| **Demo recording** | Record-demo screen or a command; `.dem` + `.nfo` in the demos folder | recorded network messages, **not** a world copy (section 8) | any session that can record | medium |
| **Server / co-op save** | **none** | | `Cannot save game in multiplayer.` and `Cannot load game in multiplayer.` | high (three independent checks) |

There is **no autosave to a `.sav`**: the function that saves is reached from exactly three places (new slot, overwrite, quick save) and a console wrapper; none is timed or event-driven. The only automatic persistence is the chapter save into the profile. The "Saving..." text (a HUD element) is shown for **1.0 s** after the game's "last save" time stamp, which is set both by a user save and by a chapter start; so players see it at every chapter start too (medium: the stamp is written in both places, the 1.0 s is the constant compared against).

### 2. Files, folders and naming

For one saved game `<name>`:

| File | What | Written |
|---|---|---|
| `<name>.sav` | the world copy (section 3) | by the engine's `CSimulation::Save_t` |
| `<name>.nfo` | the list entry (below) | **before** the `.sav` (the game writes it, then calls the saver) |
| `<name>.sav.preload` | a text copy of the level's own `<level>.wld.preload` with **one line appended**; if the level has no `.preload`, a stale one next to the save is deleted | by `Save_t`, after the `.sav` |

- **`.preload` format** (shipped, measured): text, CR LF line ends, one resource per line, `<size in bytes>:<path>` (for example `158491:Content/SeriousSam2/Fonts/SeriousVerdana.fnt`). The install has **46** `.wld.preload` files (23 in `All_PC_02.gro`, 19 in `All_PC_03.gro`, 4 in `Patch_02_068.gro`), 56,471 lines in all, of which **257 are the bare line `-1:`** (no size, no path). None of the 46 lists the level's own `.wld`; **the line `Save_t` appends is `<size of the level file>:<its path>`**, so a save's list is the level's list plus the level file itself. The list is a prefetch hint for the resource loader (`.preload` use at load time is T01-088).
- **`.nfo` format.** Text, **UTF-8 with a byte-order mark**, one `KEY="value"` or `KEY=value` per line, CR LF (as in the shipped demo `.nfo`; the save's own lines are written by the same stream type: medium). Read **line by line, in any order**, with these keys (all read by the save list): `NAME`, `TIMESTAMP`, `TOTAL_PLAYTIME`, `STAT_CHEAT` (`True` or `False`), `STAT_PLAYTIME`, `STAT_SCORE`, `STAT_KILLS`, `STAT_SECRETS` (found/total), `HIGHSCORE`; an unknown key is ignored. The demos' `.nfo` use only `NAME` and `TIMESTAMP`. The values are formatted from the game statistics at save time (play time as `HH:MM:SS` text; `TOTAL_PLAYTIME` and `HIGHSCORE` are the larger of the profile's best and the current value, medium). `TIMESTAMP` is the local time formatted as weekday abbreviation, comma, space, then the locale's date and time (`Mon, 13-02-06 14:57:52` in the demos: day-month-year with a two-digit year, then `HH:MM:SS`). **There is no thumbnail and no level name key**: the list shows the player's name for the slot and these numbers.
- **The save list** scans the profile's folder for `*.nfo`, **drops every entry whose `.sav` does not exist**, sorts the file names **in descending order** (the comparison is a case-sensitive string comparison with its sign reversed, so `Save_0007` comes before `Save_0003` and `QuickSave`, which compares lower than `Save_`, comes last), and then moves **`QuickSave` from the end of the list to the first position**: the list shows the quick save first, then the numbered saves with the highest number first (medium: the two functions agree). A `.sav` without a `.nfo` is invisible; a `.nfo` without a `.sav` (a crash between the two writes) is dropped.
- **Naming of a new slot.** The folder is scanned, the names sorted in descending order (above), the **first** (highest) name taken; if it is not `QuickSave` its number is read from the pattern `Save_<n>` and incremented; the result is `Save_` plus the number zero-padded to **4 digits** (`Save_0000` when the folder is empty). If the last file is `QuickSave`, the number stays 0 (so a folder holding only a quick save gives `Save_0000`). Numbers above 9999 get wider, but because the sort is alphabetical `Save_9999` stays the highest name, so the 10,001st slot would be given the name of the 10,000th (an edge case nobody reaches; low). (Medium: one function; the pad width is the format `04` read from the program's data.)
- **Folder.** `Content/<mod>/SavedGames/<H>/`, where `<mod>` is the folder name of the running mod (`SeriousSam2` for the base game; the install also holds the mods `InSamnity2` and `Sam2Renovation`) and **`<H>` is the profile name run through the engine's string hash and printed as 8 upper-case hexadecimal digits** (the hash function was not read). The **temporary (guest) profile** saves to `Temp/SavedGames/` instead. The player profile uses the **same `<H>`** under `Content/<mod>/PlayerProfiles/<H>/` (section 6). Whether `Content/` is relative to the install or redirected to a user folder is T01-081 (the install has neither folder). Saves are therefore **per mod and per profile**: a profile sees only its own saves. (Medium.)
- **No temporary file and no rename** were found: the writer opens the final name. A crash while writing leaves a damaged `.sav` next to a good `.nfo` (the list would show it).

### 3. The `.sav` file

- It is a **world resource file written by the generic resource-file writer** (`CResourceFile::SaveFile_t`, which asks the registered file types which one accepts the file), the same call chain that writes a `.wld`; the object saved is a `CWorld`. So it is a **CTSEMETA container** (`ctsemeta-container.md`: magic `CTSEMETA`, little-endian, type tables travelling inside the file, strings as a `u32` length and raw bytes), and the `CWorld` has the same members as in a `.wld` (`wld-root.md`). **Medium**: the chain is read, no `.sav` was opened. Nothing found compresses or encrypts the file, and it is **not a signed stream** (the profile is, see section 6).
- **One extra object: `CWorldSaveData`**, pointed to by `CWorld.18` (null in every shipped world: all 107 world versions in the install). Its members, with the names the binary registers:

| Member | Type | Meaning | Confidence |
|---|---|---|---|
| `wsd_tmSimTime` | `Time` (signed 64-bit, 2⁻³² s units) | the simulation clock at the moment of saving (`Now`) | medium |
| `wsd_ulSaveCounter` | `ULONG` | the **save counter of the source level** (`wo_ulSaveCounter`, data member `CWorld.19`) at saving time | medium |
| `wsd_strWorldFN` | string | `{WLD_SRC_FN_START:` + the **source world's file name** + `:WLD_SRC_FN_END}` (the two markers are part of the stored string) | high for the markers (two readers), medium for the rest |

- The record is a 16-byte object in memory (time 8, counter 4, string 4); the file stores it as the container stores any object (not specified further: needs a sample, T01-090).
- **Finding the source level without parsing the file:** the game's `GetSourceWorldFN` opens a `.sav` and **searches the raw bytes for the start marker, then the end marker**, and takes what lies between; any other file name is returned unchanged. That is a second, independent proof that the name is stored as plain bytes and that the file is not compressed as a whole (a compressed file could not be searched). It also means a stored level path can be read by a trivial tool.
- **The save counter.** `CWorld.19` is the number of times the level was saved by the editor: in the install it is **4, 12, 13** for the three versions of `1_3_village.wld` and never decreases over the 31 worlds present in more than one archive and **rises strictly with every patch level in all 31** (the whole install: 3 to 1,696; numbers in "Test vectors"). It is the level's **version number**.
- **Versioned? checksummed? compressed? byte order?** Versioned by two things only: the container's own format number (8 for every file of the install, `ctsemeta-container.md`) and the level's save counter above; there is **no save-format version of its own** in the code read. **No checksum** was found in the save path (no signed stream, no CRC field: a flipped byte is found only if it breaks parsing). **No compression** found. **Little-endian** (the container). All medium: they follow from the write chain, not from a file.
- **Size.** Unknown (T01-090). A lower bound from the construction: the copy contains the whole entity graph of the level (static models, lights, hulls, spawners), not only what changed, and only exposed resources (the baked lightmap textures) are shared; the 59 shipped final world files are between **33,217 bytes and 22,830,096 bytes** (median 10,308,185; the size line of the script), so a save is expected to be of the **order of the level file**, not a few kilobytes (low).

### 4. What a save does

`CSimulation::Save_t(path)`, in order (medium; one reading plus the callers):

1. **Refuse** (log `Cannot save '<path>', not within a valid simulation.`, nothing written) unless **all** hold: the simulation has a started world; the resource loader is not in the "prepared but not yet loaded" state; **the network interface is the local (single-player) kind**; and a world is present.
2. Log the local time stamp and `Saving '<path>'.`
3. **Suspend the sync lists** (sound, movie and vibration lists, `CWorld.12` to `.14`) so that nothing is updated while copying.
4. **Deep-copy the live world** with the metadata copy (`mdCopy`) with the flag *copy edit data* **off** and the flag *share exposed resources* **on**: the copy has every serialised member of every object except editor-only data, and the shared resources (the textures listed in `rf_crsExposed`) are **referenced, not duplicated**.
5. Attach a `CWorldSaveData` to the copy: clock (`Now`), the source level's save counter, the source file name marker (the name is the simulation's *world name*, which after a load is the **original level's** name, so saving a loaded game keeps the first level's name).
6. Register the copy as the shared resource of a new resource file, set the file name, and **write it** (`SaveFile_t`).
7. Write the `.preload` sidecar (section 2), release the copy, restore the two flags.

Before step 1 the game (the user-level wrapper) **sets the game statistics' "saving" flag (`gs_bSaving`) in the live world** and the "last save" time stamp; the flag is a persisted member of `CGameStats`, so the **saved copy carries `gs_bSaving` = true** (medium). What the flag does after loading, and where it is cleared, is not established (T01-094). The game's wrapper also refuses in multiplayer with `Cannot save game in multiplayer.` before it calls the engine.

**What a save contains.** Everything the copy reaches: the **entity list** (`CWorld.1`) with every entity's members, the entity property records (`CWorld.5`), the five domains (rendering, physics, collision, scripting with the **state manager (think queue)**, macro with the **macro threads**), the world info entity and its members, and **entities that exist only at run time** (players and their brains, the game info entity, projectiles, effects, pickups dropped; the handle to the game info entity, `CWorldInfoEntity.53`, is null in all 59 shipped worlds, `wld-entity-schema.md`, so it is filled only in a world that has been played). Because the copy uses the same type-table machinery as `.wld` files, the member lists in the data (`wld-entity-schema.md`, `classes-catalog.md`) are the per-class member lists of a save for the 1,043 classes the data defines; the classes that exist **only at run time** (`CPlayerPuppetEntity`, `CPlayerBrainEntity`, `CGameInfoEntity`, `CPlayerInventory`, the saved-player and stored-status records of section 6: none is defined by any data file) are known from the binaries' name tables only. A member flagged by the class declaration as not saved (`SMF_DONTSAVE`, `SMF_TEMPORARY`, `SMF_DONTCOPY`, `SMF_NOCLIPBOARD`; the names of the flags are in the engine) is left out; **which members carry those flags was not extracted** (T01-093).

### 5. What a load does

`CSimulation::Load_t(path)` logs the time stamp and `Loading '<path>'.`, then runs **`Start_t(path, 1)`**, the same start as for a level but with the flag "from a saved game". The game's start function (shared by new game, continue, the quick-load and menu-load commands and the start-up path that starts a game from the command line or session parameters) calls `simLoad_t` when the **file extension is `.sav`** and `simStart_t` otherwise. In order (medium):

1. **A new single-player session is built** (a fresh local network interface and a fresh simulation replace the old ones). Loads are refused in a network session (`Cannot load game in multiplayer.`) and when the file does not exist (`Can't load '<name>' saved game because it doesn't exist.`). Quick load, the menu's load list, `Continue`, new game and the start-up path all go through this one start function (six callers).
2. The resource loader loads the file as a `CWorld` (any file name; the loader is told the type). The world is **copied once more** (the same copy as for a new game) and made current.
3. **The start-of-game events are skipped.** For a normal start the engine calls the project instance's start hook and `CWorld::OnSimStart` (which calls the start function of every entity); with the "from a saved game" flag set it calls **neither** (the flag is one field of the simulation, set by `Load_t` and cleared by `simStart_t`). The world therefore **continues exactly where it was**: running macro threads, pending thinks, entity states. `netInitializeEntities` runs in both cases.
4. **The clock is restored**: `SetNow(wsd_tmSimTime)` sets the simulation clock, the cursor and the real-time reference together and the last step length to 0.001 s (`main-loop.md`). Think-queue due times are in that clock, so they stay consistent without being rewritten (medium).
5. **The version test.** The simulation's world name is set to the stored source file name; the engine obtains that **level** from the install and compares its save counter with the one in the record. **If the installed level's counter is lower than the saved one** (the save was made from a newer version of the level), it logs `World version doesn't match saved game version. Refusing to load saved game (<name>).` and, when the variable `sim_bCheckWorldVersion` (default **1**) is on, sends the message `Message.Simulation.WorldLoadFailed`. **A save made from an older level version passes** (the test is one-directional, "saved > installed" fails). Whether the message really stops the load or only informs the player is **not established**: the code continues after sending it (T01-094). A failed *file* load (no resource) sends the same message, and a world flagged "needs to be reinitialised" sends `Message.Simulation.WrongWorldVersion` (for a world that was edited and not re-saved).
6. **The macro scripts are not started again from the top**: the start events that begin them are the ones skipped in step 3, and their saved threads simply continue (medium; no sample to confirm).

**Patch levels and mods.** Reading a file is member-by-name through the type tables that travel inside it (`ctsemeta-types.md`), so a save made with an older or newer *class layout* is probably tolerated for members that exist on both sides, but this was not tested (the 37 classes whose definition differs between data files, `classes.md`, show the engine already copes with version differences in `.wld` files). Saves live in the per-mod folder, so a mod's saves are not offered to another mod; the level name stored in the save is a path under `Content/`.

### 6. The chapter save, level travel and the profile

**A chapter** is a checkpoint region of a level (`CChapterInfoEntity`, a linear chain of 1 to 12 per level, `level-logic.md`). The game keeps a **`CStoredLevelStatus`** (members named `sls_sgpGameParams`, `sls_scsCurrentChapter`, `sls_scsFirstChapter`; **two** `CStoredChapterStatus` records, the current chapter's and the first chapter's) and a copy of the **game statistics** (`CGameStats`: `gs_bFrozenStatistic`, `gs_bSaving`, `gs_bCheating`, `gs_slPlayingTime`, `gs_tmPlayingTime`, `gs_slScore`, `gs_ctKillsTotal`, `gs_ctKills`, `gs_ctSecretsTotal`, `gs_ctSecrets`). In memory it is built by `GenerateChapterSaveGame(profile)`, reached from `MarkStarted`. Its content (names from the binary; types from the Hungarian prefix, medium):

| Part | Members | Notes |
|---|---|---|
| status header | the chapter's entity id and the level's file name; the chapter index (or -1); the **game options** (`CSamProjectParams`, the difficulty and the single-player options of `console-config.md`) | a record of the first chapter is also kept (why is not established) |
| **players** | up to **64** `CPlayerSave` (`Handle<CPlayerSave>[64]`); the game info entity itself keeps **17** live player handles | a saved player is matched to a live one **by player name** (`ps_strPlayerName`, `GetSavedPlayer`) |
| `CPlayerSave` | `ps_strPlayerName`, `ps_ulWeapons` (bit set of owned weapons), `ps_ulDoubledWeapons` (bit set of weapons held in pairs), `ps_wiLastSelectedWeapon`, `ps_aslAmmoQuantity` (**11** signed 32-bit counts), `ps_slHealth`, `ps_slArmor`, `ps_ctLives` | **not** the power-up timers (`CPlayerInventory` has `pi_atmPowerUp`, `CPlayerSave` has no match), not position, not score |
| **secrets** | one record per secret entity: id (`sed_ulSecretID`) and state (`sed_sesState`, enum `SecretEntityState`) | restored by entity id |
| **navigation beacons** | `nbd_ulNavigationalBeaconID`, `nbd_bActive` | restored by entity id |
| **mission objectives** | `mod_ulMissionObjectiveID`, `mod_iActivationIndex`, `mod_iRenderingIndex`, `mod_mosMissionObjectiveState` (enum `MissionObjectiveState`) | the generating code stores the id and two further values (medium-low: it is not clear which two of the three members) |

- **Restart in place.** `ResetWorldToChapter(chapter, boot type, resetting type)` does **not reload the file**: it runs every entity's shutdown, clears the think queue, stops the dynamic music, then boots every entity again in sorted order (an *on-boot iterator*) with the stored status at hand, and finally runs every macro entity (skipped when the boot type is **11**), then sends the chapter an event. Which parts of the stored status are applied depends on the **chapter boot type** (an enumeration of at least 12 values, 0 to 11; the data's type table gives no value names): **secrets are restored for the boot types 0, 1, 3, 5, 7, 9 and 10; mission objectives and navigation beacons for 1, 2, 3 and 4** (two small functions, medium). The **world resetting type** (a second enumeration; a call that leaves it 0 gets the value **3** with a log line) says why the reset happens; `ResetWorldToCurrentChapter` passes the value 2. The in-game menu's `Restart chapter` (after a yes/no question) calls a world-info function with the boot type **3** (probably `ResetWorldToCurrentChapter`; medium-low). For boot types 0, 5, 7, 9 and 10 (and 1 when the chapter is the current one) the game totals are recalculated first (`CalculateGameTotalStats`). The stored status is applied in the game info entity's boot function **only if** its level name equals the running level's name and its chapter id equals the current chapter's.
- **Players who are not in the game keep their saved entry.** `StorePlayersData(new status, old status)` first stores every live player (up to 17 slots), then copies from the **old** status every saved player whose **name** is not among the live ones, up to the 64 entries; a player who left therefore keeps their weapons and ammo and gets them back by name when they return (medium).
- **Continue.** The single-player start function, called with an empty level name (the main menu's `Continue playing`), starts the level named in the **active profile's stored level status**; a call with a level name (new game) **discards** that stored status first. If the profile has none, the first level starts.
- **The player's progress in the profile.** `MarkStarted` (single player, a profile present) also (a) records the chapter's level in a list of level names of the profile (once), (b) computes the level statistics record from the game statistics and stores it in the profile, (c) calls `GenerateChapterSaveGame(profile)`, (d) sets the game info's "last save" time stamp (the "Saving..." text), and (e) **writes the profile**. The chapter named `EndGameChapter` takes a different branch (it marks something finished in the profile, probably `pp_bGameFinished`; low). A *favourite chapter* (`StoreFavoriteChapter`, `RestoreFavoriteChapter`) is a developer command that stores a chapter name in a global and restarts from it. The profile is also written **every time a profile option is changed** (auto aim, lives, enemy multipliers, rocket jumping, combo weapons, sprinting, the character, the difficulty, "default settings": 19 callers of the profile writer in all).
- **Level travel.** Moving from one level to the next is a new world started from its level file (the console function `simChangeWorld` exists; the start function above); what the players take along is the **chapter save** in the game info entity and, for a single-player profile, in the profile. The consumers were **not read**: the saved players are looked up by name (`CStoredChapterStatus::GetSavedPlayer`), the player brain has `BootPlayerOnChapter(boot type)` and the engine has `AddWeaponsFromPastChapters` (weapons from earlier chapters) and `SetAmmoFromChapter`; how these combine is T01-091.
- **`Profile.dat`.** The profile is a metadata object of class **`CPlayerProfile`**. It is first **serialised into a memory stream by the metadata writer** (the same writer family as world files), and a **background task** (`CSaveProfileTask`, numbered, with the time of the request) then writes the buffer through a **signed stream** (`CStream::CreateSignedStream`): the stream is cut in blocks, each followed by a **4-byte signature** (two signature types, both 4 bytes, computed from an initial value of all ones and inverted at the end, which is the framing of a CRC-32; the polynomial and block size were not read), plus a header signature. Loading reads the signed stream, loads the object with the metadata loader (`mlLoadMetaObject_t`) and refuses an object that is not a `CPlayerProfile` (`Invalid object loaded`); a bad signature (`Block signature verification failed.`, `Header signature verification failed.`) or any exception makes the profile **damaged** (the main menu offers to delete damaged profiles). The folder `Content/<mod>/PlayerProfiles/<H>/` holds `Profile.dat` and a text file `Profile.txt` (content not read, probably the profile name). Profiles are found by scanning that folder; **at most 64 profiles** load (`plp_iMaxPlayerProfiles`, initial value 64 in the PC build; `Max number of profiles reached. Refusing to load profile.` beyond it; the Xbox configuration sets 4). The temporary profile is never written. With an online service the profile is also uploaded (`onlUploadProfile`, not read).
- **What a profile stores** (member names of the metadata, medium): `pp_strProfileName`, `pp_gdDifficulty`, `pp_pliLastPlayedLevel` (a `pli_strLevelPath`), `pp_apliLevelsPlayed`, `pp_aplsLevelsStats` (per level, `CPlayerLevelStats`: `pls_strLevelPath`, `pls_gdDifficulty`, `pls_ulScore`, `pls_ulTotalScore`, `pls_ctLivesLeft`, `pls_slPlayTime`, `pls_ulEnemiesKIA`, `pls_ulEnemiesMAX`, `pls_ulSecretsFound`, `pls_ulSecretsMAX`, `pls_mtMedal`, `pls_bCheating`), `pp_pslsCurrentStats` and `pp_pslsCoopStats` (statistics of the running and of the co-op game), **`pp_pslsStoredLevelStatus`** (the chapter save), `pp_bGameFinished`, `pp_poOptions` (`CProfilesOptions`: the 24 `pop_` members, which are the settings of `console-config.md`: sensitivity, dead zone, inverted look, mouse look and smoothing, auto aim, auto centre, view bobbing, auto jump, third person, flip fire buttons, weapons list direction, crosshair colour, texture and size, puppet radar, Netricsa messages, auto weapon change, the single-player rules (`pop_bSPUseLives`, `pop_bSPUseComboWeapons`, `pop_bEnableSprinting`, `pop_bEnableRocketJumping`, `pop_iSPEnemyMultiplier`, `pop_iSPEnemyMaxMultiplier`) and the custom button preset), `pp_pibBindings` (the key and button bindings), `pp_pmcMultiplayerChar` (`CProfileMultiChar`: description, model path, character name, thumbnail path), and **`pp_apdAchievementProgressDatabase`** (`CAchievementProgressDatabase`: completed levels and the counters behind achievements: total kills, secrets found, grenades thrown, Serious Bombs used, Klodoviks fired, power-up usage time, extra lives awarded, and the flags "has ever cheated, rocket jumped, sprinted, dual wielded"). The score the end-of-level screen computes (a difficulty bonus of 1,000, 3,000, 5,000, 7,000 or 10,000 for difficulty 1 to 5, a per-life bonus, per-kill and per-secret points and a time term) is stored in `pls_ulTotalScore`; its exact formula is T01-092.
- **Profile versus save.** The **save** is the world (everything of one playthrough at one moment). The **profile** is everything that belongs to the *player* across playthroughs: options, bindings, per-level best statistics, achievements, the chapter save used by Continue, the name. The game rules of the single-player settings screen are **copied into** the chapter save (as `CSamProjectParams`) as well as kept in the profile.

### 7. Rules and limits

| Rule | Value | Confidence |
|---|---|---|
| Sessions that may save or load | **only a local (single-player) session**; a hosted game, a dedicated server and a client are all refused, so **co-op and deathmatch have no saves** | high (three independent checks) |
| In-game menu | the `Save game` and `Load game` links exist in the in-game menu; their enabling is computed from "local session", "player alive" and "lives" among other flags (which flag gates which link was not resolved) | low (T01-094) |
| In combat, on high difficulty, in cutscenes | **no such rule found** in the save path | medium (negative; a rule in a gadget-enable function would not be seen) |
| Number of saves | **no limit found** (the list scans the folder); the text "maximum saved games" appears only in the *profile* limit message | medium |
| Quick-save slot | exactly one (`QuickSave`), overwritten each time without confirmation | medium |
| Profiles | at most 64 (PC) | medium |
| Overwrite | asks `Overwrite?` and then for a name | medium |
| Write errors | the profile writer logs `Error saving player profile into <path>.` and carries on; the `.sav` writer throws a resource error; **no backup copy** | low |
| "Saving..." text | 1.0 s after the last-save stamp; drawn at the position given by the HUD element's parameters (default 50, 130 in the HUD's units) | medium |
| Typical size | unknown; expected of the order of the level file (the 59 shipped worlds: 33 KB to 22.8 MB, median 10.3 MB) | low |

### 8. Demos are not saves

A demo (`.dem`, with a `.nfo` of `NAME` and `TIMESTAMP`) records **network messages**, not a world. Recording starts, in any of the three interface kinds (local, server, client), by creating a connection-response record tagged `DemoRec` that carries the **world name and a snapshot of what a joining client would be sent** (the handle remap list, the module list and the state), and then every message is appended with its time. Playback (`CDemoPlaybackInterface`) is a network interface kind of its own: opening the file expects the two chunk ids, a `u32`, a `TIME` chunk and **sets the simulation clock to that recorded start time**; the world named in the header is then loaded through the normal connection path (not read). The engine has the message `Can't play demo file because it was saved in some other version.` and the file stores a build string; how the two are compared was not read. Measured on the three shipped demos (`savegame_verify.py`): file magic `DMSTAVTR` (two four-letter chunk ids `DMST` and `AVTR`), a `u32` of **16** (the recorder's slot count or index, meaning not established), a chunk `TIME` with a 64-bit `Time` (the start: 6.429 s, 78.676 s and 12.374 s), a second `TIME` chunk with the same value, a `MSGS` chunk whose first message carries the text `$Version: Serious Sam 2; 2.068.00:61409; 2006-PATCH-2-068-inc$` and the level path, and the four bytes **`DMEN`** at the very end; sizes 2,029,309, 1,052,862 and 1,430,104 bytes for demos of `2_3_Branchester`, `5_1_Village` and `7_2_City_Part_II`. The message framing after that was not decoded (T01-095). Demos matter to us as **a worked example of "what a client needs to join a running game"** (`T01-031`), not as a save format. Demo names: `<folder>Demo_<n>.dem` with `n` from 0 up to the first free file (at most 10,000 tried).

### 9. What must persist in our engine

Our side: `ss2_sim::save` (`docs/SAVES.md`: persistent properties of every entity, parents, tick, seed, players, notes of at most 256 bytes, CRC-32 and schema hash; "a system's private state must live in properties"), `ss2_game::level_progress` (counters and **checkpoints with an opaque payload**) and `ss2_game::campaign` (`CampaignNote`, `CarryOver`, `UnlockSet`). The columns say what the original does, how sure this page is, and what follows for us.

| Category | Original behaviour | Conf. | Implication for our engine |
|---|---|---|---|
| Entities and their state | the **whole world** is deep-copied: all entities and all serialised members; nothing is "opted in" | medium | Ours saves only **persistent** properties. Every gameplay-relevant property of every class must be marked persistent (or a test must list those that are not). Static level content (models, lights, hulls) is **not** saved by us; it comes back from the level, so a save is tiny by comparison. |
| Simulation clock | saved as a `Time`; restored with the "last step 0.001 s" rule | medium | Our tick count is in the header: keep it as the clock; **timers must be stored relative to the clock** (ticks), never as wall time. |
| Think queue and timers | inside the world (state manager); due times are absolute clock values; consistent after the clock is restored | medium | **Not saved by ours today** (the event queue is not); a timer set by script or system must be a property or be re-armed on load. Required for parity of "a door that closes in 3 s". |
| Running scripts (macro threads, waits) | inside the world (macro domain); continue after load; **level start events are not re-run** | medium | Our scripts' program counters, waits and local variables must be persistent state; loading must **restore, not boot** (no level-start event). |
| Random numbers | **not saved**; process-wide, two words, seeded from the CPU time-stamp counter at start-up; nothing writes them except start-up and the random-table set-up; no cross-process determinism | medium | Parity needs nothing. Ours keeps the **seed** in the header (more than the original); do not promise bit-identical replays after a load unless the generator state itself is saved (decision for T08). |
| Players (puppets, brains, inventory, health, ammo, weapons, score) | entities in the world, so fully saved; plus the **chapter save** summary `CPlayerSave` (name, weapons, doubled weapons, last weapon, 11 ammo counts, health, armor, lives) | medium | Ours: `PlayerCarry` for level carry-over (health, armor, weapons, ammo, items: **add power-up timers if they should survive; the original's chapter save does not carry them**); full player state belongs to persistent properties. A saved player is matched by **name** in the original; ours needs a **slot-to-profile identity** for co-op loads. |
| Player statistics (kills, secrets, score, time, cheat flag) | `CGameStats` in the game info entity; copied into the chapter save and the profile's per-level stats; shown in the `.nfo` | medium | `level_progress` has the counters; the save **notes** (256-byte limit) are enough for a list line; keep the cheat flag. |
| Secrets, beacons, objectives | per-entity state in the world, **and** a restore list in the chapter save applied by entity id at boot, by boot type | medium | `level_progress` keeps found secrets; **beacons and objective states are not modelled**: add them to the checkpoint payload. Keep the rule that **secrets are restored on a restart but objectives follow different boot types**. |
| Chapter / checkpoint | automatic at **chapter start**; restart in place by re-booting entities (no reload); a first-chapter record is also kept | medium | Matches `level_progress` checkpoints (reached in order, first payload kept). The **rewind of counters** on restore is ours; the original's boot-type table is the reference for what a restart restores (T01-091). |
| Game options and difficulty | stored in the chapter save as `CSamProjectParams` and in the profile | medium | `CampaignNote` carries difficulty; add the single-player rule flags (lives, combo weapons, sprinting, rocket jumping, enemy multipliers). |
| Level identity and version | the source level's **file name** and **save counter**; a save newer than the installed level is refused (one-directional) | medium | Ours is stricter (schema hash; level-list fingerprint) and refuses more; keep a human-readable level id in the notes. Mods: keep saves per mod. |
| Camera and view | no separate record found; the view belongs to the player entities | low | Not needed beyond player state (T01-093). |
| Sound, music, movies | the sync lists are world members (suspended while saving); the world info entity holds the current dynamic-music selection, volume multiplier and change time; **playback positions are engine state, not world state** | low | Persist the **selection** properties; start the music again after load; do not persist playback offsets. |
| Particles, effects, debris | effect entities and the world info's live-debris list are entities (saved if present); GPU particle state is not world state | low | Cosmetic: do not persist; let them be re-created. |
| Pending events / queued messages | not examined | open | T01-093. |
| UI, menus, HUD, console | **not saved**; the HUD "Saving..." text is drawn after the fact | medium | Not saved. |
| Options, bindings, achievements, unlocks | **profile**, not the save | medium | Keep in a profile/settings file (we have `settings.toml`); the unlock set is in `CampaignNote`. |
| Network session | not saved; saving and loading are refused in network games | high | **Co-op saves are new work** (`T08-022b`): decide who may save (host only), how many players the file records, how clients rejoin, and whether the join-in-progress snapshot (T08-013) can be reused. |
| File handling | the `.nfo` is written **before** the `.sav`, in place, no temporary file or backup; a list entry with no `.sav` is dropped | medium | Ours should write to a temporary name and rename; write the list metadata **last or inside the file's header** so a crash cannot leave a listed broken save. |
| Slots | one quick slot, numbered slots without a limit, per profile and mod | medium | Matches `SAVES.md`'s open "slots" item: a folder per profile, `QuickSave` plus numbered slots, no cap needed. |

## Invariants

1. **`CWorld.18` is the member of type `CWorldSaveData*`, and it is null in 107 of 107 versions of the 59 shipped worlds** (script). A reader that finds it non-null is looking at a save, not a level.
2. **The save counter (`CWorld.19`) never decreases from one patch level of a level to the next**: checked on all 31 worlds that appear in more than one archive (script); it rises strictly in all 31.
3. **None of the classes a save adds is defined by any data file** (13 class names checked over 9,269 format-8 files): a reader of a save **must take their definitions from the file's own type tables**, not from the data of the install.
4. A `.sav` is **loaded only in a single-player session**, and saving is refused in every other kind (three independent checks).
5. The saved clock is a `Time` (2⁻³² s units); after a load the last step is 0.001 s and the clock equals the saved value exactly.
6. **A load does not run the level-start events** (the flag path in the engine); **the list drops an entry whose `.sav` is missing**.
7. **A save made from a level whose counter is higher than the installed level's** is reported as not matching (the failure message is sent when `sim_bCheckWorldVersion` is 1, which is the default).
8. The `.nfo` is UTF-8 with a byte-order mark and CR LF line ends; a reader ignores unknown keys; the demo `.nfo` in the install is 59 bytes for `Demo_0001` (test vector 1).
9. The `.preload` files of the install have **no line for the level file itself** (0 of 46); a save's list does (the appended line).

## Open questions

Ranked by what blocks an implementer. Every item that needs the running game is assigned to the oracle tasks or a new follow-up.

1. **A real save.** The container version, header bytes, the stored form of `CWorldSaveData`, the real size, the real content of the entity list (which members are left out), whether the file is compressed, and whether `CWorld.18` is the only change to the world: need one `.sav`, one `.nfo`, one `.preload` and one `Profile.dat` made by the original (a few seconds of play on a machine that has the game running; numbers and structure only, never committed): **T01-090** (deps T01-038, T11-008).
2. **Chapter boot types and world resetting types** (names and values of the two enumerations, which caller passes which, exactly what each restores, the order of an inter-level travel, how players' inventory reaches the next level, what `EndGameChapter` does): **T01-091**.
3. **The end-of-level score and medal formula** and the per-level statistics in the profile (`pls_*`), difficulty bonuses (1,000 to 10,000), the "frozen statistic" flag: **T01-092**.
4. **Which members of which classes are not saved** (`SMF_DONTSAVE`, `SMF_TEMPORARY`, `SMF_DONTCOPY`), what the sync lists, the music source, particles and pending events do across a save, whether the camera is saved: **T01-093** (static reading of the class declarations of the ~1,000 classes, or the oracle).
5. **Run-time gating and the load failure path**: when `Save game` and `Load game` are enabled in the in-game menu (alive? lives?), what `gs_bSaving` is for after a load, whether `Message.Simulation.WorldLoadFailed` stops a load for a newer-level save or only informs, what the game does with a `.sav` of a missing level, and the `.nfo` key order the writer uses: **T01-094** (deps T01-038).

7. **Profile file layout and location**: the signed-stream block size and polynomial, the string hash behind `<H>`, where `Content/` is written (user folder or install), `Profile.txt`: already **T01-081**.
8. **`.preload` use at load** (prefetch order and what the `-1:` lines mean): already **T01-088**.

## Test vectors

1. **A demo's `.nfo`** (59 bytes, the shipped `Demo_0001.nfo`): `EF BB BF` (UTF-8 mark), then `NAME="BRANCHESTER"` + `0D 0A`, then `TIMESTAMP="Mon, 13-02-06 14:57:52"` + `0D 0A`. Decoded: name `BRANCHESTER`, time stamp `Mon, 13-02-06 14:57:52` (13 February 2006 was a Monday; the format is `%a, %c` with a day-month-year date). 3 + 18 + 2 + 34 + 2 = 59.
2. **A demo's start time** (`Demo_0001.dem` bytes 16 to 23, after `DMSTAVTR`, `10 00 00 00`, `TIME`): `DC 01 E3 6D 06 00 00 00` little-endian = 27,613,397,468 ticks = **6.429245 s** (divide by 2³² = 4,294,967,296). The same value follows the second `TIME`.
3. **The save-data marker** for a save made while playing the level whose path is `Content/SeriousSam2/Levels/02_Magnor/2_3_Branchester/2_3_Branchester.wld`: the stored string is `{WLD_SRC_FN_START:Content/SeriousSam2/Levels/02_Magnor/2_3_Branchester/2_3_Branchester.wld:WLD_SRC_FN_END}`; `GetSourceWorldFN` on the `.sav` returns the path between the markers; on a file that is not a `.sav` it returns the argument unchanged.
4. **File names of new slots**: empty folder gives `Save_0000`; the names `QuickSave`, `Save_0000`, `Save_0007` (descending order: `Save_0007`, `Save_0000`, `QuickSave`) give `Save_0008`; the name `QuickSave` alone gives `Save_0000`; the quick save is `QuickSave.sav` with `QuickSave.nfo`.
5. **The version rule**: `1_1_Jungle.wld` has the counters **6, 13, 14** in its three versions (`All_PC_02.gro`, `Patch_02_090_593613.gro`, `Patch_02_100_800000.gro`). The three versions of `Content/SeriousSam2/Levels/01_Mdigbo/1_3_Village/1_3_Village.wld` in the install (`All_PC_02.gro`, `Patch_02_090_593613.gro`, `Patch_02_100_800000.gro`) have `CWorld.19` = **4, 12, 13**. A save recorded against counter 13 loads on version 13 and, by the rule, reports a mismatch on versions 4 and 12; a save recorded against 4 passes on all three.
6. **A `.preload` line**: `158491:Content/SeriousSam2/Fonts/SeriousVerdana.fnt` (size, colon, path; CR LF). The line appended by a save has the same shape with the level file's size and path.
7. **Limits to test against**: at most 64 profiles; the "Saving..." text is visible for 1.0 s; 11 ammo counts per saved player; up to 64 saved players per stored status; the game info entity holds 17 live player handles.
8. **The script's numbers** (see the run in the pull request): 59 worlds, **107 versions**, null save-data pointer in 107 of 107, counter 3 to 1,696, strictly rising in 31 of 31 multi-version worlds, final world sizes 33,217 to 22,830,096 bytes (median 10,308,185), 13 save-related classes defined in 0 of 9,269 files, 46 `.preload` files with 56,471 lines (257 of them `-1:`, 0 listing their own world), 3 demos.
